## 사용자 없이 다음 작업을 이어가는 구조

자율 작업 생성·개발·검증은 첫 운영 버전의 필수 기능입니다. 초기 연결 검증에서만 읽기 전용 분석을 사용합니다. 사용자 지시는 목표와 방향을 설정하고 바꾸는 수단이며, 개별 작업을 시작할 때마다 필요한 조건은 아닙니다.

```text
프로젝트 목표·허용 범위
  → 총괄: 현재 코드·테스트·미완료 작업 확인
  → 다음 작업과 완료 기준 선택
  → 개발: 분리된 작업 공간에서 구현·테스트
  → 검증: 변경과 테스트 근거를 확인하고 재작업 요청
  → 검증된 변경·결과 기록
  → 남은 목표를 확인해 다음 작업 선택 ↺
```

### 역할과 작업 선택

- 총괄은 목표와 현재 코드의 차이, 실패한 테스트, 이전 검토에서 남은 항목을 근거로 작업을 제안합니다. 서버는 목표 범위·중복·의존 작업·실행 예산을 확인한 뒤 작업을 저장합니다.
- 개발 역할은 선택된 Task를 구현합니다. 검증 역할은 별도 호출·대화 맥락에서 동일한 변경 버전과 완료 기준을 확인합니다. 같은 모델을 사용할 수 있으며, 역할 분리만으로 판단의 정확성이 보장되지는 않습니다.
- 역할 간 전달에는 Goal·Task·Run ID, 코드 버전, 변경 내용, 테스트 결과, 검토 의견을 포함합니다. 대화가 오갔다는 사실보다 실제 결과와 검증 근거를 기록합니다.
- 초기에는 서버 전체에서 Run 하나를 실행하고, 그 Run의 AI 호출·도구 실행·검증을 순서대로 처리합니다. 총괄의 계획 Task와 개발·검증을 수행하는 실제 Task는 각각 자신의 Run을 갖습니다. 여러 역할의 협업은 첫 버전에 포함하고, 여러 프로세스의 동시 병렬 실행은 후속 확장으로 둡니다. 계획·개발·검증 호출 모두 같은 동시 실행 제한과 계정 한도를 따릅니다.
- 프로젝트 우선순위와 마지막 처리 시각을 함께 고려해 한 프로젝트가 계속 차지하지 않게 합니다. 실행 불가능한 목표는 건너뛰고 다른 실행 가능한 목표를 처리합니다.

### 내부 에이전트의 역할 지침

총괄·개발·독립 검토·수동 분석에는 역할별 gstack 판단 기준을 적용합니다. 지침은 서버 패키지의 `skills/gstack/`에 고정하며, 원본 버전과 제품용 지침 버전·내용 해시를 구분합니다. 제품용 모드는 `adapted_instructions`입니다. 호스트나 프로젝트의 스킬을 자동 검색하지 않고, 이 지침만으로 gstack CLI·브라우저·추가 모델을 실행하지 않습니다.

로더는 고정된 파일만 읽고 manifest와 각 파일의 해시를 확인합니다. 지침 하나가 빠지거나 바뀌어도 묶음 전체를 거부하며, 심볼릭 링크·일반 파일이 아닌 항목·크기 초과도 허용하지 않습니다. 개별 파일 상한은 32KiB, manifest 상한은 16KiB, 묶음 전체 상한은 128KiB입니다. 오류는 배포 경로나 파일 본문 없이 `unsupported_settings`로 반환합니다. 이 검사는 배포 누락과 버전 혼합을 감지하며, 서버 코드와 지침을 함께 바꿀 권한이 있는 관리자의 변경을 막는 장치는 아닙니다.

파일 읽기는 DB 트랜잭션 밖에서 수행합니다. 부모가 역할·버전·해시를 선택하고 실행기가 실제 지침을 읽은 뒤, 현재 Step에 로드 기록이 저장됐다는 응답을 받아야 AI 호출을 시작합니다.

선택과 로드 확인을 별도로 저장하며, 과거 실행에는 적용 기록을 추정해 채우지 않습니다. 새 Run은 배정할 때 지침 정책 버전을 고정하고, 성공 확정과 복구에서도 각 Step의 로드 기록을 확인합니다.

인증된 실행 조회와 작업 상세 화면에는 당시 역할·적용 방식·버전·해시·크기·선택/로드 시각을 표시합니다. 선택만 된 상태와 읽기 확인, 기록 없음을 구분하며 지침 읽기만으로 작업 성공을 표시하지 않습니다.

조회는 저장된 값을 사용하므로 배포 지침을 교체해도 과거 기록을 바꾸지 않습니다. 실제 Codex의 계획·개발·독립 검토 호출에서 적용 기록과 결과를 확인했습니다.

예산·취소·테스트·변경 반영은 계속 서버 규칙으로 집행합니다.

컨테이너에는 먼저 작업 내용이 없는 버전 확인 메시지를 보냅니다. 실행기가 지원 버전과 자체 지침 묶음을 확인한 경우에만 작업을 전달하므로, 새 필드를 무시하는 구버전 실행기가 먼저 AI를 호출할 수 없습니다. 이후에도 호출마다 해당 역할의 지침을 다시 읽고 저장 응답을 기다립니다. 저장 실패·취소·버전 불일치에는 호출을 허용하지 않습니다. AI 인증이 없는 실제 테스트 실행은 지침 적용과 AI 호출 수에서 제외합니다.

### 현재 목표 관리의 구현 범위

Goal의 정의·유한/지속 관리 구분·우선순위·허용/제외 경로·점검 간격·기간 예산과 상태·버전을 저장합니다. 등록·수정·일시정지·재개 및 변경 이력 API와 화면이 있습니다. 기본 점검 간격은 15분, 기간 예산은 1시간당 20호출·30분 실행입니다. 경로는 작업 폴더 기준의 정규화된 상대 경로이며 절대 경로·상위 폴더 이동·글롭 패턴은 거부합니다.

Task에 종류·목표·판단 당시 버전을 연결하고, 배정·수동 재개·자동 복구·사용 한도 확인 실행에서 같은 목표 상태·버전 검사를 적용합니다. 일시정지·완료·다른 프로젝트의 목표와 오래된 버전은 새 Run을 만들지 못합니다. 일반 대기열은 실행할 수 없는 목표의 작업을 건너뛰며, Run에는 시작할 때의 목표 버전을 보존합니다. 목표를 일시정지해도 기존 실행의 결과 저장·종료 대조·사용자 취소는 계속 가능합니다.

기간 예산은 프로젝트·목표 양쪽에서 집행합니다. 내부 계획 모듈은 예약·호출·제안 검증·작업 생성·다음 점검 시각 저장까지 구현했습니다.

실행 서버는 개발 이미지·작업 폴더·고정 테스트·종료 확인 설정이 준비된 목표의 계획을 자동 예약합니다. 최초 `nextCheckAt`이 null이면 즉시 점검 대상이며, 실제 AI 호출은 기존 대기열의 계정·예산 검사를 통과한 뒤 시작합니다.

취소한 계획 생성 작업의 명시적 재허용과 개발 실행을 연결했습니다. 계획에서 생성한 이전 버전 작업은 현재 범위와 대조해 재연결하며, 경로 근거가 없는 기존 작업은 계속 보류합니다.

목표 없는 수동 Task는 프로젝트 예산을 적용하며 목표 일시정지나 내용 변경으로 바뀌지 않습니다. 계정 사용 한도 확인의 원인 작업이 목표 변경으로 실행 불가능해지면 계정 보류를 유지합니다.

자동 한도 확인을 켠 경우, 목표 변경으로 실행할 수 없어진 원인 작업 또는 시작 전 확인 작업 대신 다른 적격 작업을 선택합니다. 계정 차단 자체는 확인 실행이 성공하고 종료가 증명될 때까지 유지합니다.

Goal 변경과 해당 버전의 전체 내용(`GoalRevision`)은 한 트랜잭션으로 저장합니다. 요청 키로 같은 변경의 중복 반영을 막고, `expectedVersion`으로 오래된 화면의 덮어쓰기를 거부합니다. 중복 요청은 당시 저장한 응답을 반환하며 현재 Goal을 과거 상태로 되돌리지 않습니다. 버전 이력은 목표·기준·범위가 언제 달라졌는지 확인하기 위한 기록입니다. 목표 완료는 검증된 계획 결과를 반영할 때만 처리하며 수동 완료 명령은 제공하지 않습니다.

### 현재 목표 기반 실행의 입력 경계

Goal에 연결된 Task를 배정할 때 해당 버전의 허용·제외 경로를 함께 고정합니다. 실행기는 자료 준비 의도를 Run에 저장한 다음, 변경 없는 Git 작업 트리의 HEAD에서 허용한 일반 파일만 읽습니다.

계획 작업에 이미 개발용 저장소가 있으면 DB에 반영 완료로 기록된 개발 브랜치의 커밋을 사용합니다. 원본과 개발 저장소의 식별 정보·기준 버전을 함께 보존하며, 반영 미확정이나 준비 중인 개발 저장소가 있으면 원본으로 돌아가 계획하지 않습니다.

원본 파일을 따라 복사하지 않고 커밋 객체의 내용을 사용하며, 원본 저장소의 Git 메타데이터와 이력은 복사하지 않습니다. 준비한 폴더에는 상위 저장소의 설정을 상속하지 않는 새 Git 루트를 만듭니다.

준비 완료 기록에는 목표 버전·원본 커밋·파일 목록·내용 객체 ID·자료 해시를 남깁니다. 기록 저장 실패나 현재 목표 상태·버전 불일치는 AI 호출을 막습니다. 허용 범위의 심볼릭 링크·서브모듈, 숨겨진 작업 트리 변경, Git 필터 설정, 파일 수·크기 초과는 `input_unavailable`로 보류합니다. 알려진 인증·환경 설정·DB 경로를 제외하며, 알 수 없는 비밀까지 탐지한다고 보장하지 않습니다.

서버와 CLI 모두 준비한 폴더를 기존 읽기 전용 실행기에 전달합니다. Docker 자식이 전달한 준비 메타데이터는 신뢰하지 않습니다.

준비 이후와 분석 결과 수신 뒤 원본 변경을 다시 검사하며, 변경됐으면 `input_changed`로 보류합니다. 개발 브랜치에서 읽은 계획은 실제 브랜치와 DB의 기준도 대조합니다.

재시작 후에도 저장된 같은 기준으로 확인하고, 바뀐 기준에서 나온 오래된 제안은 적용하지 않습니다. 완료 저장·종료 복구 때 목표가 달라졌으면 `goal_changed`로 보류하고 오래된 결과를 성공으로 적용하지 않습니다.

허용 범위를 줄이는 변경은 해당 Goal의 실행 중이거나 종료 미확인인 Run에 `scope_changed` 중단 요청을 함께 저장합니다. 목표 일시정지·내용 수정·범위 확대는 이 중단을 요청하지 않습니다.

준비 폴더는 DB별 비공개 경로 아래에 실행별로 만들고 소유권 표식을 기록합니다. 종료 증명을 DB에 저장한 뒤 일치하는 폴더만 삭제하며, 종료 미확인·표식 불일치에는 삭제하지 않습니다. 종료 증명 저장 직후 서버가 중단돼도 다음 시작 때 정리를 재시도합니다. 직접 SDK 모드에는 종료 확인 기능을 새로 부여하지 않으므로 이 모드의 미확인 자료도 보존합니다. 원본의 변경은 수정하거나 되돌리지 않습니다.

목표 없는 기존 수동 분석은 기존 작업 폴더를 사용합니다. 목표 기반 계획은 이 자료 준비 경계를 사용하며, 실제 코드 변경은 별도 개발 실행 단위에서 연결합니다.

### 현재 계획 예약과 결과 반영

`planning_cycles`에 계획 Task·목표 버전·결과를 반영한 Run을 연결합니다. Goal별 `reserved` 기록은 DB 제약으로 하나만 허용합니다. 대기열은 복구와 실행 환경 검사를 마친 뒤 계획을 예약하고 작업을 배정합니다. 미완료 작업·기간 예산·다음 점검 시각과 같은 프로젝트의 미확정 반영을 확인합니다. 실행 전 계획 예약은 AI 호출을 만들지 않습니다. 기존 배정 경로에서 Run·첫 Step·예산을 함께 예약한 뒤 호출합니다. 한 계획은 한 번의 구조화된 총괄 호출을 사용하며 일반 분석의 다단계 설정과 섞지 않습니다.

총괄 입력에는 목표 정의·기준 코드 버전·자료 해시·파일 목록과 최근 작업 최대 20개의 상태·지시 발췌·마지막 실행 결과 발췌를 담습니다. 별도로 재생성을 막는 작업 최대 20개와 각 작업의 대상 경로 최대 5개·검증 기준 발췌·전체 억제 작업 수를 전달합니다. 입력에서 생략된 오래된 기록도 서버의 검사 대상에는 포함합니다. 과거 결과와 파일 내용은 판단 자료이며 실행 권한을 바꾸는 지침으로 취급하지 않습니다. 같은 프로젝트의 서비스 관측도 다음 규칙으로 전달합니다.

계획 배정 시 같은 프로젝트에 현재 설정된 서비스만 읽고, 관측 화면과 같은 판정 함수를 사용합니다. 연결 대상의 설정 식별값이 같은 최신 수집과 마지막 수집 성공을 따로 읽습니다. 설정에서 제거한 대상은 계획에서 제외하며, 현재 서버의 관측이 꺼졌거나 저장 오류가 있으면 과거 성공을 현재 정상으로 표시하지 않습니다. 조회는 저장된 SQLite 자료만 사용하고 DB 트랜잭션 안에서 외부 서비스에 접속하지 않습니다. 주소·인증 설정은 입력에 포함하지 않습니다.

관측에는 `capturedAt` 당시의 판정과 근거, 수집 시각·관측 ID·대상 요약을 남깁니다. `lastSuccessful`은 **수집이 성공했던 기록**이며 업무가 정상이라는 뜻은 아닙니다. 새 관측이 계속 도착한다고 진행 중 계획을 매번 무효화하지는 않습니다. 입력은 해당 시점의 증거이고, 실제 변경의 효과와 목표 완료는 별도 개발·검증에서 확인해야 합니다. 현재 건강 상태 신호만으로 매매 전략 성능이나 수익률을 판단하지 않습니다.

전달할 자료는 `Run.planningInput`에 모델 호출 전에 저장합니다. 목표·기준 코드·자료 해시·선정한 이력·서비스·파일 목록과 항목별 전체/포함 개수가 함께 남습니다. 저장 실패 때는 호출하지 않으며 실행 자식이 보낸 같은 이름의 필드로 이 기록을 덮어쓸 수 없습니다. 재시작이나 이후 관측 변경에도 당시 자료를 보존합니다. 인증된 실행 조회의 `planningEvidence`와 화면에는 당시 서비스 근거와 발췌 개수를 제공합니다. 내부 자료 폴더의 절대 경로와 서비스 접속 설정은 공개 응답에 넣지 않습니다.

지시문을 포함한 JSON은 UTF-8 기준 60,000바이트 이내로 제한합니다. 서비스·억제 작업·과거 이력·파일 목록에서 번갈아 항목을 넣어 큰 파일 목록 하나가 공간을 모두 차지하지 않게 합니다. 항목이 안 들어가면 생략하고 전체/포함 개수에 반영합니다. 목표 정의·허용/제외 경로는 항상 온전히 유지하며, 필수 자료만으로 상한을 넘으면 `input_unavailable`로 보류합니다. 개별 목표 필드의 글자 수 제한을 만족해도 한글·이스케이프 문자의 합산 크기에 따라 이 제한에 닿을 수 있습니다. 생략된 이력도 서버의 취소·중복·범위 검사는 그대로 적용합니다.

제안은 종료 대조보다 먼저 `Run.planResult`에 저장합니다. 종료가 확인된 뒤 현재 목표·버전·자료 해시·허용 경로·제안 간 겹침을 검사하고, 계획 적용·후속 Task·Run 완료를 한 트랜잭션에서 확정합니다. 저장 실패에는 생성된 작업도 함께 되돌리며 앞서 보존한 제안은 남깁니다. 재시작 후 저장된 제안이 있으면 원본 변경 여부와 실제 종료를 다시 확인해 한 번만 반영합니다. 실패한 제안을 새 계획 Task로 갈아치우지 않고 같은 Task의 실행 이력·재시도 제한을 유지합니다.

`wait`는 같은 상태를 AI가 주기적으로 다시 읽으라는 뜻이 아닙니다. 서버는 점검 주기에 비용 없는 DB 상태 비교만 하고, 목표 버전·반영된 개발 커밋·실제 작업 상태·서비스 관측 내용이 바뀐 경우에만 새 계획을 예약합니다. 계획 작업 자신의 이력, 관측 ID·수신 시각·단순 heartbeat는 재호출 근거에서 제외합니다. 서비스가 정상에서 오래된 관측이나 장애 상태로 바뀌는 것은 실제 변화로 취급합니다. 비교 기준은 AI 호출 전에 저장한 계획 입력에 남기므로 재시작해도 유지되며, 호출 중 발생한 변화도 다음 점검에서 확인합니다.

기존 계획 입력에 비교 기준이 없으면 한 번 새로 판단해 기준을 저장합니다. 원본 폴더나 원격 저장소의 변경을 자동으로 가져오는 기능은 아닙니다. 자료를 작업 환경에 반영한 뒤 목표를 수정하거나 일시정지 후 재개하면 새 버전으로 다시 판단합니다. 반복 대기 때문에 목표를 완료 처리하거나 취소·실패 기록을 초기화하지 않습니다.

작업은 한 제안에 최대 3개이며 각 작업에 대상 경로·검증 기준·근거와 기준 코드 버전을 남깁니다. 작업 이름을 바꿔도 같은 목표 버전·대상 경로·기준 커밋이면 중복 생성을 억제합니다. 이는 의미가 같은 모든 문제를 알아내는 기능은 아닙니다. 대기·실행·종료 미확인·복구 중인 작업이나 경로 근거를 알 수 없는 미완료 작업이 있으면 새 계획을 보류합니다. 종료가 확인된 취소·실패·보류 작업은 해당 경로의 재생성을 억제하고 다른 경로의 작업은 계획할 수 있습니다. 취소한 계획 생성 작업은 사용자가 명시적으로 다시 허용할 때 연결된 새 Task로 처리합니다. 기존 계획 작업의 범위 재검사·재연결은 구현했습니다.

대기 판단과 중복만 남은 판단은 `nextCheckAt`을 기록합니다. 같은 목표 버전에서 중복이거나 억제된 작업만 제안한 판단이 세 번 이어지면 `planning_no_progress`로 보류합니다. 사용자가 계획 Task를 취소하면 Goal 일시정지와 버전 이력도 함께 저장합니다. 목표 재개 뒤 이전 계획은 실행 종료가 확인됐을 때만 정리합니다. 유한 목표의 완료 제안은 아래의 독립 검증을 거치며, 근거가 없거나 일치하지 않으면 `verification_required`로 보류합니다.

계획이 만든 `plannedWork` 작업은 읽기 전용 분석에 배정하지 않습니다. 개발 실행 설정이 준비된 경우에만 개발 실행기에 배정하고, 설정이 없으면 `development_pending`으로 보존합니다. 자료 확인과 DB 저장 사이에 외부 파일이 다시 바뀔 가능성은 남으므로, 후속 개발 실행은 기준 코드·허용 범위를 다시 확인해야 합니다.

취소·실패 작업의 재생성 검사는 계획 예약과 최종 반영 때 현재 DB를 읽어 수행합니다. 파일 경로를 NFC·소문자로 비교하고 같은 경로·상위 폴더·하위 경로가 겹치면 해당 제안을 제외합니다. 제목 변경, 대상 경로 추가, 목표 수정이나 코드 커밋 변경으로 이 제한이 풀리지 않습니다. 한 제안에 억제 대상과 다른 작업이 함께 있으면 허용된 작업만 생성하고 원래 제안과 제외 이유·기존 작업 ID를 `planResult.suppressed`에 남깁니다. 기록이 많으면 제안별 대표 ID 20개와 전체 개수를 저장하며 실제 검사는 전체 이력에 적용합니다.

이 규칙은 문제 의미를 완전히 판별하지 않습니다. 같은 파일의 다른 결함도 억제할 수 있고, 전혀 다른 파일로 표현된 같은 의미까지 알아내지는 못합니다. 생성된 작업의 실제 변경·검증에서도 범위와 목표 적합성을 확인해야 합니다. 실행 중인 작업·종료 미확인·진행 중 복구·경로 근거 부족은 제안 일부만 빼는 방식으로 우회하지 않고 계획 전체를 보류합니다.

### 취소한 작업을 다시 허용하기

`POST /tasks/:id/release`는 `requestKey`와 조회 당시 `expectedGoalVersion`을 받습니다. 계획에서 생성한 `cancelled` 실제 작업만 대상입니다. 활성 목표·프로젝트 연결·목표 버전·당시와 현재의 허용 범위·모든 Run의 종료 근거·진행 중 복구 유무·누적 제한을 확인합니다. 한 조건이라도 맞지 않으면 새 작업을 만들지 않습니다. 실패·보류 작업은 기존 복구 절차를 사용하며 새 Task로 바꾸지 않습니다.

취소한 원본은 그대로 두고 같은 작업 내용의 새 Task, `task_releases` 연결과 당시의 실행 횟수·복구 상태를 함께 저장합니다. 정책이 없던 과거 작업은 기존 실행 이력으로 정책과 소비량을 먼저 복원합니다. 원본 하나에는 새 작업 하나만 연결할 수 있습니다. 같은 요청을 다시 보내면 목표가 이후 바뀌었더라도 원래 접수 결과를 반환합니다. 다른 키로 원본을 다시 허용하거나 같은 키의 내용을 바꾸면 거부합니다. 저장 도중 실패하면 목표·새 작업·연결도 함께 되돌립니다.

새 작업은 이전 재시도 횟수·연속 오류·누적 시간을 이어받습니다. 앞선 실행이 있었으면 새 Task의 첫 Run도 재시도 한 번으로 계산합니다. 아직 한 번도 실행하지 않은 작업은 재시도 허용 횟수가 0이어도 최초 실행은 허용합니다. 여러 번 취소·재허용하거나 서버를 재시작해도 연결에 저장한 기준값으로 제한을 유지합니다. 계정 차단과 Goal·프로젝트 기간 예산은 별도 기록 그대로 적용합니다.

이 조작은 사용자 의도가 바뀐 것으로 기록해 Goal 버전을 하나 올리고 `nextCheckAt`을 비웁니다. 목표 정의는 바꾸지 않으며 다른 기존 작업은 같은 트랜잭션에서 범위를 재검사합니다. 이전 버전의 계획 결과는 적용할 수 없고, 오래된 계획 예약도 실행 종료가 확인돼야 정리할 수 있습니다. 원본의 재생성 억제는 연결된 새 작업으로 이어집니다. 새 작업이 대기·실행 중이면 계획을 보류하고, 다시 취소·실패하면 해당 경로의 억제를 유지합니다. 새 작업이 성공해야 원본 취소가 이후 계획을 계속 막지 않습니다.

작업 조회의 `planningTaskId`는 생성 근거인 계획 작업, `previousTaskId`·`nextTaskId`는 재허용 전후 작업입니다. 화면에서 이 연결을 따라 기록을 확인할 수 있습니다. 재허용은 실행 완료를 뜻하지 않으며, 개발 실행기 연결 전에는 새 작업도 `development_pending`으로 남습니다.

### 언제 다음 일을 찾는가

작업 완료·검증 피드백·목표 변경·다음 점검 시각 도달을 계기로 다시 판단합니다. 대기열이 비어도 활성 목표가 있으면 다음 점검을 예약합니다. 근거가 바뀌지 않았을 때는 저장된 결과와 점검 간격을 사용해 같은 분석을 반복 호출하지 않습니다.

Task의 종류는 계획(`planning`)과 실제 작업(`work`)으로 구분합니다. 계획 Task의 완료는 그 판단과 선택한 작업을 저장하는 것으로 끝나며, 완료 이벤트만으로 또 다른 계획 Task를 만들지 않습니다. 새로운 근거가 없으면 다음 점검 시각까지 기다립니다. 한 Goal에는 대기·실행·복구 확인 중인 계획 Task를 하나만 유지하고, 같은 계기의 이벤트가 반복돼도 추가하지 않습니다. 실제 작업의 검증·재작업은 현재 Task에서 처리하고, 별개의 작업이 필요할 때 총괄에 전달합니다.

유한한 목표는 현재 목표 버전의 완료 기준과 검증 근거를 확인하고, 미완료 실제 작업(`work`)이 없을 때 `completed`로 닫습니다. 완료를 판단한 계획 Task의 성공과 Goal 완료를 같은 DB 트랜잭션에서 확정합니다. 총괄의 완료 제안만으로 닫지 않습니다. 지속 관리 목표는 다음 점검 시각을 남깁니다. 할 일이 없다는 판단도 근거와 함께 저장합니다. 서버를 재시작하면 목표·진행 작업·다음 점검 시각을 복원합니다.

완료 판정을 위한 검증 실행·저장은 내부 모듈로 연결했습니다. 유한 목표의 완료 제안 뒤 같은 자료에서 고정 테스트를 실행하고, 별도 읽기 전용 호출이 전체 목표 기준을 검토합니다.

마지막 개발 작업의 검토만 재사용하지 않습니다. 자료 해시·코드 버전·테스트 설정과 종료 근거·검토 Step을 함께 보존합니다.

검토 호출도 기존 기간 예산과 Run 제한을 사용하며, 저장 실패나 종료 미확정이면 다음 단계로 넘어가지 않습니다. 검증 통과 후 현재 목표·코드·전체 작업 이력을 다시 확인하고 Goal 상태·버전 이력·계획·Run·Task를 같은 트랜잭션에서 완료합니다.

마지막 저장에 실패하면 모두 되돌리며, 재시작 때 남은 검증 근거와 실제 코드를 대조해 한 번만 완료합니다. 성공 표시가 있는 과거 작업도 종료 미확정 실행이나 진행 중 복구가 있으면 완료 근거로 사용하지 않습니다.

유효한 테스트 실패·미완료 검토는 `goal_incomplete`로 기록해 다음 계획에 전달합니다. 이때 성공한 것은 계획 점검이며 Goal은 활성 상태로 남습니다. 다음 점검 시각을 예약하고, 같은 목표 버전에서 중복·억제 작업이나 미완료 제안만 세 번 이어지면 `planning_no_progress`로 보류합니다. 불일치·누락된 근거는 재계획 허가로 쓰지 않습니다. 조회와 화면에는 테스트·검토 결과와 목표 완료 저장 여부를 별도로 표시하고, 명령 설정·서버 경로·컨테이너 인증 표시는 제외합니다.

전체 목표 검토는 같은 계획 입력에 저장된 작업·서비스 관측 이력을 사용합니다. 작업별 변경 반영 상태·기준/결과 커밋·반영 시각과 변경 파일 일부를 함께 전달하므로 작업 순서와 누적 반영을 확인할 수 있습니다. 변경 파일은 현재 목표의 허용 범위 안에서 최대 40개이며, 전체 개수와 구분합니다. 전체 입력은 이스케이프된 JSON 기준 60,000바이트 안에서 선택 자료를 줄이고, 생략 개수를 보존합니다. 기준·권한·실제 테스트 근거 자체가 들어가지 않으면 검토를 진행하지 않습니다. 오래된 기록의 반영 정보 누락이나 생략된 이력을 성공 또는 변경 없음으로 간주하지 않습니다.

### 반복과 취소의 범위

현재 계획 작업의 범위 재검사는 Goal 변경과 같은 트랜잭션에서 수행합니다. 목표 일시정지 동안에는 작업을 그대로 두고, 재개·수정 뒤 활성 목표의 이전 버전 작업만 검사합니다. 당시 목표 이력과 작업의 대상 경로를 현재 허용/제외 경로와 비교하며, 폴더 아래 새 제외 영역과 아직 없는 파일도 판단에 포함합니다. 범위에 맞으면 Task 버전을 갱신하고, 벗어나면 사용자 취소 시각을 만들지 않은 `cancelled`로 기록합니다.

`goalReview`에는 마지막 검사 시각·변경 전후 버전·대상 경로·유지/제외 판정을 저장하고 작업 상세에 표시합니다. 전체 검사 이력 테이블은 두지 않으며 Goal의 버전 이력과 과거 Run의 기준 버전은 유지합니다.

경로 근거가 없거나 종료 미확인 Run·진행 중 복구 요청이 있으면 건너뜁니다. 뒤늦게 종료·복구가 확정된 작업은 다음 대기열·계획 검사에서 다시 확인합니다.

기존 상태·재시도 횟수·오류·누적 시간은 재설정하지 않으며, 사용자 취소·이미 제외한 작업·성공 기록은 다시 열지 않습니다. 범위 제외 전에 실행한 적이 없는 작업은 새 범위에서 다시 계획할 수 있습니다.

이미 실행한 작업은 누적 제한을 새 Task로 초기화하지 않도록 해당 경로의 억제를 유지합니다.

- Goal 상태는 `active`·`paused`·`completed`로 구분합니다. Task 상태와 별도로 관리합니다. 목표 일시정지는 새 계획 호출·작업 생성·배정을 막으며, 이미 실행 중인 Run의 중단은 취소 절차로 요청합니다. 사용자 화면에서 둘을 구분합니다.
- 목표 내용·완료 기준·허용 범위·상태를 바꿀 때 Goal 버전을 올립니다. 계획 결과를 반영하는 트랜잭션에서 현재 버전과 `active` 상태를 다시 확인합니다. 이전 버전의 결과는 이력으로 보존하되 작업 생성이나 목표 완료에 적용하지 않습니다. 진행 중인 작업의 범위를 조용히 바꾸지 않습니다.
- 작업 생성 키와 해결하려는 문제의 식별자를 저장해 중복 생성을 막습니다. 사용자가 취소한 작업은 이름만 바꿔 다시 만들지 않습니다. 사용자가 취소한 문제를 다시 다루려면 명시적인 재개가 필요합니다. 목표 변경으로 범위에서 제외한 작업은 별도의 취소 사유를 기록합니다.
- 같은 Task의 검증 피드백에 따른 수정은 제한된 Step으로 기록하고, 별개의 개선은 원래 Task와 연결된 새 Task로 기록합니다. 반복 실패·시간 초과·인증 차단을 새 Task 생성으로 우회하지 않습니다.
- Task별 제한 외에 Goal·프로젝트별 기간 예산, 계획 호출 수, 재작업 횟수를 제한하고 DB에 보존합니다. 기간 예산 소진은 다음 기간까지 대기하고, 반복 실패는 해당 문제를 보류합니다. 새 작업이나 재시작으로 상한을 초기화하지 않습니다.

목표와 작업의 제어는 다음 기준으로 구분합니다. 목표가 변경됐다는 이유만으로 모든 대기 작업을 취소하지 않습니다.

| 상황 | 대기 작업·계획 | 이미 실행 중인 Run |
| --- | --- | --- |
| Goal 일시정지 | 상태와 기록을 유지하되 새 계획·배정 중지 | 기존 범위에서 마무리 가능. 즉시 중단하려면 별도 취소 요청 |
| Goal 재개·내용 변경 | 기존 계획은 새 버전에 재사용하지 않음. 실제 작업은 현재 범위에 맞으면 버전·재확인 근거 갱신, 맞지 않으면 사유를 남겨 취소 | 기존 기준의 결과로 보존하고, 현재 Goal 달성 여부는 최신 버전에서 다시 검증 |
| 허용 범위 축소 | 새 범위에 맞지 않는 작업 제외 | 해당 Goal의 실행을 중단하고 종료 확인. 중단한 Task는 범위 변경 사유로 취소하고, 새 범위에서 필요한 일은 총괄이 다시 판단 |
| 사용자 Task 취소 | 해당 작업과 같은 문제의 자동 재생성 차단 | 중단·완료 경합은 [취소 규칙](execution.md#완료와-취소가-겹치는-경우) 적용 |

오래된 계획 Task는 실행이 끝났거나 실행 전인 경우 범위 변경 사유로 취소해 새 계획을 막지 않게 합니다. 이미 성공한 계획 기록은 유지합니다. 사용자가 계획 Task 자체를 취소하면 해당 Goal도 일시정지해 다음 점검에서 같은 계획이 다시 생기지 않게 합니다. Goal 재개는 명시적인 새 계획 허용으로 기록합니다. 사용자가 취소한 실제 작업을 다시 허용할 때는 원래 `cancelled` 기록을 유지하고, 취소 억제 해제와 연결된 새 Task를 기록합니다.

기간 예산은 프로그램이 관리하는 호출 수·실행 시간 등의 한도이며 제공자의 구독 잔여량과 구분합니다. 기간 시작·종료 시각과 소비량을 저장하고, 호출 전 남은 예산과 실행 제한을 확인합니다. 기간이 바뀌어도 Task의 누적 시간과 재시도 횟수는 유지합니다. 자동 해제되는 예산 대기는 Goal을 `paused`로 바꾸지 않습니다. 배정 가능한 목표가 있어도 같은 계정의 사용 한도나 종료 미확인 실행을 우회할 수는 없습니다.

### 현재 기간 예산의 집행

프로젝트 기본 정책은 1시간당 60호출·45분 실행이며 수동 분석도 포함합니다. 목표에 연결된 작업은 목표 정책까지 함께 검사합니다. 첫 배정 검사 때 기간과 당시 정책을 저장하고, 현재 기간이 끝난 뒤 다음 검사에서 새 기간을 만듭니다. 현재 기간의 숫자 상한은 고정하므로 목표 수정·정책 변경이 사용량을 초기화하지 않으며, 변경된 숫자는 다음 기간에 적용합니다. 기존 DB 업그레이드 이전 호출의 예산 사용량은 임의로 소급 생성하지 않습니다.

프로젝트·목표 정책의 선택 필드 `unlimited: true`는 해당 범위의 기간 예산 집행을 해제합니다. 생략하거나 false이면 기존 제한을 적용합니다. 다음 배정·호출 검사에서 최신 해제 여부를 읽으므로 기존 대기도 기간 만료 전에 재검사합니다. 숫자 상한과 소비 기록은 그대로 보존하며, 다시 제한을 켜면 그 기록으로 검사합니다. 양쪽 범위가 모두 무제한이면 기간 종료로 Run을 자르지 않고, 실행·Task 시간 및 반복 실패 제한과 제공자 사용 한도는 유지합니다. 이미 배정한 Run의 타이머는 변경하지 않습니다.

첫 호출의 예약·Run·Step 생성, 다음 호출의 예약·Step 생성은 각각 같은 트랜잭션입니다. 저장 실패 시 호출 허가도 취소합니다. 준비 실패나 실행 여부 불확실에는 호출 횟수를 환불하지 않습니다. 시간은 Run에 필요한 상한만 먼저 예약하고, 실제 종료가 확인됐을 때 경과 시간으로 바꿉니다. 같은 종료를 다시 대조해도 이중 정산하지 않습니다. 종료 확인 지연·중단 처리로 초과한 시간은 숨기지 않고 합산합니다. 시계가 뒤로 이동해 시간을 산정할 수 없으면 예약량을 유지합니다.

실행 제한은 Run·Task의 남은 시간, 프로젝트·목표의 남은 시간, 양쪽 기간 종료 중 가장 이른 조건을 따릅니다. 기간 예산 때문에 중단하면 `budget_limit` 사유를 저장하며, 종료 확인 전에는 새 실행을 막습니다. 종료 확인 후에는 `waiting_capacity`와 `budgetWait`으로 대기합니다. `automaticRecovery` 설정 없이도 확인된 예산 대기는 자동 대기열에서 기간이 지난 뒤 재검사합니다. 예산이 없는 후보는 건너뛰고 다른 실행 가능한 프로젝트·목표를 처리합니다.

다음 Step 예산이 없으면 이전 보고는 보존하되 자식 실행에 다음 호출 허가를 보내지 않습니다. 재개하는 Run에는 직전 성공 Step의 제한된 발췌를 신뢰하지 않는 참고 자료로 전달하며, 현재 파일과 다시 확인하도록 지시합니다. 개발 작업은 아래의 작업 공간·후보 버전·변경 반영 기록을 대조해 이어갑니다. 이전 분석 보고서만으로 코드가 반영됐다고 판단하지 않습니다. 프로젝트 설정과 최근 기간의 사용·예약량은 API와 실행 예산 화면에서, 개별 작업의 대기 범위·사유·시각은 작업 상세에서 확인합니다.

### 변경을 축적하고 검증하는 방법

여기서 브랜치는 코드 변경 이력을 나눠 관리하는 단위이고, 커밋은 특정 시점의 코드 상태와 변경을 Git에 기록하는 것입니다. 기준 커밋은 수정의 출발점, 결과 커밋은 수정을 반영한 결과를 가리킵니다. 로컬 커밋은 해당 컴퓨터에 기록하는 것이며 원격 저장소로 보내는 푸시와 구분합니다.

프로젝트의 운영 디렉터리와 분리된 개발 브랜치·작업 공간을 사용합니다. 개발은 기록된 기준 커밋에서 시작하며, 검증은 변경된 코드 버전에 대해 수행합니다. 테스트 실행과 검토를 통과한 변경을 개발 브랜치에 로컬 커밋으로 남기고 다음 작업의 기준으로 사용합니다. 이 내부 흐름에는 매번 사용자 승인을 요구하지 않습니다.

서버가 소유한 비공개 Git 저장소에는 원본의 시작 커밋과 그 시점의 파일 상태를 가져옵니다. 원본 브랜치와 작업 폴더는 수정하지 않습니다. AI에 제공하는 별도 폴더에는 현재 Goal에서 읽도록 허용한 파일만 복사하며, 수정은 해당 Task에 지정한 경로로 더 좁힙니다. 서버는 기준 커밋·입력 식별값·수정할 파일의 바이트를 검사해 검증 대상을 만듭니다. AI가 쓰는 폴더의 Git 설정이나 훅을 서버에서 실행하지 않습니다. 원본의 미커밋 변경·HEAD 변경 또는 기록되지 않은 개발 브랜치 변경을 발견하면 보류합니다.

개발 컨테이너는 읽기 전용 입력을 크기가 제한된 임시 파일 공간에 복사해 수정합니다. 완료 시 파일 바이트·실행 권한·삭제 목록을 수집하며, 컨테이너 종료를 확인한 뒤 서버가 후보 버전을 구성하고 DB에 저장합니다. 원본·서버의 Git 객체·인증 파일은 수정 결과의 입력으로 삼지 않습니다. 실행 중 임시 공간의 내용은 서버나 컨테이너가 갑자기 종료되면 잃을 수 있으며, DB에 저장한 후보만 재작업의 출발점으로 사용합니다.

현재 고정한 Codex CLI의 쓰기 경로에는 디렉터리를 전달해야 하므로 파일을 지정한 Task에는 해당 파일을 포함하는 기존 상위 디렉터리를 허용합니다. 이 임시 복사본에서 주변 파일이 바뀌더라도 수집 시 원래 Task 경로와 Goal 범위를 다시 검사해 전체 변경을 거부합니다. 서버의 후보 트리 검사에서도 같은 범위를 적용합니다.

준비 전에 DB에 저장소·입력 생성 의도를 기록하고 저장 응답을 받은 뒤 파일을 만듭니다. 준비 완료 파일을 게시한 후 DB의 준비 상태를 확정합니다. 그 사이 중단됐으면 완료 파일의 식별자·Git 기준·실제 바이트를 대조해 이어받습니다. 준비 완료 근거가 없는 부분 생성 폴더는 덮어쓰지 않고 보류합니다. Git·파일 작업은 DB 트랜잭션 밖에서 수행합니다.

재작업은 같은 Task의 직전 후보에서 시작하며, 이전 Run의 후보를 이어받으려면 그 Run의 종료가 확인되어야 합니다. 한 Run에서 입력은 최대 3회 준비하며 기존 Task 재시도·시간·예산 제한도 유지합니다. 계획 당시 기준과 실제 개발 기준은 별도로 저장합니다. 후보의 변경 목록은 재작업 중 마지막 수정분만이 아니라 승인된 개발 기준부터의 전체 차이입니다. 입력 폴더는 Run 종료 확인 후 정리하되 Git 객체와 DB 기록은 보존합니다.

준비·수정·변경 검사·실제 테스트·독립 검토·변경 반영을 실행기로 연결했습니다. 대기열은 작업 폴더·개발 이미지·고정 테스트 설정과 종료 확인 기능이 있는 개발 작업만 배정합니다. 후보 버전만으로는 개발 브랜치나 Task 성공 상태를 바꾸지 않습니다. 검증과 반영 근거 없는 성공 완료 요청은 `development_incomplete`로 보류합니다.

실제 테스트 실행기 역시 내부 모듈로 구현했습니다. 운영자가 정한 이미지·명령 배열·제한 시간을 사용하고, 인증 폴더·Docker 소켓·외부 통신 없이 실행합니다.

입력 바이트·권한을 확인한 뒤 임시 공간에서 테스트하며, 표준 출력은 상태 변경 명령으로 읽지 않습니다. 부모 서버가 실행 식별자를 대조해 읽은 종료 코드가 0이고 강제 중단·메모리 종료가 없을 때만 테스트 통과로 판단합니다.

테스트 한도에 따른 중단은 실패 근거로 반환할 수 있지만, Run 취소·전체 종료 미확인·종료 기록 저장 실패에는 결과를 완료 근거로 반환하지 않습니다. 테스트 결과는 정확한 후보·검증 입력·고정 설정·실행 식별자와 연결해 DB에 저장합니다.

별도 검토 기록은 그 테스트 결과와 완료된 AI 호출 단계에 연결하며, 테스트가 실패했다면 AI가 승인해도 완료 근거로 받지 않습니다. 다음 수정은 검토의 미완료 사유와 후속 제안이 있을 때만 허용합니다.

부모 서버가 실제 AI 호출을 이 순서로 연결하고, 각 호출 전에 Step과 예산을 저장합니다.

Run 조회의 `developmentEvidence`와 작업 상세 화면은 저장된 개발 회차·상대 경로의 변경 파일·실제 테스트 결과·독립 검토를 표시합니다. 준비·개발·테스트·검토 단계를 구분하고, 종료한 Run에는 마지막 단계로 표시합니다. 입력 폴더·전체 파일 목록·테스트 명령·컨테이너 인증 식별자는 응답에 넣지 않으며, 출력과 검토 의견의 인증 토큰 형태는 가립니다. 검증을 통과해도 변경 반영 기록이 없으면 작업 완료로 표시하지 않습니다. 이전 실패 회차는 이후 통과 회차와 함께 남깁니다.

검증 입력은 개발 입력과 별도로 생성한 후보 버전입니다. 생성 의도 저장 후 파일을 준비하고, 준비 완료 응답을 받은 뒤 테스트를 시작합니다. 테스트와 검토의 종료 근거 및 결과 저장을 확인하기 전에는 다음 단계로 넘어가지 않습니다. 이미 저장한 결과는 덮어쓰지 않으며, 재시작 시 저장된 설정과 다른 명령으로 검증을 이어가지 않습니다. 긴 테스트 출력은 시작 부분과 마지막 오류를 보존하고 인증 문자열을 제거합니다. 개발·검증 입력은 Run의 최종 종료 확인 뒤 함께 정리하고 Git 후보와 DB 기록은 보존합니다.

한 Run의 개발 흐름은 최대 3회 수정, AI 호출 6회(개발·검토 각 3회), 컨테이너 9회(실제 테스트 포함)로 제한합니다. 테스트는 AI 호출 예산을 쓰지 않지만 Run·Task의 시간 예산에는 포함됩니다. 최초 effort는 기존 선택 규칙을 쓰고, 이후 제안은 저장된 정책의 상한과 최대 2회 변경 제한을 적용합니다. 테스트 실패를 다음 개발에 전달하며, 검토가 진행에 필요한 정보 부족으로 후속 수정을 제안하지 못하면 보류합니다. 재작업으로 Task·재시도·기간 예산을 새로 만들지 않습니다.

개발과 검토는 서로 다른 SDK 세션입니다. 검토에는 읽기 전용 후보 파일과 부모가 기록한 실제 테스트 결과를 전달합니다. 개발자의 완료 보고만으로 검증을 건너뛰지 않으며, 검토자의 승인도 실제 테스트 실패를 덮어쓰지 못합니다.

새 개발 흐름은 파일 준비 전에 실행 방식 버전(`developmentVersion: 1`)을 저장합니다. 이 방식에서는 컨테이너 식별자 저장 응답 전 실행을 시작할 수 없으므로, 재시작 후 실행 기록이 비어 있으면 작업 코드가 시작되지 않았음을 확인할 수 있습니다. 이 보장이 없는 예전 실행은 식별자가 없다는 이유만으로 종료됐다고 간주하지 않습니다. 준비 중 취소도 진행 중인 준비·저장 응답이 끝날 때까지 확인한 뒤 정리합니다.

Git 변경과 SQLite 기록은 하나의 트랜잭션으로 함께 확정할 수 없습니다. 먼저 DB에 반영 작업 ID·기준 커밋·검증한 파일 내용의 식별값과 반영 예정 상태를 남깁니다. 이후 Git 작업을 수행하고, 결과 커밋·브랜치와 검증 대상의 일치를 확인한 뒤 DB에서 반영 완료와 Task 성공을 확정합니다. 테스트와 Git 작업을 기다리는 동안 DB 트랜잭션을 유지하지 않습니다.

이때 사용하는 DB 기록을 **변경 반영 기록(`ChangeApplication`)**이라고 부릅니다. 예를 들어 커밋 직후 서버가 꺼졌을 때 “코드는 반영됐는데 완료 기록만 빠진 것인지” 확인하기 위한 기록이며, 별도 프로그램을 뜻하지 않습니다.

내부 반영 모듈은 이 기록을 구현했습니다. 부모·트리·작성 시각·반영 ID로 커밋 내용을 고정하고 예정 커밋 식별값을 DB에 먼저 저장합니다.

반영 예약 전에 저장된 취소·목표 변경은 반영을 막습니다. 예약 이후 중단된 반영은 이미 허용된 같은 커밋을 대조하며, 원본이나 예상 밖 브랜치 변경이 있으면 보류합니다.

Git 반영 완료 후 개발 기준과 반영 상태를 같은 DB 트랜잭션에서 갱신합니다. Git 반영 모듈 자체는 Task 상태를 바꾸지 않습니다.

일반 완료와 복구 처리기가 동일한 반영·검증·종료 근거를 확인한 뒤 Task를 완료합니다. 서버 중단으로 마지막 완료 기록만 빠졌으면 AI를 다시 호출하지 않고 저장된 검토 결과를 사용합니다.

취소·허용 범위 축소·시간 초과·예산 중단은 각각의 상태를 유지하며, 이미 반영한 코드는 자동으로 되돌리지 않습니다.

미확정 반영이 남으면 해당 프로젝트의 새 배정을 막습니다. 자동 복구는 종료 확인 후 같은 반영 기록을 한 번 대조하고, 실패하면 원인 해결과 수동 상태 확인을 기다립니다. 복구 도중 서버가 종료되면 요청을 대기 상태로 남겨 다음 소유자가 이어받습니다. 반영 기록이 있는 Task는 새 AI 실행으로 재개할 수 없습니다. 작업 상세는 반영 대기·완료, 기준·예정 또는 결과 커밋, 확인 시각을 표시합니다.

커밋 후 DB 저장 전에 중단됐다면 반영 작업 ID와 실제 Git 상태를 대조해 기존 결과를 연결합니다. 확인 없이 다시 커밋하거나 성공으로 표시하지 않습니다. 반영 여부가 불명확한 동안 같은 프로젝트의 후속 변경은 막고 복구합니다. 외부 프로세스가 기준 브랜치를 바꿨다면 덮어쓰지 않고 현재 기준에서 변경·검증을 다시 확인합니다.

실패한 변경은 작업별로 보존하고 검증된 기준에 섞지 않습니다. 재시작 시 기준 커밋·변경·검증 기록을 대조하며, 실제 파일 상태를 확인하기 전에 작업을 다시 실행하지 않습니다. 검증 이후 코드가 바뀌면 재검증합니다. 외부 푸시·기본 브랜치 병합·운영 배포는 별도 정책으로 두며, 이를 기다리는 동안에도 독립적인 개발 작업은 계속할 수 있습니다.

SDK 호출 종료는 Step의 실행 결과입니다. 코드 변경 Task는 필요한 검증과 개발 브랜치 반영 기록까지 확인한 뒤에만 성공합니다. 검증에서 발견한 결함은 Task가 실행 중인 동안 제한된 재작업 Step으로 처리합니다. 그 한도를 소진하면 `blocked`로 보류하고, Run 시간 초과·재시도 불가능한 실행 오류는 기존 규칙대로 `failed`로 처리합니다. 실패한 검증 결과를 그대로 성공으로 바꾸거나 새 Task로 재작업 한도를 초기화하지 않습니다.

개선은 목표에 등록한 테스트·사용자 시나리오·측정 기준으로 판단합니다. 개발·검증 에이전트의 의견 일치만으로 성공 처리하거나 통과를 위해 기준을 낮추지 않습니다. 자동 생성 작업도 기존 상태 전이·취소·복구 규칙을 그대로 따릅니다.
