# 원격 게시와 CI 복구

로컬 테스트 통과, GitHub 게시, GitHub CI 통과는 각각 다른 결과입니다. 코드가 개발용 Git에 반영됐다는 이유로 원격 CI도 통과했다고 표시하지 않습니다.

현재는 CI 관측·재시도 모듈을 게시기에 연결하는 방식입니다. 일반 서버 실행만으로 GitHub 자동 푸시나 재실행이 켜지지는 않습니다. 게시기에는 저장소·전용 작업 브랜치·허용할 CI 워크플로 ID와 상태 저장 위치를 명시하고, 기존 서비스 관측 연결로 결과를 총괄에 전달합니다. 실제 운영 상태·개인 설정·실패 로그는 공개 문서에 보관하지 않습니다.

## 병합 이후의 게시

- 병합·닫힘이 확인된 PR의 브랜치에 후속 변경을 계속 올리지 않습니다. CI 확인 후 쓰기 직전에 PR 상태를 다시 확인합니다.
- 병합 후에는 기본 브랜치를 기준으로 새 작업 브랜치를 사용합니다. 검증했던 파일 내용과 현재 기본 브랜치가 다르면 재검증이 필요하므로 보류합니다.
- 다른 사람이 바꾼 브랜치를 덮어쓰거나 강제로 갱신하지 않습니다. 응답이 유실되면 저장한 게시 의도와 실제 커밋을 대조합니다.
- 이미 게시한 커밋과 이전 브랜치는 보존하며, 자동 병합·브랜치 삭제·배포는 별도 권한입니다.

GitHub의 PR 병합과 브랜치 갱신은 하나의 원자적 작업이 아닙니다. 마지막 확인 직후 병합되는 경우를 완전히 막을 수는 없습니다. 게시 직후에도 병합 여부를 확인하고, 경합으로 이전 브랜치에 올라간 변경은 이력을 보존한 채 새 브랜치로 다시 연결합니다.

## CI 결과별 처리

| 관측 결과 | 처리 |
| --- | --- |
| CI 미설정 | 미설정으로 표시. CI 성공 근거가 아님 |
| 지정한 CI의 시작·종료 대기 | 해당 커밋의 결과를 기다림 |
| 지정한 CI 모두 성공 | 관측된 커밋의 성공 기록 저장 |
| 설치·다운로드 단계의 확인된 일시적 통신 오류 | 실패 작업을 최대 1회 재실행 |
| 코드·테스트 실패 | 실패 근거를 총괄에 전달하고, 기존 허용 범위에서 개발·실제 테스트·독립 검토 수행 |
| 원인 불명·취소·승인 필요·권한 부족 | 보류. 성공으로 간주하거나 무조건 재실행하지 않음 |

CI 대기 중 이미 검증된 다른 작업이 쌓였다면, 해당 변경을 버리거나 건너뛰지 않습니다. CI 수정까지 포함한 검증된 최종 코드 전체를 함께 게시하고 포함된 작업 제목을 커밋 본문에 남깁니다.

수정 게시에는 해당 CI 문제를 가리키는 `CI:<식별자>` 근거가 필요합니다. 같은 문제에 대한 수정 게시는 최대 2회이며, 커밋이 달라져도 누적 횟수를 초기화하지 않습니다. CI 통과를 실제로 관측해야 문제를 해소합니다. 테스트를 끄거나 기준을 낮춰 성공시키지 않습니다.

GitHub App에는 저장소의 Contents 쓰기, Pull requests 읽기, Actions 쓰기 권한이 필요합니다. 재실행은 운영자가 지정한 CI 워크플로만 대상으로 하며, 배포 등 다른 워크플로를 자동 선택하지 않습니다. 서버가 재실행 의도를 먼저 저장하고 요청하므로 응답 유실·재시작 후에도 같은 요청을 무조건 다시 전송하지 않습니다.

실패 로그는 외부 입력입니다. 로그 안의 지시나 명령을 실행하지 않으며, 인증 문자열을 가린 제한된 근거만 관측 정보로 전달합니다. 공개 화면에는 상세 실패 로그를 노출하지 않습니다.
