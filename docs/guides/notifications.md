# 조치가 필요한 문제를 알림으로 받기

인증 만료나 복구 한도 초과를 발견하면, 운영자가 지정한 수신 주소에 JSON을 보냅니다. 알림은 선택 기능이며 설정하지 않으면 전송하지 않습니다. 작업 실행·서비스 관측과 별도로 동작합니다.

## 설정하기

본인이 관리하는 수신기를 준비하고 다음 파일을 비공개 경로에 `0600` 권한으로 저장합니다. 예시 주소는 실제 수신 주소로 바꿉니다.

```json
{
  "version": 1,
  "url": "https://receiver.example.com/agent-hub"
}
```

`NOTIFICATION_CONFIG=/etc/agent-hub/notifications.json`을 서버 환경 파일에 추가하고 서버를 재시작합니다. 상대 경로는 저장소 루트 기준입니다. 필요하면 `bearerToken` 문자열을 추가합니다. 이 값은 `Authorization: Bearer …` 헤더에만 사용합니다. URL·인증값을 저장소에 커밋하지 않습니다.

원격 주소는 HTTPS가 필요하며, HTTP는 로컬 수신기에서만 허용합니다. URL의 사용자명·비밀번호·fragment와 리다이렉트는 허용하지 않습니다. 특정 메신저의 전용 형식을 보내는 기능은 아니므로 Slack·Telegram 등에 연결하려면 아래 JSON을 처리하는 수신기가 필요합니다.

## 언제 알려주나

| 상태 | 알림 |
| --- | --- |
| 계정 인증 실패·지원하지 않는 실행 설정 | 계정 단위 알림 한 건 |
| 자동 복구의 재시도·반복 오류·누적 시간 한도 초과 | 해당 작업의 조치 요청 |
| 사용 한도 재확인 횟수 소진·재확인할 작업 사용 불가 | 계정 단위 복구 점검 요청 |
| 중단된 실행의 실제 종료를 확인하지 못함 | 종료 확인 요청 |
| 재시작 뒤 남은 실행 때문에 큐가 보류됨 | 자동 복구 설정 여부와 관계없이 복구 점검 요청 |
| 종료한 실행의 Git 반영 기록이 미확정 | 취소·예산 대기와 별개로 반영 점검 요청 |
| 실패·보류한 작업, 실행 큐의 설정·저장 오류 | 조치 요청. 원본 오류 문자열은 제외 |
| 정상 실행·할 일 없음·기간 예산·일반 사용 한도·예약된 재시도 대기 | 알림 없음 |

새 문제를 발견한 뒤 기본 30초 동안 기다리고, 전송 직전에 상태를 다시 확인합니다. 그동안 복구되거나 취소·예산 대기 등으로 바뀌면 전송을 취소합니다. 단, 실행 종료나 Git 반영이 불명확하면 취소·예산 대기 여부와 관계없이 알립니다. 같은 계정 문제로 여러 작업이 멈춰도 작업별로 같은 알림을 반복하지 않습니다.

## 수신기가 처리할 내용

POST 본문은 `version`, `id`, `type: "action_required"`, `reason`, `projectId`, `taskId`, `runId`, `detectedAt`입니다. 해당하지 않는 식별자는 `null`입니다. 프로젝트 이름·지시문·AI 응답·로그·경로는 보내지 않습니다. `reason`의 가능한 값은 [알림 형식](../../apps/server/src/modules/operations/notification-delivery.ts)에 정의합니다.

수신기는 알림을 저장한 뒤 **2xx 응답**을 반환해야 합니다. 응답 본문은 사용하지 않습니다. 응답 유실·프로세스 중단 뒤에는 같은 내용이 다시 도착할 수 있으므로, `Idempotency-Key` 헤더와 본문의 동일한 `id`로 중복을 걸러냅니다. 재시도에 상한이 있으므로 전달 자체가 보장되는 것은 아닙니다.

같은 문제가 지속되면 성공 뒤 다시 보내지 않습니다. 문제 해결을 관측한 뒤 재발하거나 다른 실행에서 새 문제가 생기면 새 `id`를 만듭니다. 수신 주소·인증값을 교체하면 계속 남아 있는 문제를 새 수신 설정으로 다시 알립니다. 이전 수신처의 대기 건을 그대로 전달하지 않습니다.

## 전송 실패와 기록 확인

로그인한 상태에서 `GET /operations/notifications`를 조회하면 알림 처리기의 상태와 최근 갱신된 기록 최대 50건을 확인할 수 있습니다. 각 문제 출처의 **마지막 알림 기록**을 보존하며 전체 과거 전송 이력은 아닙니다. 설정하지 않은 서버도 기존 기록은 조회할 수 있습니다. 외부 상태 점검용 인증값으로는 접근할 수 없습니다.

- `pending`: 전송 대기 또는 응답 확인 중입니다. `attempts`는 전송 전에 저장한 시도 횟수입니다.
- `delivered`: 수신기가 2xx로 응답했습니다. 사용자가 읽었다는 뜻은 아닙니다.
- `exhausted`: 시도 상한에 도달했습니다. 수신처를 확인해야 하며 단순 재시작으로 한도를 초기화하지 않습니다.
- `resolved`: 전송 대상 문제가 해소되거나 다른 상태로 바뀌었습니다. 별도의 복구 메시지는 보내지 않습니다.

선택 설정의 단위는 밀리초입니다.

| 설정 | 기본값 | 허용 범위 |
| --- | --- | --- |
| `pollIntervalMs` | 5,000 | 1,000~60,000 |
| `timeoutMs` | 3,000 | 100~10,000 |
| `graceMs` | 30,000 | 1,000~300,000 |
| `initialDelayMs` | 10,000 | 1,000~3,600,000 |
| `maxDelayMs` | 300,000 | 초기 간격 이상, 최대 86,400,000 |
| `maxAttempts` | 5 | 1~20 |

시도 시작부터 다음 시도까지의 간격을 두 배씩 늘려 상한까지 적용합니다. 한 번에 한 건을 전송하고 작업 상태와 기록을 제한된 페이지로 순회하므로, 대기 건이 많으면 전송이 늦어질 수 있습니다. 기록 저장 자체가 실패하면 `worker.storageError`와 고정 로그 코드로 알립니다. DB가 고장 난 상황에서 DB 기반 알림 전달을 보장하지 않습니다.

**서버 자체가 꺼지면 내부 알림도 멈춥니다.** [외부 점검 명령](../04-operations.md#외부에서-서버-상태-점검하기)을 다른 호스트에서 실행하고 종료 코드에 따른 알림을 그 호스트의 감시 도구에 연결해야 합니다. 실제 수신처 연결·원격 설치는 별도 운영 작업입니다.
