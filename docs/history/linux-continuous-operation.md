# Linux에서 실제 Codex로 진행한 1시간 시험

**목표 하나를 맡긴 뒤 입력 변화에 따라 두 작업을 개발·검증·반영하고, 할 일이 없을 때 기다리는 흐름을 확인했습니다.** 서버 프로세스 재시작과 관측 서비스 장애도 포함했습니다. 실제 원격 서버의 24시간 운영은 아직 검증하지 않았습니다.

## 어떻게 시험했나

API로 프로젝트와 지속 관리 목표만 등록했습니다. 첫 요구는 문자열을 URL용 이름으로 바꾸는 함수, 두 번째는 그 함수를 재사용해 이름별 개수를 세는 함수입니다. 두 요구는 처음부터 목표에 포함했고, 시험용 서비스의 관측 값을 바꿔 차례로 활성화했습니다. 이후 새 사용자 지시나 DB에 직접 넣은 작업은 없습니다.

| 조건 | 내용 |
| --- | --- |
| 시각·코드 | 2026-11-07 23:41~11-08 00:42 KST, `58af9f9` |
| 환경 | 로컬 Docker의 Linux arm64 VM, Node 24.22.1, VM RAM 약 7.65GiB |
| 실제 AI | Codex `gpt-6.1-sol`, `medium` |
| 실행 방식 | 별도 Linux 프로세스에서 빌드된 서버 실행, 5분마다 다음 작업 점검 |
| 상한 | AI 실행 컨테이너·SDK 호출 20회, 단계당 6분, 시험 75분·별도 감시 프로그램 80분 |
| 시간 | 관찰 60분 1.302초, 최종 정리·측정까지 60분 17.522초 |

20회는 실행 횟수 제한입니다. SDK 내부의 모델 턴·토큰·금액을 같은 수로 제한한다는 뜻은 아닙니다. 서버와 관측 프로그램을 담은 컨테이너의 설정 상한은 768MiB이며 전체 운영 서버의 권장 RAM이 아닙니다.

## 실제로 일어난 일

| 시작 후 | 결과 |
| --- | --- |
| 0~5분 | 활성화된 요구가 없어 개발 작업 없이 대기 |
| 5분~6분 39초 | 첫 입력을 읽고 첫 작업 개발·검증·반영 |
| 12분 15~21초 | 서버 프로세스를 종료·재시작. 작업·실행 이력, 예산, 다음 점검 시각 유지 |
| 12분 21초~17분 32초 | 관측 서비스에 HTTP 503 주입. 새 개발 작업 없이 대기하고 복구 후 새 관측 수신 |
| 35분~39분 57초 | 두 번째 입력을 읽고 첫 변경을 사용하는 후속 작업 반영 |
| 이후~60분 | 추가 개발 작업 없이 대기. 지속 관리 목표는 활성 상태 유지 |

최종 기록은 **계획 13건·개발 작업 2건·Run 15건·AI 단계 17건·Git 반영 2건**입니다. 모든 AI 단계에 고정 gstack 지침을 읽은 기록이 있으며, 실제 테스트 2회와 별도의 12개 검산도 통과했습니다.

두 번째 반영의 기준 커밋과 작업 입력이 첫 번째 반영 커밋과 일치했습니다. AI 실행 17개와 고정 테스트 2개, 총 **19개 컨테이너 실행의 신원·종료 기록**을 단계 수와 대조했습니다. 관측은 719건이며 의도한 장애 구간의 실패 62건을 포함합니다. 요청은 GET만 사용했습니다.

서버를 멈춘 뒤 DB 무결성과 기록을 읽었습니다. 실행 중에는 관측용 SQLite 연결을 추가하지 않았습니다. 프로젝트 원본은 유지됐고, 소유한 작업·검산 컨테이너와 임시 인증 사본은 정리됐습니다. 실패나 강제 정리가 필요한 실행은 없었습니다.

## 자원 사용

약 2초 간격으로 표본 1,785개를 수집했습니다. 간격 중앙값은 2.026초, 최대는 2.057초입니다. 아래는 **표본에서 본 최대값**이며 순간 최고 사용량은 놓칠 수 있습니다. 포함 관계가 있으므로 행들을 합산하지 않습니다.

| 측정 범위 | 최대 메모리 |
| --- | --- |
| Node 서버 프로세스의 실제 메모리(RSS) | 178.4MiB |
| 서버·관측 프로그램·자식 명령을 합친 묶음 | 188.1MiB |
| 작업 컨테이너 한 개의 원시 사용량 | 453.6MiB |
| Docker·서버·작업을 포함한 Linux VM 전체 사용량 추정 | 1,000.1MiB |

VM 값은 `MemTotal − MemAvailable`입니다. 서버·관측 프로그램 묶음의 누적 CPU 시간은 약 68.45초였습니다. 종료 후 서버 RSS가 없는 표본 8개는 0으로 계산하지 않았습니다.

첫 입력 전 2분과 종료 전 2분의 대기 표본을 비교하면 서버 RSS 중앙값은 **125.6 → 154.0MiB**, VM 전체는 **661.1 → 692.8MiB**였습니다. 사이에 서버 재시작과 작업 수행이 있었으므로 같은 프로세스의 장기 추이로 해석하지 않습니다. 이 결과만으로 메모리 누수 여부를 판단할 수 없습니다.

종료 후 파일의 논리적 크기는 DB 1,044KiB, 개발 Git 약 5.37KiB, 서버 로그 약 951.5KiB였습니다. WAL은 최대 약 3.96MiB이고 종료 후 0바이트 파일로 남았습니다. 준비 입력은 최대 약 8.52KiB, 종료 후 0바이트였습니다. Docker 이미지·가상 디스크 전체 크기는 포함하지 않습니다.

## 확인 범위와 남은 검증

이번 결과는 미리 정한 작은 요구와 시험용 관측 서비스에 대한 한 시간의 기록입니다. 실제 프로젝트의 문제 발견·개선 품질, 큰 빌드·테스트 부하, 장기간 파일 증가, **원격 24시간 운영과 2GiB 서버 적합성**은 별도로 확인해야 합니다. 실제 트레이딩 서비스는 연결하거나 변경하지 않았습니다.

대기 중 정상 종료·재시작을 검사했습니다. 실행 중 강제 종료와 systemd 복구는 [별도 Linux CI 검사](../04-operations.md#ci의-실제-서비스-재시작-검사)의 근거를 따릅니다. 이 Linux 성공으로 과거 macOS SQLite `SIGBUS`의 원인이 해결됐다고 판단하지 않습니다.
