# 자원 사용 기록

**작은 예제에서 실행·종료 후 정리까지 확인했습니다. 이 결과로 2GiB 서버의 충분 여부를 판단할 수는 없습니다.**

현재 남은 검증은 [진행 상태](../02-implementation-plan.md), 원래 측정 조건은 [운영 계획](../plans/operations.md#performance-review)을 따릅니다.

후속 [Linux 1시간 시험](linux-continuous-operation.md)에서는 실제 Codex와 서버를 같은 Linux VM에서 실행하고, 재시작·관측 장애와 함께 자원을 측정했습니다. 아래는 그 전에 수행한 서로 다른 조건의 기록입니다.

## 2026-11-07: 실제 Codex로 두 작업 연속 실행

측정 대상은 `04c42b1`입니다. 기존 F3 예제를 재사용해 문자열을 정리하는 함수와 그 함수를 사용하는 집계 함수를 순서대로 만들었습니다. 프로젝트·목표만 API로 등록했고, 작업과 실행 결과를 미리 DB에 넣지 않았습니다.

| 조건 | 내용 |
| --- | --- |
| 환경 | macOS arm64, 호스트 RAM 24GiB, Node 24.22.1 |
| Docker | Engine 28.0.4, Linux VM에서 보고한 RAM 약 7.65GiB·CPU 10개 |
| AI | 실제 Codex, `gpt-6.1-sol`, `medium` |
| 상한 | 작업 관측 15분, 목표의 AI 호출 최대 20회 |
| 관측 | 총 307.6초, 150개 표본. 간격 중앙값 2.03초·최대 2.09초 |
| 비교 구간 | 실행 전 15초, 완료 후 재시작·대기 30초, 임시 폴더 정리 후 15초 |

계획 3건·개발 작업 2건·AI 호출 단계 8건으로 목표를 완료했습니다. 두 번째 작업이 첫 번째 반영 커밋을 사용했고, 실제 테스트·독립 검토·별도 12개 검산을 통과했습니다. 원본은 바뀌지 않았으며 완료 후 재시작해도 작업이 늘지 않았습니다.

### 메모리와 CPU

단위는 MiB입니다. **서로 포함 관계가 있는 값이므로 아래 행들을 더하면 안 됩니다.** 최대값은 표본에서 본 값이며 순간 최고 사용량을 보장하지 않습니다.

| 측정 대상 | 실행 전 | 실행 중 최대 | 완료·재시작 후 |
| --- | --- | --- | --- |
| Node 부모 프로세스의 실제 메모리(RSS) | 중앙값 271.5 | 314.5 | 중앙값 320.5 |
| 작업 컨테이너 한 개 | 없음 | 원시 사용량 462.4 / 비활성 파일 캐시 제외 453.8 | 남은 작업 컨테이너 0개 |
| Docker Linux VM 전체의 사용량 추정 | 중앙값 513.5 | 858.6 | 중앙값 529.2 |

부모 프로세스에는 서버·검증 코드·추가 SQLite 연결·측정 루프가 함께 들어 있습니다. 독립 운영 서버만의 메모리 사용량으로 해석하지 않습니다.

VM 값은 `/proc/meminfo`의 `MemTotal − MemAvailable`입니다. Docker 데몬·작업 컨테이너·측정용 컨테이너를 포함하고, macOS에서 실행한 Node 부모는 포함하지 않습니다. 측정용 컨테이너 자체의 원시 메모리 최대값은 55.6MiB였습니다.

컨테이너 캐시를 제외하는 계산은 [Docker의 통계 API 정의](https://docs.docker.com/reference/api/engine/version/v1.44/)를 따랐습니다. CPU는 코어 한 개를 100%로 볼 때 실행 중 구간 표본 최대값이 부모 8.8%, 작업 컨테이너 8.7%였습니다. 짧게 실행된 테스트나 순간 CPU 사용량은 약 2초 간격의 표본에서 빠질 수 있습니다.

부모 메모리는 대기 중에도 초기 수준으로 돌아오지 않았습니다. 이 한 번의 실행만으로 정상적인 메모리 보존인지 누수인지 판단하지 않습니다.

### 상태 파일과 정리

파일 내용은 열지 않고 크기를 측정했습니다. 실행 중 DB를 외부 도구로 반복 조회하지 않았습니다.

| 대상 | 관측 결과 |
| --- | --- |
| SQLite 본체 | 모든 DB 연결을 닫은 뒤 524KiB |
| WAL — DB에 합쳐지기 전 변경 기록 | 최대 약 3.96MiB, 모든 연결을 닫은 뒤 파일 없음 |
| 개발 상태 폴더 | 종료 후 약 5.8KiB 보존 |
| 작업에 전달하는 준비 입력 | 최대 약 10.3KiB, 완료 후 0바이트 |
| 검증 도구의 출력 | 진행 로그 약 2.4KiB, 별도 AI 결과 기록 약 88.3KiB |

위 값은 파일의 논리적 크기입니다. Docker 이미지·가상 디스크·운영 journald 로그의 총 사용량은 이 표에 포함하지 않습니다. 상태 보존을 먼저 확인한 뒤 **이 검증에서 만든 임시 폴더만** 삭제했습니다. 작업·측정용 컨테이너도 모두 제거됐고, 측정 오류와 다른 실행 컨테이너의 간섭은 없었습니다.

### 아직 확인하지 못한 것

Linux 운영 서버 전체의 사용량, 큰 프로젝트의 빌드·테스트, 장기간 DB·Git·로그 증가, 반복 실행의 메모리 추이, 실제 원격 24시간 운영은 남아 있습니다. 앞선 macOS SQLite `SIGBUS`의 원인도 이 성공으로 해결됐다고 보지 않습니다.

실행 스크립트·원시 표본·AI 결과는 비공개 검증 자료로 보존했습니다. 원시 표본 SHA-256은 `9658f48c385ee62256d481558cd81004e2cab3110f837ca39324b2b06d49e2d4`입니다. 공개한 것은 측정 방법과 집계 결과이며, 공개 CI에서 개인 인증으로 이 실행을 재현하지 않습니다.

## 2026-11-07: Linux 서비스의 짧은 반복 시험

측정 대상은 `77df859`이며 [Ubuntu 22.04·24.04 CI](https://github.com/lmj00/agent-hub/actions/runs/42378103563)가 모두 통과했습니다. 실제 systemd 서비스와 Docker를 사용하고 **AI 응답만 테스트 대역으로 대체**했습니다. 위의 실제 Codex 시험과 다른 조건입니다.

각 환경에서 장애 복구 2건과 짧은 작업 10회를 수행했습니다. 작업 12개·실행 시도 14개, 단계별 표본 19개를 확인했습니다. 반복 작업이 끝날 때마다 실행 종료·컨테이너 제거를 확인했고, 재시작 후 중복 실행은 없었습니다. DB 무결성 검사와 시험용 데이터 정리도 통과했습니다.

| 관측값 | Ubuntu 22.04 | Ubuntu 24.04 |
| --- | --- | --- |
| 시험 시간 | 66.52초 | 60.07초 |
| 서버 메모리 — 반복 1회 후 → 10회 후 | 269.2 → 277.0MiB | 270.0 → 279.9MiB |
| 서버 메모리 표본 최대 | 279.8MiB | 281.4MiB |
| 대기 중 작업 컨테이너의 메모리 표본 최대 | 19.4MiB | 19.7MiB |
| 호스트 전체 사용량 추정 표본 최대 | 1,642.2MiB | 1,787.2MiB |
| 종료 후 DB 본체 / WAL 표본 최대 | 392.0 / 2,840.6KiB | 392.0 / 2,840.6KiB |
| 전용 로그 파일에 할당된 디스크 | 8.0MiB | 8.0MiB |

서버 수치는 서버와 자식 프로세스 묶음의 사용량입니다. 반복 1회 후부터 10회 후까지의 누적 CPU 시간 증가는 각각 4.351초·5.475초였습니다. 호스트는 약 16,000MiB RAM의 GitHub 임시 VM이며, 호스트 값에는 Docker·CI·측정 도구도 포함됩니다. 포함 관계인 수치를 더하지 않습니다. 로그의 8MiB는 파일에 할당된 공간이며 로그 본문 길이를 뜻하지 않습니다.

이 시험은 **약 1분의 대역 작업**입니다. 위의 실제 Codex 컨테이너 사용량과 큰 차이가 있으며, 장기 메모리 안정성·개발 Git 증가·2GiB 서버 적합성·원격 24시간 운영을 증명하지 않습니다. 수치 정의와 제한은 [Linux 자원 검사 안내](../guides/linux-resource-check.md)에 있습니다.

CI 첨부 파일은 7일간 보관합니다. 원본 로그와 집계 검증 자료는 별도로 보존했으며, 원본 SHA-256은 Ubuntu 22.04가 `2fd1b69fc539d3d906e4819e9896543db1257dde34e3519d2b764fb4048ebdb6`, Ubuntu 24.04가 `c8ac62c6218147b86dde73479f128941b93438c5c8632350fd73414373eaeccf`입니다. 로그에는 인증·AI 결과·실제 프로젝트 데이터가 없습니다.
