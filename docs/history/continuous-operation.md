# 지속 관리 목표의 20분 자율 실행 시험

**입력이 없으면 기다리고, 관측 값이 바뀌면 개발·검증·반영을 이어가는 흐름을 로컬에서 확인했습니다.** 실제 서버의 24시간 운영 검증은 아닙니다.

이후 [Linux 1시간 시험](linux-continuous-operation.md)에서 실제 프로세스 재시작과 자원 측정까지 확인했습니다. 아래는 앞선 20분 시험의 기록입니다.

## 무엇을 시험했나

처음에 지속 관리 목표와 두 구현 요구를 등록했습니다. 이후 가상 서비스의 관측 값을 바꾸어 요구를 차례로 활성화했습니다. 에이전트에게 새 지시를 보내거나 DB에 작업을 직접 넣지는 않았습니다.

첫 작업은 문자열을 URL용 이름으로 바꾸는 함수, 두 번째는 그 함수를 재사용해 같은 이름의 개수를 세는 함수입니다. 작업 사이에는 입력 유지, 관측 서비스의 일시적인 HTTP 503, 같은 Node 프로세스 안에서 앱을 닫고 다시 여는 검사를 넣었습니다.

| 조건 | 값 |
| --- | --- |
| 날짜·검증 코드 | 2026-11-07, `c36334c` |
| 환경 | macOS의 Node 24.22.1 서버 + Docker 실행기 |
| 실제 AI | Codex `gpt-6.1-sol`, `medium` |
| 관측 시간 | 1,201.072초, 약 20분 |
| 상한 | AI 호출 20회, 주 실행 루프 35분 |
| 등록 방식 | API로 프로젝트·목표 등록, 이후 자동 실행 |

## 관측 결과

| 경과 시간 | 실제 결과 |
| --- | --- |
| 시작~3분 | 다음 할 일을 두 번 점검하고 대기. 앱을 다시 연 뒤 작업 수·예산·다음 점검 시각 유지 |
| 3분~5분 54초 | 첫 입력을 관측하고 첫 작업 개발·검증·반영 |
| 6분 10초~8분 21초 | 관측 서비스가 실패한 동안 새 개발 작업 없이 대기, 복구 후 새 관측 수신 |
| 10분 54초~14분 22초 | 두 번째 입력을 관측하고 앞선 변경을 사용하는 두 번째 작업 반영 |
| 이후~20분 | 추가 개발 작업 없이 대기. 지속 관리 목표는 활성 상태 유지 |

최종 기록은 **계획 10건·개발 작업 2건·Run 12건·AI 호출 14건·Git 반영 2건**입니다. 모든 실행이 성공했고, 14개 AI 호출 모두 gstack 지침을 읽은 기록이 있습니다. 개발 결과는 별도의 12개 검산도 통과했습니다.

서비스 관측은 241건이며 의도한 장애 구간의 실패 26건을 포함합니다. 관측 요청은 GET만 사용했습니다. 프로젝트 원본은 바뀌지 않았고, 실행 종료와 소유한 컨테이너 정리를 확인한 뒤 임시 인증·작업 공간을 정리했습니다.

## 이 결과의 범위

- 미리 정한 작은 요구를 데이터에 따라 실행한 예제입니다. 실제 프로젝트의 문제를 얼마나 잘 발견하고 개선하는지는 별도 검증이 필요합니다.
- 앱을 닫고 다시 열 때 관측용 DB 연결은 유지했습니다. 실제 프로세스 강제 종료·재시작은 [별도 Linux CI 검사인 O4a](../plans/operations.md#implementation-tasks--운영-준비)의 근거를 따릅니다.
- 실행 중 호스트 장애·장기간 자원 증가·원격 24시간 운영을 검사한 결과는 아닙니다.
- 이 실행은 SQLite 잠금 보완 **이전** 코드에서 수행했습니다. 잠금 수정의 검증 근거는 별도의 회귀 테스트이며, 이 성공으로 과거 `SIGBUS` 원인이 해결됐다고 판단하지 않습니다.

원본 DB·AI 출력·인증·작업 경로는 공개하지 않습니다. 비공개 결과 JSON의 SHA-256은 `1271b50fddf2c8223e34ad6059238c2af446fff786e61b1eb0821972e55fecaa`입니다. 현재 진행 상태는 [구현 계획](../02-implementation-plan.md)을 참고합니다.
