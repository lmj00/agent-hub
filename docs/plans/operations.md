## 6단계 운영 준비 검토

검토 대상은 [진행 문서의 운영 단계](../02-implementation-plan.md#첫-운영-버전의-완료-기준)입니다. F3 뒤의 운영 준비를 아래 O1~O4로 나눕니다. O1·O2는 아래에 구현 결과를 추가했으며 O3·O4는 남아 있습니다. 이 계획을 배포·장기 운영 완료 기록으로 보지 않습니다. 사용자가 일반적인 결정을 기존 방향과 문서에 따라 독립적으로 진행하도록 지시했으므로, 아래 권고안은 그 범위에서 자율 선택했습니다. 실제 클라우드 배포와 실제 트레이딩 서비스 변경은 현재 실행 권한에서 제외합니다. 6단계의 원격·24시간 완료 기준은 유지합니다.

### Scope Challenge와 전제

기존 단일 백엔드·단일 Run·Docker 실행 격리·인증·복구를 재사용합니다. 새 큐나 원격 worker를 만들지 않습니다. 이번 준비는 실행 설정, 저장 상태 보존, 알림, 운영 검증이라는 네 순차 단위입니다. 별도 병렬 PR 없이 현재의 커밋 단위 작업을 유지합니다. 전체 변경 파일 수는 구현 중 확정하며 O1은 문서·검사 포함 약 9개, O2~O4는 각각 약 6~12개로 추정합니다. 이 수치는 실제 구현량이 아닙니다.

### Architecture review

**A1 — 서버 실행 방식.** 두 구조를 비교했습니다. A는 백엔드·HTTPS 프록시 모두 컨테이너로 운영하며 호스트 Docker를 제어합니다. 배포 묶음은 간결하지만 실행기에 전달하는 절대 경로와 컨테이너 안팎 경로를 함께 관리해야 합니다. B는 Linux 호스트의 systemd가 Node 서버를 관리하고 Caddy가 HTTPS를 종료하며, 기존 Docker 실행기를 그대로 사용합니다. 첫 버전은 B를 선택합니다. 기존 경로·종료·소유권 규칙을 재사용할 수 있기 때문입니다. Docker 소켓 접근 권한을 가진 서버는 신뢰하는 관리 프로그램이며, 작업 컨테이너의 제한과 서버 자체의 권한을 혼동하지 않습니다.

**A2 — 저장·백업 경계.** 앱 배포 파일과 비공개 상태·설정·인증을 나눕니다. DB·개발 Git·준비한 입력을 같은 백업 시점으로 묶습니다. 처음에는 서버를 멈춘 상태의 백업을 지원합니다. 실행 소유권과 미확정 실행·반영을 검사하고, 복원 미리보기에서 저장 경로·해시·스키마·Git 일치를 확인합니다. 첫 복원 계약은 같은 절대 경로·호환 앱 버전입니다. 운영 데이터를 덮어쓰기 전에 빈 복원 위치에서 검증하며, 임의 경로 이동·온라인 Git 변경 중 백업은 지원했다고 표시하지 않습니다. DB만 복사하는 대안은 WAL 및 Git 반영 기록을 함께 보존하지 못하므로 채택하지 않습니다.

**A3 — 장애 감지와 알림.** systemd는 부모 프로세스의 종료를 감지합니다. 별도 위치의 외부 점검은 HTTPS 접근과 `/health/ready`를 확인합니다. 앱 내부는 인증 실패·복구 한도 초과 등 사용자 조치가 필요한 상태를 알립니다. 정상 대기·예산 대기와 장애를 구분하고, 긴 실행 동안 대기열의 마지막 점검 시각이 오래됐다는 이유만으로 죽었다고 판정하지 않습니다. 알림은 제한 시간·재시도 상한·중복 억제를 갖고, 전송 실패가 작업 배정이나 상태 저장을 막지 않게 합니다. 실제 수신처 적용 전에는 소유한 로컬 수신기만 사용합니다.

**A4 — 배포와 검증 경계.** 설치를 자동 실행하는 스크립트 대신 검토 가능한 서비스·프록시·로그 설정과 실행 절차부터 제공합니다. Node·pnpm·앱 의존성은 저장소의 고정 버전을 사용하고, Linux 도구의 실제 검사 버전도 기록합니다. 앱 교체는 서버 중지 → 백업 → 검증한 빌드 교체 → 시작 → 상태 확인 순서입니다. DB 마이그레이션 이후 예전 실행 파일만 되돌리는 것을 복구로 안내하지 않습니다.

```text
브라우저 → Caddy HTTPS → 127.0.0.1의 인증된 Node 서버
                            ├─ SQLite + 비공개 개발 Git + 준비한 입력
                            └─ 기존 Docker 개발 / 테스트 / 독립 검토
systemd → 부모 종료 감지·제한된 재시작 → 기존 실행 대조·복구
외부 점검 → HTTPS / DB 준비 상태 → 지정한 알림 수신처
서버 중지·실행 대조 → 일관된 백업 → 미리보기·무결성 검사 → 복원
```

새 공개 모듈의 책임은 운영 보존·전달에 둡니다. 업무 실행 상태의 소유자는 기존 서버입니다. 얕은 전달 계층, 단계별로 흩어진 백업 모듈, 별도 상태 사본, 두 큐, 임의 내부 import, 수동으로 맞추는 스키마 목록을 추가하지 않습니다. 배포 설정의 고정 경로는 한 운영 문서에서 관리하고 실제 설정 검사로 불일치를 찾습니다. Dispositions: A1~A4 accepted(사용자의 자율 진행 지시, R1~R4).

### Code quality review

**Q1 — 비밀과 실패 출력.** 공개 예제에는 서버 주소·인증 키·실제 프로젝트 경로를 넣지 않습니다. 운영 설정·백업은 비공개 파일 권한으로 보존합니다. 백업 중 공간 부족·부분 복사·권한 오류는 완료 표시 없이 실패시키고, 임시 결과만 정리합니다. 알림에는 상태와 식별 정보만 포함하며 원본 로그·AI 응답·인증을 그대로 전송하지 않습니다.

**Q2 — 기존 코드 재사용.** 백업은 현재 DB 연결·실행 소유권·준비한 입력과 Git 검사를 먼저 대조해 재사용합니다. 복구 정책·Run 상태 전이를 운영 도구에서 재구현하지 않습니다. 앱 오류와 알림 전달 오류를 따로 기록합니다. 새로운 범용 워크플로·메시지 브로커·플러그인 계층은 필요하지 않습니다. Dispositions: Q1/Q2 accepted(R2/R3). 공유 함수 추가는 실제 두 호출의 계약을 확인한 경우에 한합니다.

### Performance review

**P1 — 측정 전 사양 확정 금지.** F3의 337.0MiB는 부모 Node의 표본 최대 RSS입니다. Docker·OS·동시 서비스가 빠져 있어 서버 최소 사양으로 쓰지 않습니다. 대표 작업의 CPU·전체 메모리·디스크 증가량과 종료 후 반환을 따로 측정합니다. 측정 때문에 실행 중 SQLite를 외부 도구로 반복 열 필요는 없습니다.

**P2 — 보존과 반복 상한.** 서비스 전용 로그 공간에 용량·보존 기간을 둡니다. 전체 호스트의 다른 서비스 로그 설정은 변경하지 않습니다. DB 업무 이력의 삭제 정책과 로그 파일 회전은 별개입니다. 상태 폴링·알림 조회는 범위를 제한하고, 백업은 파일을 통째로 메모리에 읽지 않습니다. 디스크 공간 부족과 전송 실패는 유한한 실패로 드러나야 합니다. Dispositions: P1/P2 accepted(R5/R6). 운영 수치는 측정 전 추정으로 표시합니다.
