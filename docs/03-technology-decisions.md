# 기술 선택과 대안

기준은 **혼자 이해하고 운영할 수 있는 구조로 시작하되, 중요한 규칙을 바꾸기 어렵게 만들지 않는 것**입니다. 아래는 지금의 선택이고, 자세한 비교와 변경 이유는 [기술 결정 기록](history/technology-decisions.md)에 보존합니다.

정확한 버전은 [Node 버전 파일](../.nvmrc), [루트 패키지 설정](../package.json), 각 앱의 `package.json`과 [잠금 파일](../pnpm-lock.yaml)을 기준으로 합니다. 과거 문서의 버전을 복사해 설치하지 않습니다.

## 선택 한눈에 보기

| 선택 | 왜 골랐나 | 감수하는 점 |
| --- | --- | --- |
| TypeScript + Node.js 24 | 서버·화면의 자료 형식을 공유하고 Codex SDK와 연결 | TypeScript 문법·비동기 처리 학습 필요 |
| pnpm | 화면·서버·공통 패키지를 한 저장소에서 관리 | npm과 설치·실행 방식의 차이를 알아야 함 |
| Fastify | API를 작은 기능부터 구성하고 요청·응답 검사 연결 | 필요한 기능을 직접 골라 연결해야 함 |
| React + Vite | 목표·작업·실행 상태를 화면에서 관리 | 서버와 별도의 화면 빌드 필요 |
| SQLite + better-sqlite3 | 단일 서버의 상태를 파일 DB로 저장하고 트랜잭션 사용 | 긴 동기 쿼리와 여러 쓰기 작업의 경합 관리 필요 |
| Drizzle ORM + Kit | TypeScript 테이블 정의와 SQL 변경 이력 연결 | 생성 SQL을 직접 검토해야 함 |
| 기능별 코드 구성 | 등록·실행·복구 코드를 하는 일 기준으로 찾기 쉽게 배치 | 공통 규칙이 여러 곳에 복사되지 않게 관리 |
| Docker 실행기 | AI 작업·테스트의 파일 접근과 실행 수명을 분리 | Docker 운영과 Linux 권한 정책 관리 필요 |
| systemd + Caddy | 단일 서버의 Node 재시작·로그·HTTPS 관리 | 서비스 계정·인증서·파일 권한 준비 필요 |

## pnpm을 고른 이유

npm·pnpm·Yarn 모두 가능한 선택입니다. 이 프로젝트는 화면·서버·공통 패키지를 함께 관리하므로 pnpm의 workspace 구성을 사용합니다. 팀 규모나 배포 환경이 달라지면 다시 비교할 수 있습니다.

Spring에 비유하면 라이브러리 설치·버전 관리·실행 명령을 맡는 부분이 Maven·Gradle과 일부 겹칩니다. TypeScript 컴파일이나 Node 실행 자체를 대체하는 도구는 아닙니다. [상세 비교](history/technology-decisions.md#패키지-관리자)

## SQLite와 Drizzle을 고른 이유

처음에는 사용자 한 명·서버 한 대·동시 Run 하나입니다. 별도 DB 서버 없이 상태를 보존하고, 작업 배정처럼 여러 변경을 함께 저장할 수 있는 SQLite를 선택했습니다.

`schema.ts`는 코드에서 사용하는 테이블 정의입니다. 변경하면 Drizzle Kit로 **SQL 마이그레이션을 생성하고 검토해 적용**합니다. 이미 적용한 SQL을 고치거나 운영 DB를 변경 이력 없이 동기화하지 않습니다.

직접 SQL, Kysely, Prisma도 비교했습니다. 현재는 테이블 정의·타입·마이그레이션을 연결하는 Drizzle 흐름을 사용합니다. 복잡한 쿼리는 값을 별도로 전달하는 안전한 SQL을 사용할 수 있습니다. [드라이버 비교](history/technology-decisions.md#sqlite-드라이버) · [DB 접근 방식 비교](history/technology-decisions.md#db-접근-방식과-마이그레이션)

여러 실행 서버가 필요해지면 DB 선택부터 재검토합니다. ORM을 쓴다고 DB 교체가 자동으로 끝나는 것은 아닙니다.

## 코드 구조를 정한 이유

프로그램 하나 안에서 기능을 나눕니다. 단순한 등록은 작게 만들고, 취소·복구·예산처럼 중요한 규칙은 공통 기준으로 관리합니다.

| 개념 | 이 프로젝트에서 사용하는 뜻 |
| --- | --- |
| DDD | Goal·Task·Run의 의미와 업무 규칙을 코드에서도 일관되게 사용 |
| 클린 아키텍처 | 업무 판단과 DB·HTTP·AI 연결의 책임을 나누어 핵심 규칙을 보호 |
| 헥사고날 아키텍처 | 내부가 필요로 하는 기능을 인터페이스로 정하고 외부 연결 코드가 이를 구현 |
| 기능별 구성 | 등록·취소·복구처럼 함께 바뀌는 코드를 가까이 배치 |

이 관점들은 서로 겹칩니다. 이름 하나를 선택하거나 모든 기능에 같은 네 계층을 만들 필요는 없습니다. Claude 등 다른 제공자를 붙일 때에도 연결 구현과 실제 실행·종료·결과 검증은 새로 필요합니다. [구조 대안 비교](history/technology-decisions.md#애플리케이션-구조) · [코드 예시](reference/code-and-runtime.md#외부-기술과-분리한다는-뜻)

## 실행과 운영 방식을 정한 이유

AI 역할의 판단은 Codex가 수행하고, 예산·취소·종료 확인·반영은 서버가 집행합니다. 실제 테스트는 AI 인증과 외부 통신을 제거한 별도 컨테이너에서 실행합니다.

Node 서버는 호스트 systemd로 관리합니다. 백엔드까지 Compose에 넣는 대안은 Docker 데몬이 사용하는 호스트 경로와 컨테이너 내부 경로를 함께 관리해야 하므로 현재는 선택하지 않았습니다. [운영 구성 비교](history/technology-decisions.md#운영-서버-구성--2026-11-07)

백업은 서버를 멈춘 상태에서 DB·개발 Git·준비 입력을 묶고, 원래 경로의 새 위치에 복원합니다. SQLite 파일 하나만 복사하는 방법은 WAL과 Git 기록을 놓칠 수 있어 선택하지 않았습니다. [백업 대안 비교](history/technology-decisions.md#상태-백업과-복원--2026-11-07)

외부 상태 점검에는 상태 조회만 가능한 인증값을 내보냅니다. 관리자 비밀번호 공유는 권한이 너무 넓고, 브라우저 세션은 8시간 뒤 만료되므로 사용하지 않습니다. 기존 서명 키에서 용도·주소를 구분한 HMAC 값을 계산해 별도 서버 비밀 저장소를 추가하지 않습니다. 대신 점검 인증값 폐기는 로그인 설정 교체와 함께 이루어집니다. [사용법과 폐기 방법](04-operations.md#외부에서-서버-상태-점검하기)

알림은 별도 메시지 브로커 없이 기존 SQLite에 전송 기록을 저장하고 서버 안의 독립 루프에서 전달합니다. 단일 사용자·단일 서버에 맞춰 운영 요소를 줄이되, 작업 큐가 전송 응답을 기다리지 않게 했습니다. 특정 메신저 SDK 대신 운영자가 지정한 JSON webhook을 사용하므로 수신처의 형식 변환과 중복 처리는 별도로 필요합니다. [알림 계약과 제한](guides/notifications.md)

## 코드 검사 도구

코드 형식과 기본 오류 검사는 Biome을 사용하고, 타입 검사는 기존 TypeScript 컴파일러로 유지합니다. Biome은 포맷과 검사를 한 도구로 관리할 수 있으며 [공식 설치 안내](https://biomejs.dev/installation/quick-start/)에 따라 버전을 고정합니다. 검사 범위와 활성 규칙은 `biome.json`, 실행 방법은 [개발 참여 안내](../CONTRIBUTING.md)를 기준으로 합니다.

Prettier와 ESLint·typescript-eslint 조합도 검토했습니다. 도입 시 확인한 typescript-eslint 8.72.1의 TypeScript 지원 범위는 `>=4.8.4 <6.1.0`으로, 이 저장소의 7.0.2와 맞지 않았습니다. Biome의 기본 오류 규칙부터 명시적으로 적용하며, 추가 규칙은 실제 결함 예방 효과와 현재 코드·도구의 지원을 확인해 도입합니다. 포맷 변경은 동작 변경과 분리하고, 생성된 마이그레이션·호환성 재현 자료는 자동 포맷하지 않습니다.

## 언제 다시 결정하나

실제 문제가 생기면 근거를 남기고 바꿉니다. 여러 서버가 필요하거나, 긴 DB 처리로 응답이 지연되거나, 반복 배포 비용이 커지면 관련 선택을 재검토합니다. 패턴 이름을 맞추기 위해 범용 계층·별도 큐·원격 worker를 미리 추가하지 않습니다.

역할별 gstack 적용 방식, 보안 경계, 복구·검증의 세부 대안은 [날짜별 결정 기록](history/technology-decisions.md)에 있습니다. 현재 동작 규칙은 [구조 문서](01-architecture.md), 완료 여부는 [진행 상태](02-implementation-plan.md)를 따릅니다.

## 개인용 GitHub 연결

관리 화면은 기존 비밀번호 로그인을 유지하고 GitHub 저장소 접근에는 개인 GitHub App 설치 인증을 사용합니다. 로그인 권한과 저장소 권한을 분리합니다. OAuth로 로그인을 바꾸는 대안은 사용자 토큰·콜백·만료 관리가 추가되며, 현재 저장소 목록 조회에는 필요하지 않습니다. PAT는 설정이 쉽지만 개인 토큰의 범위와 수명을 직접 관리해야 하므로 기본 연동으로 선택하지 않았습니다.

현재 세 REST 요청은 Node의 `crypto`와 `fetch`로 처리합니다. 고정 API 주소·리다이렉트 거부·전체 제한 시간·본문 크기 상한·응답 검증을 명시합니다. Octokit은 더 많은 API와 토큰 생명주기를 제공하는 대안입니다. 웹훅이나 복잡한 쓰기 작업으로 연결 코드가 커지면 도입을 다시 검토합니다. 사용자에게 제공하는 로그인 토큰을 직접 구현하는 선택과는 다릅니다. [연결 방법과 현재 범위](guides/github.md).
