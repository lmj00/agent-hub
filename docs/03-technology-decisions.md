# 초기 기술 선택과 대안

검토 기준일: 2026-10-26. 상태: 1단계 구현을 위한 초기 선택안. 아직 패키지를 설치하거나 조합의 동작을 검증하지 않았습니다. 정확한 의존성 버전은 1단계에서 호환성을 확인하고 고정합니다.

## 판단 기준

단일 사용자·단일 서버에서 작업 기록을 보존하고, 이후 무인 실행으로 확장할 수 있는 구성을 선택합니다. TypeScript 입문 시 이해할 수 있는 구조, 재현 가능한 설치, DB 변경의 검토 가능성, 운영 구성의 단순함을 우선합니다. 특정 도구의 인기도나 검증하지 않은 성능 차이를 선택 근거로 삼지 않습니다.

선택 기록에는 요구사항, 대안의 장점, 이번에 선택하지 않은 이유, 선택으로 감수할 비용과 재검토 조건을 함께 남깁니다. 대안을 제외하는 판단은 이 프로젝트의 현재 조건에 한정합니다.

## Node.js 버전

초기 선택안은 Node.js 24 LTS입니다. 기준일에 확인한 패치 후보는 24.22.1이며, 구현 시점의 보안 업데이트와 호환성을 재확인합니다. 공식 릴리스 목록에서 24는 LTS, 26은 Current로 표시됩니다. [Node.js 릴리스 목록](https://nodejs.org/en/blog/release), [24.22.1 릴리스](https://nodejs.org/en/blog/release/v24.22.1)

| 후보 | 장점 | 현재 판단 |
| --- | --- | --- |
| Node.js 22 LTS | 기존 22 환경과 버전을 맞출 때 유리 | 기존 런타임 제약이 없는 새 프로젝트이므로 24를 우선 검증 |
| Node.js 24 LTS | 장기 지원 계열을 기준으로 신규 개발 가능 | 초기 선택 |
| Node.js 26 Current | 새 런타임 기능을 사용할 수 있음 | 현재 요구에 필수인 26 전용 기능이 없어 LTS 계열 우선 |

**감수하는 점:** 최신 메이저 기능을 즉시 사용하지 않으며, 선택한 LTS도 패치와 보안 업데이트를 관리해야 합니다. 버전 고정은 업데이트를 영구히 멈춘다는 뜻이 아닙니다.

**재검토 조건:** 필요한 의존성이 다른 런타임을 요구하거나, 지원 종료가 다가오거나, 다음 LTS에서 필요한 기능과 호환성이 검증되는 경우입니다.

## 패키지 관리자

초기 선택안은 pnpm입니다. `apps/web`, `apps/server`, `packages/contracts`를 workspace로 관리하고 내부 참조를 명시합니다. 공식 설치 문서의 현재 배포 계열은 12이며, 정확한 버전은 구현 때 고정합니다. [pnpm 설치·호환성](https://pnpm.io/installation)

| 후보 | 장점 | 현재 판단 |
| --- | --- | --- |
| npm | 별도 패키지 관리자 도입 부담이 작고 workspace 지원 | 충분히 가능한 대안. 초기안에서는 pnpm의 workspace 설정과 내부 참조 방식을 선택 |
| pnpm | workspace와 `workspace:` 프로토콜로 내부 패키지 연결 명시 | 초기 선택 |
| Yarn | workspace, 내부 참조, 패키지 간 규칙을 관리하는 constraints 제공 | 현재 규모에서는 이 추가 기능을 선택 근거로 삼을 요구가 없음 |

세 도구 모두 여러 패키지를 한 저장소에서 관리할 수 있습니다. pnpm만 가능한 구조라는 이유로 선택하지 않습니다. [npm workspaces](https://docs.npmjs.com/cli/v11/using-npm/workspaces/), [pnpm workspace](https://pnpm.io/workspaces), [Yarn workspaces](https://yarnpkg.com/features/workspaces)

**감수하는 점:** 기여자가 pnpm을 준비해야 하고, CI·배포에서도 동일한 버전을 사용해야 합니다. 설치 시간이나 디스크 절약 효과는 이 프로젝트에서 아직 측정하지 않았습니다.

**재검토 조건:** 배포 환경에서 pnpm을 지원하기 어렵거나, 협업 환경의 표준화 이익이 전환 비용보다 큰 경우입니다. 다른 잠금 파일을 함께 유지하지 않고 선택한 관리자로 통일합니다.

## SQLite 드라이버

드라이버는 SQLite 파일에 실제로 연결하는 도구입니다. ORM 선택과 구분하며, 초기 선택안은 better-sqlite3입니다.

| 후보 | 장점 | 현재 판단 |
| --- | --- | --- |
| better-sqlite3 | 동기 API와 트랜잭션 지원, 주요 플랫폼 사전 빌드 제공 | 짧은 메타데이터 조회·쓰기와 트랜잭션을 처리하는 초기 드라이버로 선택 |
| Node.js 내장 `node:sqlite` | 별도 SQLite 드라이버 패키지 없이 런타임에서 제공 | Node.js 24 문서상 Stability 1.2, RC 단계이므로 현재는 보류 |
| libSQL 클라이언트 | 로컬 파일과 원격 DB 연결을 지원 | 현재는 로컬 SQLite 파일만 필요하므로 원격 연결 기능을 선택 근거로 삼지 않음 |

근거: [better-sqlite3 공식 저장소](https://github.com/WiseLibs/better-sqlite3), [Node.js 24 SQLite](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html), [Drizzle의 SQLite 드라이버 안내](https://orm.drizzle.team/docs/sqlite/get-started-sqlite).

**감수하는 점:** better-sqlite3는 네이티브 모듈이므로 개발·배포 플랫폼에서 설치를 확인해야 합니다. 동기 쿼리가 길어지면 API 응답도 지연될 수 있습니다. 짧은 트랜잭션, 적절한 인덱스와 WAL을 사용하고, DB 트랜잭션 안에서 AI 응답을 기다리지 않습니다.

**재검토 조건:** 내장 모듈의 안정성과 필요한 기능이 검증되거나 네이티브 모듈 설치가 운영 부담이 되는 경우입니다. 장시간 쿼리가 관측되면 쿼리 개선과 실행 분리를 검토합니다. 원격 DB나 다중 서버가 필요해지면 드라이버뿐 아니라 DB 선택부터 다시 검토합니다.

## DB 접근 방식과 마이그레이션

초기 선택안은 Drizzle ORM + Drizzle Kit입니다. TypeScript로 스키마와 쿼리를 작성하고, 생성된 SQL 마이그레이션을 검토해 적용합니다. Drizzle은 better-sqlite3 연결을 지원합니다. [SQLite 연결](https://orm.drizzle.team/docs/sqlite/get-started-sqlite), [SQL 마이그레이션 생성](https://orm.drizzle.team/docs/drizzle-kit-generate)

| 후보 | 장점 | 현재 판단 |
| --- | --- | --- |
| 직접 SQL + 별도 마이그레이션 관리 | 실행 SQL과 트랜잭션이 명확하고 ORM 학습이 필요 없음 | 유효한 대안이나 결과 타입·스키마와 코드의 일치를 직접 관리해야 함 |
| Drizzle ORM + Drizzle Kit | TypeScript 스키마·쿼리와 SQL 마이그레이션 생성 연결 | Task·Run·Step·Event의 스키마 변경을 함께 관리하기 위해 선택 |
| Kysely | 타입을 검사하는 SQL 쿼리 빌더로 쿼리를 명시적으로 작성 | SQL 중심 개발의 대안. 현재는 스키마 선언부터 SQL 변경 생성까지 연결하는 Drizzle 흐름을 우선 |
| Prisma | 데이터 모델·클라이언트·마이그레이션을 연결하는 도구 체계 | 검토 시점의 Prisma 8 문서에서 SQLite가 실험적으로 표시되어 초기안에서는 제외. 이전 메이저의 지원 상태와 동일하게 취급하지 않음 |

대안 근거: [Kysely 공식 문서](https://www.kysely.dev/), [Prisma 마이그레이션과 지원 범위](https://www.prisma.io/docs/orm/migrations/how-migrations-work).

**감수하는 점:** ORM과 마이그레이션 도구의 개념·버전 호환성을 추가로 학습해야 합니다. 타입 검사는 실제 DB 상태나 모든 SQL 오류를 보장하지 않습니다. ORM이 SQLite와 다른 DB 사이의 전환을 자동으로 해결한다고 가정하지 않습니다.

**마이그레이션 원칙:** 생성된 SQL과 메타데이터를 Git에 보관하고 검토한 뒤 적용합니다. 적용 이력을 보존하며 이미 적용된 파일은 임의 수정하지 않습니다. 운영 스키마를 변경 이력 없이 직접 동기화하지 않습니다. 빈 DB 생성과 기존 DB 업그레이드를 검증하며, 데이터 손실 가능 변경은 백업·복원 절차를 먼저 확인합니다.

**재검토 조건:** 필요한 SQLite 기능이나 트랜잭션을 표현하기 어려워지거나, 타입 복잡도·마이그레이션 문제가 유지보수 비용을 키우는 경우입니다. 특정 복잡한 쿼리는 매개변수 바인딩을 적용한 SQL로 작성할 수 있으며, 곧바로 ORM 전체를 교체할 필요는 없습니다.

## 구현 시 확정할 버전과 검증

- 런타임은 프로젝트의 버전 파일과 배포 설정에, pnpm은 `packageManager`에 정확한 버전을 명시합니다. 의존성 선언과 잠금 파일을 함께 커밋하고 CI에서 잠금 파일 변경 없는 설치를 사용합니다.
- Drizzle 공식 안내에는 `@rc` 예제가 포함되어 있습니다. 예제를 그대로 설치하지 않고 정식 배포된 ORM·Kit·드라이버 조합의 지원 범위를 확인해 고정합니다. 정식 조합으로 요구를 충족하지 못하면 대안을 다시 비교합니다.
- 개발 환경과 Linux 배포 환경에서 설치, 타입 검사, DB 열기·쓰기·트랜잭션, 마이그레이션을 검증합니다. 성능이나 메모리 이점은 측정 전 확정하지 않습니다.
- 보안·패치 업데이트는 별도 변경으로 검증하고, 메이저 변경은 호환성과 DB 영향을 검토합니다. 실제 고정 버전은 패키지·잠금·런타임 설정을 기준으로 조회하고 이 문서는 선택 이유와 변경 이력을 보존합니다.
