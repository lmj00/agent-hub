# 초기 기술 선택과 대안

> 이 문서는 **왜 이 기술과 코드 구조를 선택했는지**를 남깁니다. 다른 도구보다 항상 우수하다는 평가가 아니라, agent-hub의 현재 요구에 대한 판단입니다.

초기 자료 검토 기준일: 2026-10-26. 2026-10-29에 서버 실행 골격과 SQLite 저장 기반의 설치·동작을 검증하고 버전을 고정했습니다. 아래 비교는 각 검토일 기준이며, 실제 고정 버전은 패키지·잠금·런타임 설정을 기준으로 확인합니다.

## 기술 용어를 읽는 방법

| 용어 | 이 문서에서 뜻하는 것 |
| --- | --- |
| 런타임 | 서버 코드를 실제로 실행하는 환경. 이 프로젝트에서는 Node.js |
| LTS | 장기간 지원하는 릴리스 계열 |
| 패키지 관리자 | 라이브러리 설치·버전과 실행 명령을 관리하는 도구 |
| workspace | 한 저장소의 화면·서버·공통 패키지를 함께 관리하는 구성 |
| 드라이버 | 프로그램과 실제 DB를 연결하는 코드 |
| ORM | 코드로 DB의 테이블·데이터 접근을 표현하는 도구 |
| 마이그레이션 | 테이블·인덱스 등의 변경 내용을 순서대로 기록하고 적용하는 절차 |
| 스키마 | 데이터에 어떤 항목과 형식이 있는지 정한 구조. DB에서는 테이블·열·제약 등의 정의 |
| 쿼리 | DB에서 데이터를 조회하거나 변경하는 명령 |
| 인덱스 | DB에서 필요한 데이터를 빠르게 찾기 위한 보조 구조 |
| 메타데이터 | 데이터 자체를 설명하거나 관리하는 정보. 예: 파일 위치·크기, DB 변경 이력 |
| 네이티브 모듈 | 운영체제·CPU 환경에 맞는 바이너리 코드가 포함된 모듈. 환경에 따라 설치 확인 필요 |
| 동기 API | 호출한 코드가 작업 결과를 받은 뒤 다음 처리를 이어가는 방식 |
| 잠금 파일(lockfile) | 설치할 의존성의 구체적인 버전과 연결 관계를 기록한 파일 |
| RC | 정식 출시 전 검증 단계인 릴리스 후보 |

설치할 패키지의 이름은 코드와 공식 문서를 찾을 수 있도록 그대로 사용합니다. [실행 규칙의 용어 설명](01-architecture.md#문서에서-쓰는-용어)과 [DB 변경을 함께 저장하는 이유](01-architecture.md#함께-저장할-데이터와-테스트-방법)도 참고할 수 있습니다.

## 판단 기준

단일 사용자·단일 서버에서 목표와 작업 기록을 보존하고, 첫 운영 버전부터 자율 작업 생성·개발·검증을 이어갈 수 있는 구성을 선택합니다. TypeScript 입문 시 이해할 수 있는 구조, 재현 가능한 설치, DB 변경의 검토 가능성, 운영 구성의 단순함을 우선합니다. 특정 도구의 인기도나 검증하지 않은 성능 차이를 선택 근거로 삼지 않습니다.

선택 기록에는 요구사항, 대안의 장점, 이번에 선택하지 않은 이유, 선택으로 감수할 비용과 재검토 조건을 함께 남깁니다. 대안을 제외하는 판단은 이 프로젝트의 현재 조건에 한정합니다.

## Node.js 버전

초기 선택안은 Node.js 24 LTS입니다. 기준일에 확인한 패치 후보는 24.22.1이며, 구현 시점의 보안 업데이트와 호환성을 재확인합니다. 공식 릴리스 목록에서 24는 LTS, 26은 Current로 표시됩니다. [Node.js 릴리스 목록](https://nodejs.org/en/blog/release), [24.22.1 릴리스](https://nodejs.org/en/blog/release/v24.22.1)

| 후보 | 장점 | 현재 판단 |
| --- | --- | --- |
| Node.js 22 LTS | 기존 22 환경과 버전을 맞출 때 유리 | 기존 런타임 제약이 없는 새 프로젝트이므로 24를 우선 검증 |
| Node.js 24 LTS | 장기 지원 계열을 기준으로 신규 개발 가능 | 초기 선택 |
| Node.js 26 Current | 새 런타임 기능을 사용할 수 있음 | 현재 요구에 필수인 26 전용 기능이 없어 LTS 계열 우선 |

**감수하는 점:** 최신 메이저 기능을 즉시 사용하지 않으며, 선택한 LTS도 패치와 보안 업데이트를 관리해야 합니다. 버전 고정은 업데이트를 영구히 멈춘다는 뜻이 아닙니다.

**재검토 조건:** 필요한 의존성이 다른 런타임을 요구하거나, 지원 종료가 다가오거나, 다음 LTS에서 필요한 기능과 호환성이 검증되는 경우입니다.

## 패키지 관리자

초기 선택안은 pnpm입니다. `apps/web`, `apps/server`, `packages/contracts`를 workspace로 함께 관리하고, 어떤 내부 패키지를 사용하는지 명시합니다. 자료 검토일의 공식 배포 계열은 12이며, 정확한 버전은 구현 때 고정합니다. [pnpm 설치·호환성](https://pnpm.io/installation)

| 후보 | 장점 | 현재 판단 |
| --- | --- | --- |
| npm | 별도 패키지 관리자 도입 부담이 작고 workspace 지원 | 충분히 가능한 대안. 초기안에서는 pnpm의 workspace 설정과 내부 참조 방식을 선택 |
| pnpm | workspace와 `workspace:` 프로토콜로 내부 패키지 연결 명시 | 초기 선택 |
| Yarn | workspace, 내부 참조, 패키지 간 규칙을 관리하는 constraints 제공 | 현재 규모에서는 이 추가 기능을 선택 근거로 삼을 요구가 없음 |

세 도구 모두 여러 패키지를 한 저장소에서 관리할 수 있습니다. pnpm만 가능한 구조라는 이유로 선택하지 않습니다. [npm workspaces](https://docs.npmjs.com/cli/v11/using-npm/workspaces/), [pnpm workspace](https://pnpm.io/workspaces), [Yarn workspaces](https://yarnpkg.com/features/workspaces)

**감수하는 점:** 기여자가 pnpm을 준비해야 하고, CI·배포에서도 동일한 버전을 사용해야 합니다. 설치 시간이나 디스크 절약 효과는 이 프로젝트에서 아직 측정하지 않았습니다.

**재검토 조건:** 배포 환경에서 pnpm을 지원하기 어렵거나, 협업 환경의 표준화 이익이 전환 비용보다 큰 경우입니다. 다른 잠금 파일을 함께 유지하지 않고 선택한 관리자로 통일합니다.

## SQLite 드라이버

드라이버는 SQLite 파일에 실제로 연결하는 도구입니다. ORM 선택과 구분하며, 초기 선택안은 better-sqlite3입니다.

| 후보 | 장점 | 현재 판단 |
| --- | --- | --- |
| better-sqlite3 | 동기 API와 트랜잭션 지원, 주요 플랫폼 사전 빌드 제공 | 짧은 메타데이터 조회·쓰기와 트랜잭션을 처리하는 초기 드라이버로 선택 |
| Node.js 내장 `node:sqlite` | 별도 SQLite 드라이버 패키지 없이 런타임에서 제공 | Node.js 24 문서상 Stability 1.2, RC 단계이므로 현재는 보류 |
| libSQL 클라이언트 | 로컬 파일과 원격 DB 연결을 지원 | 현재는 로컬 SQLite 파일만 필요하므로 원격 연결 기능을 선택 근거로 삼지 않음 |

근거: [better-sqlite3 공식 저장소](https://github.com/WiseLibs/better-sqlite3), [Node.js 24 SQLite](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html), [Drizzle의 SQLite 드라이버 안내](https://orm.drizzle.team/docs/sqlite/get-started-sqlite).

**감수하는 점:** better-sqlite3는 네이티브 모듈이므로 개발·배포 플랫폼에서 설치를 확인해야 합니다. 동기 쿼리가 길어지면 API 응답도 지연될 수 있습니다. 짧은 트랜잭션, 적절한 인덱스와 WAL을 사용하고, DB 트랜잭션 안에서 AI 응답을 기다리지 않습니다.

**재검토 조건:** 내장 모듈의 안정성과 필요한 기능이 검증되거나 네이티브 모듈 설치가 운영 부담이 되는 경우입니다. 장시간 쿼리가 관측되면 쿼리 개선과 실행 분리를 검토합니다. 원격 DB나 다중 서버가 필요해지면 드라이버뿐 아니라 DB 선택부터 다시 검토합니다.

## DB 접근 방식과 마이그레이션

초기 선택안은 Drizzle ORM + Drizzle Kit입니다. TypeScript로 스키마와 쿼리를 작성하고, 생성된 SQL 마이그레이션을 검토해 적용합니다. Drizzle은 better-sqlite3 연결을 지원합니다. [SQLite 연결](https://orm.drizzle.team/docs/sqlite/get-started-sqlite), [SQL 마이그레이션 생성](https://orm.drizzle.team/docs/drizzle-kit-generate)

| 후보 | 장점 | 현재 판단 |
| --- | --- | --- |
| 직접 SQL + 별도 마이그레이션 관리 | 실행 SQL과 트랜잭션이 명확하고 ORM 학습이 필요 없음 | 유효한 대안이나 결과 타입·스키마와 코드의 일치를 직접 관리해야 함 |
| Drizzle ORM + Drizzle Kit | TypeScript 스키마·쿼리와 SQL 마이그레이션 생성 연결 | Task·Run·Step·Event의 스키마 변경을 함께 관리하기 위해 선택 |
| Kysely | 타입을 검사하는 SQL 쿼리 빌더로 쿼리를 명시적으로 작성 | SQL 중심 개발의 대안. 현재는 스키마 선언부터 SQL 변경 생성까지 연결하는 Drizzle 흐름을 우선 |
| Prisma | 데이터 모델·클라이언트·마이그레이션을 연결하는 도구 체계 | 검토 시점의 Prisma 8 문서에서 SQLite가 실험적으로 표시되어 초기안에서는 제외. 이전 메이저의 지원 상태와 동일하게 취급하지 않음 |

대안 근거: [Kysely 공식 문서](https://www.kysely.dev/), [Prisma 마이그레이션과 지원 범위](https://www.prisma.io/docs/orm/migrations/how-migrations-work).

**감수하는 점:** ORM과 마이그레이션 도구의 개념·버전 호환성을 추가로 학습해야 합니다. 타입 검사는 실제 DB 상태나 모든 SQL 오류를 보장하지 않습니다. ORM이 SQLite와 다른 DB 사이의 전환을 자동으로 해결한다고 가정하지 않습니다.

**마이그레이션 원칙:** DB 구조는 변경 이력을 남기면서 수정합니다.

1. 생성된 SQL과 메타데이터를 검토하고 Git에 보관합니다.
2. 적용 이력을 보존하며, 이미 적용한 파일은 임의 수정하지 않습니다. 운영 DB 구조를 변경 이력 없이 직접 동기화하지 않습니다.
3. 빈 DB를 처음 만드는 경우와 기존 DB를 업그레이드하는 경우를 검증합니다. 데이터 손실 가능성이 있으면 백업·복원 절차를 먼저 확인합니다.

**재검토 조건:** 필요한 SQLite 기능이나 트랜잭션을 표현하기 어려워지거나, 타입 복잡도·마이그레이션 문제가 유지보수 비용을 키우는 경우입니다. 특정 복잡한 쿼리는 입력값을 SQL 문자열에 직접 끼워 넣지 않고 별도 값으로 전달하는 방식(매개변수 바인딩)으로 작성할 수 있으며, 곧바로 ORM 전체를 교체할 필요는 없습니다.

## 애플리케이션 구조

**선택:** 프로그램 하나 안에서 프로젝트 관리·작업 관리·AI 실행을 나눕니다. 각 기능에서는 등록·취소·재시도처럼 실제로 하는 일에 따라 코드를 모읍니다. 공통 규칙과 DB·AI 연결 코드는 분리합니다. 구체적인 파일 구성과 연결 기준은 [구조 문서](01-architecture.md#코드를-나누고-연결하는-기준)를 따릅니다.

설계 방식의 이름은 서로 다른 관점을 설명합니다. 아래 원칙은 함께 적용할 수 있으며, 이름 하나를 골라 모든 코드를 같은 모양으로 만들 필요는 없습니다.

| 관점 | 쉬운 설명 | agent-hub에서 적용하는 부분 |
| --- | --- | --- |
| 모듈형 모놀리스 | 프로그램은 하나로 배포하고 내부 기능을 나눔 | 프로젝트 관리·작업 관리·실행 모듈 |
| Vertical Slice | 변경할 기능의 코드를 가까이 모음 | 작업 등록·취소·재시도별 파일 |
| DDD | 업무의 개념·용어·규칙을 코드에 반영 | 장기 목표 Goal, 개별 작업 Task, 실행 시도 Run을 구분 |
| 클린 아키텍처 | 규칙·처리 절차·연결 코드의 책임을 나누고, 업무 코드가 외부 기술을 직접 참조하지 않게 함 | 작업 규칙과 등록·취소 절차에서 DB·AI SDK 사용법 분리 |
| 헥사고날 아키텍처 | 내부와 외부를 포트·어댑터로 연결 | 저장·실행 인터페이스와 SQLite·Codex 구현 |

클린과 헥사고날은 많이 겹칩니다. 예를 들어 작업 서비스가 저장 인터페이스를 사용하고 Drizzle 코드가 이를 구현하면, 헥사고날에서는 포트·어댑터로 설명하고 클린에서는 외부 구현이 내부의 약속을 따르는 의존 방향으로 설명할 수 있습니다. 인터페이스를 하나 만들었다는 사실만으로 전체 프로그램이 두 아키텍처를 만족하는 것은 아닙니다. 실제 코드 예시는 [코드 연결 기준](01-architecture.md#외부-기술과-분리한다는-뜻)을 참고합니다.

| 검토한 접근 | 장점 | 감수할 점과 현재 판단 |
| --- | --- | --- |
| 전체 기능을 Controller·Service·Repository 계층으로 구성 | 계층별 역할이 익숙하고 일관된 탐색 가능 | 한 기능 변경이 여러 계층에 흩어지고 단순 기능에도 전달 코드가 생길 수 있어 전역 폴더 기준으로는 선택하지 않음 |
| 모든 기능에 동일한 클린·헥사고날 구조 적용 | 의존 방향이 명확하고 외부 기술 없이 업무 로직 테스트 가능 | 기능마다 동일한 네 계층·인터페이스를 만들 필요는 없으므로 핵심 규칙과 실제 외부 연결에 분리 원칙을 적용 |
| 사용 사례별 Vertical Slice 구성 | 등록·취소·재시도 등 변경 단위로 관련 코드를 모으고 기능별 복잡도에 맞게 구성 | 규칙 중복과 기능 간 결합을 관리해야 함. 공통 상태 규칙과 외부 연결 경계를 함께 두는 방식으로 선택 |
| 기능별 서비스를 별도 배포 | 독립 배포·확장과 장애 격리 가능 | 현재는 단일 서버·동시 실행 하나이며, 통신·분산 상태 관리 비용을 정당화할 요구가 없어 미선택 |

클린·헥사고날 자체가 네 개의 폴더나 클래스 수를 강제하는 것은 아닙니다. 위 비교는 이 프로젝트에서 어느 범위까지 구조를 적용할지에 대한 판단입니다. Vertical Slice는 기능별 변경을 묶는 접근이고, 헥사고날은 외부 기술과 업무 로직 사이의 경계를 통해 독립 실행·테스트를 가능하게 하는 접근입니다. [Jimmy Bogard의 Vertical Slice 설명](https://www.jimmybogard.com/vertical-slice-architecture/), [Alistair Cockburn의 헥사고날 원문](https://alistair.cockburn.us/hexagonal-architecture)

**선택 이유:** 프로젝트 등록·조회는 작은 코드로 만들 수 있지만, 작업 취소·재시도·복구에는 여러 기능이 함께 지켜야 할 규칙이 있습니다. 간단한 기능은 작게 유지하고, 중요한 규칙은 한곳에 모아 테스트합니다. 나중에 Claude 같은 다른 제공자를 연결하거나 AI 장애를 재현할 때도 작업 관리 코드를 크게 바꾸지 않도록 실행 요청과 실제 SDK 호출을 분리합니다.

**감수하는 점:** 어떤 코드를 함께 쓰고 어디에서 나눌지 판단해야 합니다. 폴더만 나누고 다른 기능의 내부 코드를 마음대로 가져오면 구조가 다시 얽힙니다. AI가 코드를 추가할 때도 같은 규칙이 복사됐는지, 정한 연결 방식을 지키는지 확인해야 합니다. AI 제공자를 바꿀 때에는 새 연결 코드와 실제 실행·종료·결과 품질 검증이 필요합니다.

**재검토 조건:** 같은 규칙이 여러 기능에 반복되면 공통 규칙으로 모읍니다. 기능끼리 서로의 내부 구현을 필요로 하게 되면 역할을 다시 나눕니다. 파일이 커지면 하는 일에 따라 분리하고, AI 실행에 별도 서버가 필요해지면 기존 worker 분리 계획을 적용합니다. 실제 문제가 생겼을 때 구조를 보강하며, 패턴 이름을 맞추기 위해 공통 기반 클래스·범용 저장소·이벤트 버스를 추가하지 않습니다.

## 구현 시 확정할 버전과 검증

- 런타임은 프로젝트의 버전 파일과 배포 설정에, pnpm은 `packageManager`에 정확한 버전을 명시합니다. 의존성 선언과 잠금 파일을 함께 커밋하고 CI에서 잠금 파일 변경 없는 설치를 사용합니다.
- Drizzle 공식 안내에는 `@rc` 예제가 포함되어 있습니다. 예제를 그대로 설치하지 않고 정식 배포된 ORM·Kit·드라이버 조합의 지원 범위를 확인해 고정합니다. 정식 조합으로 요구를 충족하지 못하면 대안을 다시 비교합니다.
- 개발 환경과 Linux 배포 환경에서 설치, 타입 검사, DB 열기·쓰기·트랜잭션, 마이그레이션을 검증합니다. 성능이나 메모리 이점은 측정 전 확정하지 않습니다.
- 보안·패치 업데이트는 별도 변경으로 검증하고, 메이저 변경은 호환성과 DB 영향을 검토합니다. 실제 고정 버전은 패키지·잠금·런타임 설정을 기준으로 조회하고 이 문서는 선택 이유와 변경 이력을 보존합니다.

## 서버 실행 골격 적용 — 2026-10-29

첫 적용은 서버 실행·종료와 응답 확인까지입니다. Node.js 24.22.1, pnpm 12.16.1, Fastify 5.12.7, TypeScript 7.0.2, Vitest 5.0.5, tsx 4.23.15, Node.js 타입 정의 24.19.2를 고정했습니다. 직접 의존성은 정확한 버전으로 선언하고, 간접 의존성까지 포함한 설치 결과는 잠금 파일에 기록합니다. pnpm의 설정은 [공식 설정 문서](https://pnpm.io/settings)에 따라 `pnpm-workspace.yaml`에 둡니다.

| 결정 | 이유와 대안 |
| --- | --- |
| 개발 실행은 tsx, 빌드는 TypeScript 컴파일러 | 소스 변경 때 자동 재시작하고 배포 실행은 빌드한 JavaScript로 통일. Node.js의 TypeScript 직접 실행도 대안이지만, 개발·테스트에서 사용하는 모듈 변환 흐름을 먼저 검증 |
| 타입 검사는 별도 명령 | tsx와 테스트 실행의 변환만으로 타입 오류를 검사했다고 보지 않고 `pnpm typecheck`를 실행 |

| 서버 테스트는 Vitest | 기존 테스트 도구 선택을 적용. Node.js 내장 테스트 러너도 가능하지만, 이후 화면 테스트와 도구를 맞출 수 있는 Vitest를 사용 |
| 현재 필요한 서버 패키지만 생성 | workspace에 `apps/*`, `packages/*`를 지정하고, 화면·공통 계약·DB 파일은 사용하는 기능을 추가할 때 생성 |

macOS arm64에서 설치, 타입 검사, 빌드, 테스트와 실제 HTTP 응답·종료를 확인했습니다. Linux 설치와 SQLite 조합은 해당 구현 단계에서 확인합니다. 버전 업데이트 시 이 검증을 다시 수행합니다.

## SQLite 저장 기반 적용 — 2026-10-29

better-sqlite3 13.0.3, Drizzle ORM 0.45.4, Drizzle Kit 0.31.11, 타입 정의 9.6.0을 적용했습니다. 정식 버전과 Node.js 24 지원 범위를 확인하고, 기존 TypeScript 7.0.2 조합으로 설치·실행을 검증했습니다. 공식 문서의 `@rc` 예제와 실제 고정 버전을 구분합니다.

| 결정 | 이유와 감수하는 점 |
| --- | --- |
| 프로젝트 기본 테이블부터 생성 | ID·표시 이름·작업 공간 식별자·생성 시각만 저장. 실제 경로는 비공개 설정에서 연결하며, 실행 허용 정책은 AI 연동 단계에서 구체화해 추가 |
| 서버 시작 시 미적용 SQL 실행 | 단일 서버의 시작 순서를 DB 준비 → HTTP 시작으로 통일. 생성 SQL을 검토한 뒤 반영하며, 적용에 실패하면 DB를 닫고 시작 실패로 종료 |
| DB 경로와 SQL 경로를 실행 위치에서 분리 | 개발·빌드 실행이나 현재 디렉터리가 달라도 같은 DB와 마이그레이션을 사용. 배포 시 `migrations/`를 빌드 결과와 함께 보관해야 함 |
| WAL·외래 키 검사·FULL 동기화 | 짧은 트랜잭션과 데이터 제약을 사용. 잠금은 최대 1초 대기하며, 긴 동기 쿼리가 서버 응답을 지연시킬 수 있으므로 이후 쿼리도 짧게 유지 |
| DB 준비 상태는 프로젝트 테이블 조회로 확인 | 단순 서버 응답과 실제 DB 조회를 구분. 실행 중 조회 실패 시 503과 관측 시각을 반환하며, 응답에 SQL 오류나 파일 경로를 노출하지 않음 |

테이블은 `schema.ts`에 정의하고 Drizzle Kit으로 SQL·스키마 기록을 생성했습니다. 적용에는 ORM의 마이그레이션 기능을 사용합니다. 변경 이력을 남기지 않고 DB 구조를 바로 동기화하는 방식은 사용하지 않습니다. 생성 시각은 SQLite에 UTC 기준 Unix 시간의 밀리초 정수로 저장하고, Drizzle에서 `Date`로 변환합니다.

**타입 검사 설정:** 이번 조합에서는 Drizzle의 `.d.ts` 파일에서 사용하지 않는 DB 드라이버 참조와 타입 정의 정합성 오류가 발생했습니다. 서버 설정에 `skipLibCheck: true`를 적용해 선언 파일 자체의 검사를 제외합니다. 서버·테스트·스키마·도구 설정의 `.ts` 코드와 그 코드에서 사용하는 타입은 계속 검사하지만, 선언 파일 사이의 오류를 놓칠 수 있는 비용이 있습니다. 의존성 업데이트 시 이 설정의 필요성을 재검토합니다. [TypeScript 공식 설명](https://www.typescriptlang.org/tsconfig/skipLibCheck.html)

**검증:** macOS arm64와 Linux arm64 컨테이너에서 잠금 파일 기반 설치, 타입 검사, 빌드, 실제 SQLite 테스트를 통과했습니다. 테스트는 빈 DB 생성·재개방 후 데이터 보존·중복 적용 방지·트랜잭션 취소·기존 DB 업그레이드·실패한 마이그레이션의 되돌리기·조회 실패와 서버 응답의 구분을 확인합니다. macOS에서는 빌드한 프로그램을 다른 디렉터리에서 실행하고, HTTP 응답·프로세스 재시작·DB 연결 종료·잘못된 DB 경로의 시작 실패도 확인했습니다. 실제 AWS 운영 환경은 아직 검증하지 않았습니다.

## 프로젝트 등록·조회 적용 — 2026-10-31

기존 Fastify·Drizzle·SQLite 조합으로 구현하며 새 의존성과 DB 마이그레이션은 추가하지 않습니다. HTTP 요청 검증·응답은 `modules/projects/routes.ts`와 `schemas.ts`, 등록 절차와 필요한 저장 기능의 약속은 `create-project.ts`, 실제 DB 접근은 `drizzle-project-store.ts`에 둡니다. `app.ts`가 DB 구현을 연결합니다. 단순 목록·상세 조회는 별도 전달용 서비스 없이 저장 기능을 호출합니다.

| 결정 | 이유와 대안 |
| --- | --- |
| 기존 Fastify JSON Schema로 요청·응답 정의 | 상태 확인 API와 같은 도구로 런타임 입력 검증과 응답 필드 제한. Zod 같은 추가 도구 없이 시작하며, 현재 TypeScript 타입과 JSON Schema의 일치는 타입 검사·API 테스트로 확인 |
| 타입 변환·추가 필드 제거 비활성화 | 잘못된 타입이나 필드 오타를 자동 보정하면 요청 실수를 놓칠 수 있어 오류로 반환. 서버의 Ajv 설정에서 `coerceTypes: false`, `removeAdditional: false` 적용 |
| 저장 인터페이스와 Drizzle 구현 분리 | 등록 절차가 Fastify·Drizzle을 참조하지 않도록 작은 함수와 타입으로 연결. 범용 저장소·기반 클래스는 도입하지 않음 |
| 전체 목록 조회로 시작 | 초기 개인용 프로젝트 수에 맞춰 단순하게 구현. 목록이 커지면 페이지 단위 조회 추가 |

입력·반복 등록·응답의 기준은 [1단계 프로젝트 API](01-architecture.md#1단계-프로젝트-api)에 둡니다. 화면과 공유할 계약 패키지는 실제 화면 연결 단계에 추출합니다. 요청·응답 정의는 DB 테이블을 정의하는 `db/schema.ts`와 역할이 다릅니다. [Fastify 검증·직렬화 공식 설명](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)

**검증:** macOS arm64의 Node.js 24.22.1에서 타입 검사·빌드·전체 테스트 46개를 통과했습니다. 실제 SQLite를 사용하는 프로젝트 API 테스트로 입력 거부·등록·조회·정렬·앱 재개방 후 보존·DB 장애 응답을 확인했습니다. 빌드 결과를 별도 임시 DB로 실행해 HTTP 등록·조회와 프로세스 재시작 후 데이터 보존도 확인했습니다. 이번 API 변경의 Linux·AWS 검증은 수행하지 않았습니다.

## 작업 등록·조회 적용 — 2026-11-01

새 의존성 없이 기존 Fastify·Drizzle·SQLite를 사용합니다. `0001_tasks.sql`로 작업 테이블과 제약을 추가하며 기존 프로젝트 테이블·데이터와 `0000_projects.sql`은 유지합니다. 작업은 지시·프로젝트 ID·등록 요청 키·생성 시각과 `queued` 상태만 저장합니다. 실행 상태·취소·제한 시간·Goal은 해당 기능을 도입하는 단계에서 마이그레이션으로 확장합니다.

| 결정 | 이유와 대안 |
| --- | --- |
| 프로젝트별 요청 키를 DB 유일성 제약으로 관리 | 메모리만 사용하면 재시작 시 사라지고, 먼저 조회한 뒤 일반 INSERT하면 별도 연결 간 중복 경합이 생길 수 있어 `(project_id, request_key)`를 고유하게 지정 |
| 충돌 시 기존 작업 반환 | `ON CONFLICT DO NOTHING`의 대상을 요청 키 제약으로 한정. 저장과 기존 기록 조회를 짧은 immediate 트랜잭션으로 묶고, 등록 절차에서 지시가 다르면 409 처리. 기존 작업 내용은 덮어쓰지 않음 |
| 프로젝트 존재 확인 함수와 외래 키 | `app.ts`에서 프로젝트 조회를 연결해 없는 프로젝트는 404로 안내. DB에도 외래 키와 삭제 제한을 두어 데이터 관계를 보존 |
| 현재 필요한 등록·조회 필드만 추가 | 실제 실행 전에는 `queued`만 허용. 실행 기능을 붙일 때 상태 제약도 함께 확장하며 미구현 상태를 API로 받지 않음 |

등록 절차와 저장 기능의 약속은 `modules/tasks/create-task.ts`, 실제 DB 처리는 `drizzle-task-store.ts`, HTTP 요청·응답은 `routes.ts`·`schemas.ts`에 둡니다. 중복 처리 규칙은 DB 없이도 검사하고, 실제 저장·제약·업그레이드는 SQLite로 검증합니다. [등록·재전송 계약](01-architecture.md#1단계-작업-api), [Drizzle 충돌 처리](https://orm.drizzle.team/docs/insert#on-conflict-do-nothing), [트랜잭션](https://orm.drizzle.team/docs/transactions)

**검증:** macOS arm64의 Node.js 24.22.1에서 타입 검사·빌드·전체 테스트 70개를 통과했고 스키마를 재생성해 추가 변경이 없음을 확인했습니다. 실제 파일 DB로 재개방 후 작업·요청 키 보존, 동일 요청·다른 내용의 키 충돌, 프로젝트별 키 범위, 외래 키·상태 제약, 프로젝트만 있던 DB의 업그레이드를 확인했습니다. 빌드한 별도 서버 프로세스 두 개에서 같은 요청을 동시에 12번 보내 한 건만 생성되는 것과 서로 다른 지시의 같은 키 요청이 201/409로 나뉘는 것을 확인했습니다. 프로세스 재시작 후에도 상세·목록·중복 방지가 유지됩니다. 이번 변경의 Linux·AWS 검증과 실제 AI 호출은 수행하지 않았습니다.

설치한 SDK에는 사용자 설정을 완전히 무시하는 전용 옵션이 없어, 초기에는 인증만 담은 별도 폴더를 준비하고 사용자 설정·사용자 스킬·플러그인 및 프로젝트가 상속하는 `.codex/config.toml`을 거부합니다. Codex가 첫 실행에 만드는 `skills/.system`은 후속 실행을 막지 않도록 허용합니다. 자식 실행의 `HOME`도 전용 폴더로 지정하고 호스트 스킬 탐색·스킬 검색·스킬을 통한 MCP 설치를 끕니다. 호스트 스킬 탐색 차단은 설치한 CLI의 실험 기능이므로 SDK를 올릴 때 다시 검증해야 합니다. 명명된 권한 설정은 [공식 권한 문서](https://learn.chatgpt.com/docs/permissions)의 베타 기능입니다. 예전 `sandboxMode`를 함께 지정하면 이 설정을 덮어쓸 수 있어 사용하지 않습니다. 프로젝트 내용은 분석할 데이터로 취급하며 별도 지침 파일을 자동 주입하지 않습니다. 이것만으로 임의의 비신뢰 저장소를 안전하게 실행한다고 보장하지 않으므로 현재 입력은 비밀 정보 없는 준비된 예제로 제한합니다.

SDK의 중단 신호는 자식 명령 전체가 종료됐다는 증거를 제공하지 않습니다. 현재 CLI의 Ctrl+C·제한 시간 초과는 `interrupted`로 보존하고 후속 실행을 막습니다. 강제 종료 후 남은 `running`도 같은 이유로 막습니다. 인증·설정·한도 오류는 Run에 보류 상태로 남기며, 계정별 차단 해제·확인된 재시도 시각·수동 복구는 다음 단위입니다. 사용자의 새 요청만으로 불확실한 실행을 건너뛰지 않습니다.

**검증:** macOS arm64·Node.js 24.22.1에서 타입 검사·빌드·전체 테스트 91개를 통과했습니다. 실제 SQLite로 배정·완료의 원자성, 두 연결의 중복 시작 방지, 기존 작업 보존 마이그레이션, 이벤트·결과 제한, API 조회를 확인했습니다. 실제 ChatGPT 인증을 사용한 예제 분석에서 결과·사용량·세션·이벤트 저장과 API 조회, 대상 파일 불변을 확인했습니다. 동일 인증 폴더로 작업 두 건을 순차 실행해 자동 생성된 기본 스킬 폴더가 다음 실행을 막지 않는 것도 확인했습니다. 작업 폴더 안의 DB를 외부 심볼릭 링크 경로로 지정해도 AI 호출 전에 거부하는지 확인했습니다. 모델이 거부 동작을 직접 시도한 것은 아니므로, 별도로 같은 CLI 버전의 샌드박스에 명령을 보내 지정 파일 읽기 성공과 쓰기·폴더 밖 파일·인증 폴더 읽기 차단을 검증했습니다. 오류 분류·시간 초과·취소는 자동 테스트로 재현했습니다. Linux·AWS에서의 Codex 실행, 자식 명령 전체 종료·복구, 24시간 운영은 검증하지 않았습니다.

## 서버 내부 자동 대기열 적용 — 2026-11-03

**결정:** 기존 실행 모듈을 서버 내부의 순차 실행 루프에 연결했습니다. 의존성 버전 변경이나 별도 큐 서버 추가 없이, `EXECUTION_CONFIG`로 명시적으로 켜고 `GET /execution`에서 현재 서버의 실행 상태를 조회합니다.

| 선택 | 이유·대안과 감수하는 점 |
| --- | --- |
| SQLite 작업 목록과 1초 대기 확인 | 현재는 동시 Run 하나이므로 Redis·외부 작업 큐가 필요한 처리량이 아님. 새 작업을 발견하기까지 최대 대기 확인 간격만큼 지연될 수 있음 |
| 작업 선택과 Run 생성을 한 트랜잭션으로 처리 | 먼저 읽고 나중에 실행 상태를 쓰는 사이의 중복 선택을 방지. 상태·등록 시각·ID 인덱스로 순서대로 선택 |
| 명시적으로 연결한 작업 공간만 자동 처리 | 미등록 폴더의 작업은 대기로 남기고 건너뜀. 실행 환경 검사에서 문제가 발견되면 새 Run을 만들지 않고 현재 서버 전체의 배정 보류 |
| DB에 실행 프로세스 소유권 저장 | 다른 자동 실행 서버·수동 CLI가 동시에 같은 DB의 실행을 맡지 못하게 함. 조회 전용 서버는 계속 사용 가능 |
| 시간만으로 잠금을 만료하지 않음 | 느려진 서버를 죽은 것으로 오인해 중복 실행하는 문제 방지. 부모 PID 재사용·권한 부족·호스트 변경이면 보수적으로 시작 거부 |
| HTTP 수신 시작 후 루프 시작, 종료 시 루프 먼저 중지 | 포트 충돌로 시작하지 못한 서버가 AI를 호출하지 않음. DB 연결을 닫기 전에 현재 실행 상태 저장 |

실행 소유권은 같은 호스트·같은 PID 공간의 로컬 실행을 전제로 합니다. 기존 부모가 사라졌다고 확인해 소유권을 교체해도 미완료 Run은 유지합니다. 부모 종료는 자식 명령 전체 종료의 증거가 아니며, 실제 종료·결과를 확인해 보류를 해제하는 복구는 다음 단위입니다. 시간 기반 잠금·외부 큐·분산 실행 권한은 여러 실행 서버가 필요한 시점에 다시 검토합니다.

자동 대기 중에는 AI를 호출하지 않습니다. 설정 파일의 값은 시작 시 읽고, 인증 파일·작업 폴더·프로젝트의 추가 설정 유무는 매 호출 전에 다시 확인합니다. 원격 인증 실패나 사용 한도가 Run에 저장되면 설정 파일이 정상이어도 다음 호출을 막습니다. 일시적 DB·파일 검사 오류와 제공자가 반환한 보류를 구분합니다.

실제 반복 실행에서 Codex가 인증 폴더 안에 플러그인 캐시를 생성하는 것을 확인했습니다. 캐시 디렉터리 존재만으로 사용자 설정이라고 판단하면 정상적인 후속 실행·서버 재시작도 막힙니다. SDK가 만드는 `plugins/cache`와 `plugins/.remote-plugin-install-staging`은 허용하고, `plugins`·`remote_plugin`·`plugin_discovery_prefetch` 기능은 명시적으로 끕니다. 플러그인 설정과 원격 카탈로그의 동작은 [공식 설정 문서](https://learn.chatgpt.com/docs/config-file/config-reference)와 설치된 CLI 0.166.0의 기능 목록을 대조했습니다. 플러그인은 비활성화 상태에서도 파일 갱신이 발생할 수 있으므로 캐시와 활성 설정을 구분합니다. [공식 플러그인 문서](https://developers.openai.com/plugins/build/plugins)

**검증:** macOS arm64·Node.js 24.22.1에서 타입 검사·빌드·전체 테스트 110개를 통과했습니다. 실제 SQLite로 순서·설정 대상 필터·원자적 배정·실행 소유권·보류·종료 상태 저장을 확인했습니다. 빌드한 서버에 HTTP로 작업 두 건을 등록해 실제 `gpt-6.1-sol / medium` 분석·결과 조회·대상 파일 불변·순차 실행을 확인했습니다. 중복 자동 서버와 수동 CLI는 거부됐고, SIGTERM·SIGINT 종료 후 재시작해도 완료 작업은 다시 실행되지 않았습니다. SDK 캐시가 있는 인증 폴더에서도 재시작을 확인했습니다. 별도 AI 호출 없는 대기 실행을 SIGKILL로 종료한 뒤 새 서버가 미완료 Run을 유지하고 다음 작업을 실행하지 않는 것도 확인했습니다. 자식 명령 전체 종료·복구, Linux·AWS·24시간 운영은 검증하지 않았습니다.

### 중단 대기와 오류 진단 보완

SDK에 중단을 요청하는 것만으로는 호출 대기가 끝난다고 보장할 수 없습니다. 분석 결과와 중단 신호를 `Promise.race`로 함께 기다려 중단 후에는 `interrupted`를 저장하도록 했습니다. 중단 순간부터 이벤트 저장을 차단하고 늦은 결과·실패도 기존 상태를 변경하지 않습니다. 실제 실행 프로세스 종료 확인을 대신하는 방법은 아니므로 Run의 보류와 신규 실행 차단은 유지합니다.

부모 종료 제한은 HTTP·DB가 닫힌 뒤에도 유지합니다. SDK가 프로세스를 붙잡고 있으면 10초 뒤 부모 서버·CLI를 종료하고, 정상 종료 시에는 이 타이머가 종료를 지연시키지 않도록 `unref`를 사용합니다. 실행 중인 자식 명령 전체의 종료를 보장하거나 보류를 자동 해제하지 않습니다.

오류 원문 전체를 로그로 남기면 인증 정보·경로·SQL이 포함될 수 있습니다. 대기열은 실패한 단계, 허용 목록에 있는 오류 코드·고정된 설명, 관련 Run·Task ID, 누적 발생 횟수만 기록합니다. OS·SQLite 오류와 설정 정책 위반을 구분하고, 알 수 없는 원인은 `UNKNOWN_ERROR`로 남깁니다. 원문·스택을 제외하므로 미분류 오류의 상세 진단에는 재현과 코드 확인이 필요하다는 비용을 감수합니다.

동일 단계·실행·오류 코드는 최초와 이후 1분 간격으로 기록합니다. 실패했던 단계가 다시 정상 처리될 때 복구 확인 로그를 한 번 남기며, 단순 조회 성공으로 실패한 실행 결과 저장까지 복구됐다고 표시하지 않습니다.

**보완 검증:** 전체 테스트 117개·타입 검사·빌드 통과. 실제 SQLite로 중단 신호를 무시하는 실행의 보류 기록, DB를 닫은 뒤 오는 이벤트 무시, 늦은 성공·실패가 상태를 바꾸지 않는 것을 확인했습니다. 진단 코드의 민감 정보 제외, 반복 기록 제한, 서버 로거 연결도 검증했습니다. 응답하지 않는 SDK 대역을 넣은 빌드 결과의 별도 서버·CLI 프로세스에서 기록 저장 후 10초 유예 종료를 확인했고, 일반 서버의 정상 종료가 10초를 기다리지 않는 것도 확인했습니다. ## 단일 사용자 인증 — 2026-11-03

**선택:** Fastify 공식 쿠키·세션·CSRF·요청 제한 플러그인을 사용하고, 세션 저장소를 기존 SQLite에 연결합니다. 고정 버전은 `@fastify/cookie 11.1.5`, `@fastify/session 11.1.6`, `@fastify/csrf-protection 8.0.2`, `@fastify/rate-limit 11.2.1`입니다. 설치한 코드의 Fastify 5 호환 범위와 저장소 계약을 확인했습니다.

| 대안 | 판단 |
| --- | --- |
| 서버 세션 + SQLite | 선택. 로그아웃·재로그인으로 이전 세션을 폐기하고 재시작 후에도 상태 유지 |

| JWT·외부 로그인 제공자 | 여러 사용자·서비스 연동의 대안. 현재 단일 사용자 요구에는 설정·키 관리 범위가 커짐 |

현재 [세션 플러그인](https://github.com/fastify/session)은 저장소에 버전을 대조하는 원자적 `compareAndSet`을 요구합니다. SQLite 갱신 조건에 이를 적용해 로그아웃한 세션을 뒤늦은 요청이 되살리지 못하게 합니다. [CSRF 플러그인](https://github.com/fastify/csrf-protection)의 세션 연결 방식을 쓰고 변경 요청의 토큰을 헤더에서 받습니다. Host·Origin 검사와 SameSite 쿠키도 함께 적용합니다.

비밀번호에는 Node의 비동기 scrypt를 사용합니다. [OWASP의 메모리·계산량 조합](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt) 중 N=2^15, r=8, p=3을 선택해 메모리를 약 32 MiB로 제한합니다. 별도 네이티브 암호 패키지를 추가하지 않으며 계산 중 HTTP 흐름을 동기적으로 막지 않습니다. Argon2id는 향후 인증 요구와 런타임 지원을 재검토할 때의 대안입니다.

공개 가입·기본 비밀번호·비밀번호 찾기는 추가하지 않습니다. 소유자가 로컬 설정 명령으로 비공개 파일을 만들고, 변경 시 새 설정으로 재시작합니다. 인증 없는 기존 curl 개발 흐름은 명시적인 로컬 API 모드로 남기며, 아무 설정 없이 시작해 인증이 빠지는 동작은 거부합니다.

**검증:** 세션·CSRF·로그아웃·재시작·절대 만료·동시 갱신 버전·저장 실패와 설정 파일 권한을 테스트했습니다. 실제 별도 서버의 HTTP 로그인·작업 관리 API·로그아웃, 초기 설정의 표준 입력·원문 미저장·덮어쓰기 거부를 확인했습니다. HTTPS 쿠키는 신뢰한 프록시와 신뢰하지 않은 요청을 구분해 검증했으며 원격 TLS 배포는 하지 않았습니다.

## 제한을 보존하는 자동 복구 — 2026-11-03

**선택:** 기존 단일 실행 루프가 SQLite에 저장된 정책·다음 시도 시각을 확인합니다. 종료 관측은 기존 복구 접수를 재사용하고, 실제 새 Run은 정상 배정 트랜잭션에서만 만듭니다. 추가 실행 서버나 큐 라이브러리는 도입하지 않았습니다.

정책은 Task에 한 번 저장하고 새 설정으로 기존 제한을 초기화하지 않습니다. 재시도 예약과 횟수 소비를 나누고, 수동 재개에도 같은 제한을 적용합니다. Run별 합산 시간을 보존해 복구 요청 재전송으로 시간이 이중 계산되지 않게 했습니다. 연속 오류는 완료 저장 때 갱신하므로 자동 루프보다 먼저 들어온 수동 요청도 최신 값을 확인합니다.

자동 복구는 명시적으로 켜며 종료 관측 기능을 요구합니다. 첫 단위의 오류 대상은 일시 연결 오류·서버 종료·소유자 상실입니다. 종료 근거가 없는 실행에 무한 중단 요청을 보내지 않고 한 번 대조한 뒤 보류합니다. 사용 한도는 기존 ProviderGate로 계속 차단하며 아래 계정 확인 정책으로 자동 회복을 검사합니다.

**검증:** 실제 SQLite·HTTP에서 재시작·상한·취소·정책 보존·계정 차단·저장 실패를 확인합니다. 실제 Docker에서는 서버 SIGKILL 뒤 자동 종료 대조와 두 번째 실행, runner의 일시 오류 전달·재시도를 확인합니다. 오류·모델은 대역을 사용하며 실제 계정 한도를 소진하지 않습니다.

**검증 범위:** 실제 로컬 HTTP 서버·SQLite·Chromium으로 정상 대기·오래된 응답·수집 실패·시간 초과·잘못된 형식·큰 응답·리다이렉트 거부·인증 문자열 제거·재시작·보관 제한·설정 변경을 검증합니다. AI 보류·취소 중 관측 지속, 느린 조회 중 API 응답과 종료를 확인합니다. 실제 트레이딩 서비스 연결이나 원격 배포를 검증했다는 뜻은 아닙니다.

## 관리 화면과 공통 API 형식 — 2026-11-03

**선택:** React로 로그인·프로젝트·작업·실행 기록 화면을 구성하고 Vite로 빌드합니다. Fastify가 빌드 결과와 API를 같은 주소에서 제공합니다. 화면을 위한 별도 운영 서버, 전역 상태 관리 제품, 페이지 라우터는 현재 넣지 않습니다.

| 대안 | 판단 |
| --- | --- |
| React + Vite | 선택. 기존 Fastify API를 사용하면서 상태별 화면과 입력을 컴포넌트로 나눌 수 있음 |
| Next.js 등 전체 웹 프레임워크 | 서버 렌더링·라우팅·데이터 처리가 통합돼 있지만 현재 로그인한 한 사람의 관리 화면에는 별도 서버 책임이 겹침 |
| Vue·Svelte | 상태 기반 화면을 만드는 충분한 대안. React보다 불가능한 기능이 있어서 제외한 것은 아니며 기존 설계와 학습 범위를 유지 |
| 직접 DOM 조작 또는 서버 HTML | 초기 파일 수는 줄지만 폴링·선택 변경·취소 접수·오류 상태가 늘수록 화면 갱신 규칙을 직접 관리해야 함 |

[React 공식 문서](https://react.dev/learn/build-a-react-app-from-scratch)는 직접 구성할 때 라우팅·데이터 처리 등의 책임이 생기는 점을 설명합니다. 현재는 단일 관리 화면으로 범위를 제한하며 공개 콘텐츠·SEO·서버 렌더링이나 다수 페이지가 필요해지면 프레임워크를 재검토합니다. [Vite](https://vite.dev/guide/)는 정적 파일 빌드에 사용하고, [Fastify Static](https://github.com/fastify/fastify-static)으로 제공합니다. 개발 중에도 빌드 감지 + 브라우저 새로고침을 사용해 로그인 Origin을 하나로 유지합니다. 즉시 화면 갱신(HMR) 편의는 현재 포기한 부분입니다.

**공통 형식:** TypeBox로 JSON Schema와 TypeScript 타입을 함께 정의합니다. Fastify는 같은 스키마로 요청·응답을 처리하고 브라우저는 응답을 받은 뒤 실제 값을 검사합니다. [TypeBox](https://github.com/sinclairzx81/typebox)의 JSON Schema 기반 방식을 사용하되 설치 패키지는 검증한 `@sinclair/typebox` 0.34.52입니다. 이름이 다른 후속 `typebox` 패키지로 자동 전환하지 않습니다.

| 대안 | 판단 |
| --- | --- |
| TypeScript 타입만 공유 | 빌드 이후 서버에서 잘못된 응답을 받아도 잡지 못함 |
| JSON Schema와 타입을 각각 수동 작성 | 라이브러리는 줄지만 상태·날짜·필드 변경 때 두 정의가 어긋날 수 있음 |
| Zod + JSON Schema 변환 | 입력 조합이 복잡하면 유용하지만 현재는 기존 Fastify JSON Schema를 그대로 공유하는 편이 단순함 |
| OpenAPI 생성·클라이언트 코드 생성 | 외부 소비자나 다언어 클라이언트가 늘면 재검토. 현재 두 TS 패키지에는 생성 파이프라인을 먼저 추가하지 않음 |

React·React DOM 19.3.1, 타입 정의 19.3.0, Vite 8.3.5, React 플러그인 6.1.2, TypeBox 0.34.52, Fastify Static 10.1.8을 고정했습니다. 당일 배포된 React 플러그인 대신 기존 설치 대기 정책을 만족하는 버전을 선택했고 예외 목록은 추가하지 않았습니다. Node 24.22.1에서 타입 검사·빌드·실제 브라우저 동작을 확인했습니다.

화면 흐름은 [Playwright의 테스트 서버 기능](https://playwright.dev/docs/test-webserver)을 사용합니다. 이미 검증한 Chromium과 맞는 Playwright 1.62.1을 고정했으며 최신 릴리스라는 뜻은 아닙니다. 테스트 서버는 임시 DB·인증과 AI 대역을 사용하고 기존 서버를 재사용하지 않습니다. 별도 실제 Codex 호출로 분석 결과·취소·종료 확인도 검증했습니다. 자동 테스트가 실제 AI 품질이나 원격 TLS 배포까지 증명하지는 않습니다.

**재검토 조건:** 화면이 늘면 라우팅과 서버 상태 캐시, 여러 사용자가 상태를 함께 보면 SSE, API가 외부에 공개되면 계약 버전과 OpenAPI를 검토합니다. 지금은 실패 시 마지막 기록 보존·요청 취소·선택이 바뀐 뒤 늦은 응답 무시·요청 키 유지에 필요한 작은 코드만 둡니다.

## 복구 요청을 먼저 저장하는 API — 2026-11-03

**선택:** 재개·상태 확인·취소를 `RecoveryRequest`로 먼저 저장하고 HTTP 응답은 접수 기록을 반환합니다. 실행 루프가 접수를 읽어 이전 컨테이너를 관측한 뒤, 짧은 트랜잭션에서 조건을 다시 검사합니다. 같은 요청 키는 같은 기록으로 연결하고 처리 중 서버가 종료돼도 접수가 남습니다.

| 대안 | 판단 |
| --- | --- |
| HTTP 요청 안에서 관측·재개를 끝내기 | 응답 유실·연결 종료와 복구 진행을 구별하기 어렵고 오래 걸리는 관측에 요청이 묶임 |
| 메모리에서만 비동기 처리 | 응답은 빠르지만 서버 종료 시 접수와 처리 결과가 사라짐 |
| DB에 접수 후 기존 실행 루프가 처리 | 선택. 접수·상태 테이블은 추가하지만 새 큐 제품이나 별도 서버 없이 재시작·중복 요청을 처리 |

`requestKey`는 작업별 중복 방지, `runId`는 요청자가 확인한 최근 실행, `providerGateVersion`은 확인한 차단 조건을 뜻합니다. 접수와 최종 저장에서 다시 검사하므로 관측 중 들어온 취소나 새 차단이 오래된 요청으로 덮어써지지 않습니다. 취소는 진행 중인 재개 접수를 거부한 뒤 먼저 기록합니다. 종료 근거를 저장하지 못한 경우 컨테이너를 정리하지 않고 접수도 pending으로 보존합니다.

이전 Run은 그대로 남고 재개는 Task를 queued로 전환합니다. 새 Run 생성은 기존 원자적 배정 한곳에서만 수행합니다. 종료·결과 확정의 공통 저장 함수를 공유하되 과거 오류를 다시 기록해 제공자 차단 버전을 불필요하게 올리지 않습니다. 중단된 확인 실행을 정리해 버전이 바뀌면 최신 버전으로 새 요청을 받습니다.

**검증:** 전체 테스트 177개·타입 검사·빌드, 실제 HTTP·SQLite·Docker 강제 종료 후 복구. 별도 실제 Codex로 서버 종료 후 수동 재개와 2번째 분석 성공을 확인했습니다. 종료 불명확·8초 관측 초과·모호한 구버전 중단·저장 실패는 해제하지 않습니다. 관측 대기 중 HTTP 응답을 확인했으며 장시간 부하 성능을 측정한 것은 아닙니다.

## 취소 상태와 실행 시도 순서 — 2026-11-03

**선택:** 종료 근거가 확인된 뒤 사용자 취소·시간 초과·서버 종료를 서로 다른 상태로 확정합니다. Task의 취소 의도를 배정·완료 시 다시 확인하며, `queued`로 바뀌었다는 이유만으로 취소를 지우지 않습니다. 같은 작업의 최근 실행은 시각 대신 증가하는 `attempt`로 구분합니다. 서버 시계 변화나 같은 밀리초에 생성한 실행을 UUID 순서로 비교하는 대안은 실행 순서를 보장하지 못합니다.

기존 Task의 상태 제약을 바꾸는 자동 생성 SQL은 테이블을 교체하며 `foreign_keys=OFF`를 사용합니다. 그러나 [SQLite는 트랜잭션 안에서 이 설정을 변경하지 않습니다](https://www.sqlite.org/pragma.html#pragma_foreign_keys). 실제 참조 이력이 있는 DB로 재현했고, Drizzle의 트랜잭션을 유지하면서 참조 검사를 잠시 지연하는 방식으로 SQL을 보완했습니다.

마지막에 전체 `foreign_key_check`의 위반 수가 0인지 SQL 제약으로 검사합니다. 통과한 뒤에만 교체 전 테이블에 대한 지연 검사 기록을 초기화합니다. [지연 검사를 끄는 것만으로는 무결성이 보장되지 않으므로](https://www.sqlite.org/pragma.html#pragma_defer_foreign_keys) 이 검사는 생략하지 않습니다. Run·Step·이벤트·차단 예약이 있는 DB의 업그레이드와, 부모 행이 빠진 잘못된 변경의 전체 롤백을 모두 테스트했습니다. 애플리케이션의 외래 키 강제 검사는 계속 켜 둡니다.

**검증:** 전체 테스트 153개, 타입 검사·빌드. 실제 컨테이너에서 사용자 취소의 종료·`cancelled` 확정, SQLite에서 시계 역행·취소 재배정 차단·기존 참조 보존·검사 실패 시 원복을 확인했습니다. 이 단위 뒤에 수동 복구 API를 연결했으며 검증은 위 절에 기록합니다.

## 제공자 차단과 확인 실행 — 2026-11-03

**선택:** 과거 Run의 상태를 전역 잠금처럼 사용하는 방식에서, 종료 미확인 실행과 제공자 차단을 분리합니다. `ProviderGate`에 현재 사유·버전·제공된 시각·확인 실행 예약을 저장합니다. 단일 계정인 현재 단계에서는 Codex 로그인 전체에 적용하며, 계정 식별을 확인하지 못한 상태에서 인증 폴더마다 별도 계정이라고 가정하지 않습니다. 공통 실행 설정 오류도 같은 범위에서 차단해 다음 작업을 연속 실패시키지 않습니다.

한도 시각이 지나면 바로 차단을 해제하는 대안은 실제 회복을 확인하지 못합니다. 대신 명시적으로 예약한 작업 하나만 확인 실행으로 배정하고, 성공·종료 근거 저장과 함께 해당 버전의 차단을 풉니다. 일반 작업을 모두 다시 배정하거나 오래된 확인 결과로 새 차단을 해제하지 않습니다. 실패·중단·저장 오류는 차단을 유지합니다. 자동 예약·대기 간격 계산은 4단계입니다.

고정 SDK 0.166.0의 오류 계약에는 `message`만 있고 재시도 시각 필드가 없습니다. 시간대가 포함된 절대 시각을 오류 메시지에서 확인한 경우에만 `retryAt`을 기록합니다. 자연어·현지 시각을 임의 해석하지 않습니다. 실제 사용 한도 응답의 시각 제공은 아직 검증하지 않았고 테스트는 오류 대역과 컨테이너 runner를 사용합니다.

실제 연결 실패 실험에서 재연결 이벤트도 `error`로 도착했습니다. 뒤이어 정상 완료된 호출을 실패로 남기지 않도록 일시적 스트림 오류와 최종 실패·금지된 도구 실행을 구분했습니다. 이후 성공이 있어도 접근 정책 위반은 무시하지 않습니다.

**검증:** 실제 SQLite에서 차단 보존·동시 예약 거부·과거 Run 보존·시각 경계·늦은 응답 거부·원자적 저장·마이그레이션을 확인했습니다. 별도 실제 컨테이너의 모의 한도 응답으로 재시도 시각이 부모와 DB까지 전달되는지도 확인했습니다. 실제 계정에 한도 오류를 일으키거나 인증을 만료시키는 실험은 하지 않았습니다.

## 실행 전체의 종료 확인 — 2026-11-03

**선택:** 기존 직접 SDK 실행을 유지하고, `containerImage`를 지정하면 Run별 로컬 Docker 컨테이너 안에서 같은 SDK 어댑터를 실행합니다. 총괄·DB·대기열은 기존 서버가 소유합니다. 원격 작업 서버나 Kubernetes는 추가하지 않습니다.

설계 검토에서는 관리 대상 Node 자식 프로세스로 SDK를 감싸는 안을 먼저 선택했습니다. 하지만 고정 SDK 0.166.0에 모의 CLI를 연결한 실제 OS 실험에서 정상 응답·AbortError 후 모두 별도 프로세스 그룹의 손자가 살아남았습니다. 부모 종료·그룹 신호만으로 전체 종료를 증명할 수 없어 이 부분을 변경했습니다.

| 대안 | 판단 |
| --- | --- |
| 부모 PID·프로세스 그룹 확인 | 그룹을 벗어난 명령을 놓칠 수 있어 복구 근거로 사용하지 않음 |
| OS별 네이티브 프로세스 추적 | macOS·Linux에 별도 추적 구현이 필요하고 자식 생성 경합 검증 부담이 큼 |
| SDK를 Run 전용 컨테이너에서 실행 | 전체 프로세스 공간의 수명을 확인할 수 있어 선택. Docker 준비·이미지 빌드 비용을 감수 |
| CLI를 직접 실행 | SDK 호환 책임이 늘고 같은 프로세스 추적 문제도 남아 미선택 |

[Linux PID namespace](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)의 init 종료 시 하위 프로세스 종료 규칙을 사용합니다. [Docker 실행 설정](https://docs.docker.com/reference/cli/docker/container/run/)에서 호스트 PID 공간·특권 모드를 사용하지 않고 재시작 정책도 끕니다. 임의 토큰·전체 컨테이너 ID·엔진 ID가 일치하는 실행만 중단합니다. PID 재사용을 이유로 호스트 프로세스에 신호를 보내지 않습니다.

아직 시작하지 않은 컨테이너도 `created` 조회만으로 완료 처리하지 않습니다. 전체 ID 삭제가 성공해야 지연된 시작 요청을 차단한 것으로 판단합니다. 이미 실행한 컨테이너는 종료 근거 저장 후 제거합니다. 관측·저장 실패 때는 보류가 남을 수 있지만 근거 없이 재개하지 않습니다.

기본 직접 실행은 Docker 없이 사용할 수 있지만 종료 증명을 제공하지 않습니다. 자동 복구가 필요한 환경은 컨테이너 실행을 준비해야 합니다. 컨테이너의 일반 사용자 실행은 SDK의 Linux sandbox도 동작하게 하며 관리자 권한이나 샌드박스 해제가 필요하지 않습니다. 이미지에는 시스템 CA 인증서를 설치해 SDK의 HTTPS 인증서 검증을 유지합니다.

**검증:** macOS arm64·Docker Desktop의 Linux arm64 엔진에서 실제 프로세스의 정상 종료, 분리된 손자, SIGTERM 무시, 호스트 SIGKILL, 잘못된 식별자, 늦은 시작 요청을 재현했습니다. 실제 SQLite로 실행 식별자 보존·교체 거부·완료 저장 실패 시 정리 금지까지 확인했습니다. 이 테스트의 runner는 모델을 호출하지 않습니다. 실제 SDK 검증과 Linux 호스트·AWS 운영 검증은 별도로 기록합니다.

### 여러 컨테이너를 순차 실행할 때의 종료 기록 — 2026-11-03

**선택:** Run의 단일 실행 식별자를 `run_executions` 테이블로 옮깁니다. 각 행은 컨테이너 전체 ID·소유 토큰·엔진 ID·순서·종료 확인 시각을 보존합니다. 이전 행의 종료가 확인되기 전에는 새 행을 만들 수 없도록 DB 제약도 적용합니다. 기존 열은 데이터 이전 후 제거해 식별자의 저장 기준을 하나로 유지합니다.

| 대안 | 판단 |
| --- | --- |
| Run의 식별자를 마지막 컨테이너로 교체 | 앞선 실행의 종료·복구 근거가 사라져 제외 |
| Run 안의 JSON 배열 | 개별 종료 갱신과 미확인 실행 하나 제약을 앱 코드에만 의존하므로 제외 |
| 개별 실행 테이블 | 기존 결과·복구 이력을 보존하고 DB가 순서·단일 미확인 실행을 강제할 수 있어 선택 |

부모가 비동기 저장을 끝냈다는 확인 뒤에만 Docker를 시작합니다. 단계 종료와 취소가 겹치면 진행 중인 관측을 공유하고, 전체 종료 확인을 시작한 뒤에는 새 단계를 만들지 않습니다. 자식이 보내는 종료 시각·식별자는 저장하지 않습니다. 복구는 저장된 과거 종료 근거를 재사용하되 관측한 실행 목록이 달라지면 보류합니다. Run당 12개 상한은 자원 기록의 무한 증가를 막는 장치이며 AI Step·재시도 예산은 별도로 유지합니다.

이 단위는 기존 읽기 전용 실행을 유지하면서 다단계 개발에 필요한 수명 관리를 준비합니다. 실제 코드 변경·인증 없는 테스트·별도 검토 연결은 다음 구현입니다.

**검증:** SQLite 이전 데이터 보존·순서 제약·저장 실패·복구 관측 목록 변경과 실제 Docker의 두 단계 실행·저장 확인 대기·늦은 시작 차단·동시 종료 관측을 확인했습니다. 전체 테스트 585개(실제 Docker 26개)와 Chromium 11개·타입 검사·빌드를 통과했습니다. 이 단위에서는 실제 AI를 호출하지 않았습니다.

## 중단 요청 근거 저장 — 2026-11-03

**결정:** 중단 신호를 보내기 전에 Run의 사유·요청 시각을 짧은 트랜잭션으로 저장합니다. 사용자 취소는 Task에도 시각을 남깁니다. 부모 종료와 실제 실행 종료 확인은 구분해 `terminationConfirmedAt`을 별도로 두며, 아직 관측하지 않은 값을 채우지 않습니다.

메모리에만 사유를 남기는 대안은 재시작 때 정보가 사라집니다. 모든 중단을 `cancel_requested`로 처리하는 기존 방식은 사용자 취소와 서버 종료를 구별하지 못해 복구 판단에 쓰기 어렵습니다. 처음 저장한 사유를 보존하고, 이전 버전의 모호한 기록은 `unknown`으로 옮깁니다. 이력의 실제 요청 시각은 추정하지 않습니다.

DB가 중단 요청을 저장하지 못하면 신호 전송까지 막지 않습니다. 실행에는 중단을 요청하고 호출자에게 저장 오류를 전달하며 기존 활성 Run을 남겨 새 배정을 차단합니다. 오류를 숨기고 취소 완료로 표시하는 방식은 선택하지 않았습니다.

**검증:** Node.js 24.22.1·macOS arm64에서 테스트 123개·타입 검사·빌드 통과. 실제 SQLite로 요청 저장 순서·첫 사유 보존·저장 실패의 원자적 취소·구버전 이력 보존을 검증했습니다. 종료 확인이나 실제 SDK 취소 검증이 완료됐다는 뜻은 아닙니다.

## 자율 운영 범위 정정 — 2026-10-28

기존 문서는 자동 작업 생성·개발·상호 검토를 후속 기능으로 미루고, 첫 버전을 수동으로 등록한 분석 작업의 실행·복구로 제한했습니다. 이는 사용자가 의도한 “부재중에도 스스로 일을 찾고 개선하는 시스템”을 충족하지 못해 정정합니다.

첫 운영 버전에는 목표 기반 작업 생성, 개발용 작업 공간의 코드 수정, 역할 간 검증·재작업, 다음 작업 선택을 포함합니다. 수동·읽기 전용 실행은 연동 검증 단계로 남깁니다. 기존 기술 선택은 유지하며, 목표·계획 기록과 반복 제어를 추가합니다. 여러 역할의 순차 협업으로 시작하므로 병렬 실행을 위해 별도 서버를 먼저 도입하지 않습니다.

**감수하는 점:** 초기 범위가 커집니다. 목표 달성 판단, 반복 작업 방지, 변경 축적과 검증, 프로젝트별 기간 예산을 구현해야 합니다. 동작 범위를 단계별로 검증하되 자율 작업 기능을 MVP 밖으로 다시 미루지 않습니다. 개발 순서는 [구현 계획](02-implementation-plan.md)을 따릅니다.


## 최초 호출의 추론 강도 선택 — 2026-11-03

**선택:** 기존 고정 medium을 기본으로 보존하고 `effortPolicy`로 자동 선택을 켭니다. 작업 지시의 단서를 순수 함수로 판단해 medium/high/xhigh 중 선택하고 설정 상한을 적용합니다. Run에는 정책, Step에는 적용 값·이유·정책 버전을 저장하며 화면에도 같은 값을 표시합니다.

| 대안 | 판단 |
| --- | --- |
| 모든 작업 xhigh | 간단하지만 단순 작업에도 시간·사용량을 소비하므로 기본값으로 채택하지 않음 |
| 별도 AI 난도 분류 호출 | 의미를 폭넓게 해석할 수 있지만 호출·복구 부담을 늘리므로 초기에는 미채택 |
| 지시문 단서와 명시적 상한 | 선택 근거를 재현하고 AI 없이 검증할 수 있어 초기 정책으로 채택. 단어만으로 실제 난도를 완벽하게 구분하지 못함 |

고정 SDK 0.166.0의 `ThreadOptions.modelReasoningEffort`에 실제 선택값을 전달합니다. `TurnOptions`에는 effort 항목이 없어 아래 다단계 구현에서는 값을 바꿀 때 새 세션에 필요한 맥락을 전달합니다. SDK의 전체 허용 목록과 이 프로젝트의 medium/high/xhigh 범위를 구분합니다. 계정·연결 오류를 이유로 추론 강도를 자동 상향하지 않습니다.

실제 예제 검증 중 Linux 읽기 전용 권한이 `/app` 아래의 Codex 자체 실행 파일을 숨겨 도구 명령이 실패하는 문제를 찾았습니다. 고정 버전의 네이티브 실행 묶음을 이미지의 `/usr/local/lib/codex`에 설치하고 SDK 실행 경로를 명시했습니다. 명령 환경에는 PATH만 명시적으로 전달하며 인증 폴더 차단과 네트워크 제한은 유지합니다. 실제 분석 이미지를 사용하는 회귀 테스트로 실행 파일·rg·프로젝트 읽기 성공, 쓰기·인증·폴더 밖 읽기·통신 차단을 확인합니다. 분석문 반환 성공만으로 파일을 실제로 읽었다고 판단하지 않고, 별도 예제의 정답까지 대조합니다.

실제 예제 1회씩의 측정값은 medium 12.2초·입력 46,832/캐시 44,160/출력 271토큰, high 12.4초·46,951/44,160/331, xhigh 18.4초·47,149/44,416/583입니다. 모두 계산 오류의 현재 값 190과 기대 값 180을 확인했습니다. SDK가 보고한 사용량이며 과금액·남은 구독 한도를 뜻하지 않습니다. 이 작은 표본으로 일반적인 품질 우열을 결론내리지는 않습니다. 전체 테스트 279개(실제 Docker 12개)·Chromium 5개·타입 검사·빌드를 통과했습니다.


## 같은 실행 안의 제한된 분석 단계 — 2026-11-03

**선택:** `analysisWorkflow`를 명시한 실행만 여러 Step으로 분석합니다. 한 Run·한 컨테이너를 유지하고 내부에서 새로운 SDK 세션을 순차 생성합니다. 앞선 보고서·근거·미해결 질문을 전달하고 effort를 다음 호출에 적용합니다. SDK의 구조화된 출력 기능과 서버의 별도 형식·순서 검사를 함께 사용합니다.

| 대안 | 판단 |
| --- | --- |
| 한 호출에서 모든 역할과 분석 처리 | 호출이 적고 단순하므로 기본값으로 유지. 호출 경계의 effort 변경·개별 기록은 불가능 |
| 같은 세션의 진행 중 effort 변경 | 고정 SDK의 TurnOptions에 해당 설정이 없어 채택하지 않음 |
| Step마다 별도 Run·컨테이너 | 정상 단계와 재시도를 혼동하고 종료·예산 관리가 복잡해져 미채택 |
| 같은 Run에서 새 세션을 순차 실행 | 기존 전체 종료 확인·Run 제한 시간을 보존하면서 단계별 설정과 기록을 지원하므로 선택 |

다음 Step을 바로 시작하는 대신 부모 서버의 저장 확인 응답을 기다립니다. 부모가 저장된 이전 제안·정책으로 effort를 다시 계산하고 Step을 만든 뒤에만 확인합니다. 저장 실패·순서 오류·취소 시 다음 AI 호출을 막습니다. 마지막 결과가 완료되지 않으면 횟수·맥락 상한에서 작업을 보류하고 이전 결과는 보존합니다. 요청 하나의 타이머가 전체 흐름을 감싸므로 단계가 바뀌어도 Run·Task 시간 상한을 초기화하지 않습니다.

실제 `gpt-6.1-sol` 계산 예제에서 high → xhigh → medium의 서로 다른 세 세션을 같은 Run에 저장했습니다. 요구사항 확인 → 수치 검증 → 최종 요약을 이어받아 현재 190·기대 180을 설명했고, 약 40.4초와 입력 60,094/캐시 23,680/출력 898토큰을 기록했습니다. 파일 불변·전체 종료와 세션별 적용 effort도 확인했습니다. 앞선 단일 medium 약 12.2초와 같은 답을 얻었으며, 이 작은 예제에서는 추가 호출 비용만 늘었습니다. 복잡한 작업 전반의 품질 우열을 입증하는 측정은 아닙니다.

검증은 서버·화면 테스트 295개(실제 Docker 14개)·Chromium 6개·타입 검사·빌드를 통과했습니다. 별도 실제 Codex의 두 번째 세션 시작 시 취소하여 첫 보고서 보존·후속 호출 중지·전체 종료를 확인했습니다. 실제 계정 한도 소진·AWS·24시간 운영은 여전히 미확인입니다.


## 목표 정의와 변경 이력 — 2026-11-03

**선택:** Goal의 현재 상태와 `GoalRevision`의 버전별 전체 내용을 함께 저장합니다. 목표·완료 기준·허용 경로·예산 정책은 공통 형식으로 검사하고, 상태 변경과 이력 저장은 짧은 SQLite 트랜잭션에서 수행합니다. HTTP와 화면에서 같은 형식을 사용합니다.

| 대안 | 판단 |
| --- | --- |
| 현재 목표만 덮어쓰기 | 간단하지만 이전 기준과 오래된 계획을 대조할 근거가 사라져 미채택 |
| 모든 변경을 사건으로 저장하고 상태 복원 | 유연하지만 현재 규모에 비해 복원·재생 규칙이 복잡해 미채택 |
| 현재 상태와 버전별 전체 내용 저장 | 조회와 이력 확인이 단순하고 계획 버전 대조에 필요한 근거가 남아 채택 |

요청 키는 같은 변경의 재전송을 식별하고, 예상 버전은 동시에 열린 화면의 덮어쓰기를 막습니다. 정의는 공백·경로 순서를 정규화한 뒤 요청 내용의 해시와 비교합니다. 재전송에는 당시 응답을 반환하며 현재 상태를 되돌리지 않습니다. 상태·이력 중 하나라도 저장에 실패하면 둘 다 취소합니다.

경로·예산은 이 단위에서 정의를 저장하고 검사합니다. 실제 접근 제한·예산 소비·계획 예약은 다음 단위에서 연결합니다. 목표 등록을 곧바로 자율 실행처럼 표시하지 않고 화면에도 현재 동작을 명시합니다. 현재 수동 분석은 Goal과 독립적이며 목표 일시정지로 취소되지 않습니다.

## 목표 범위의 읽기 전용 자료 준비 — 2026-11-03

| 별도 억제 해제 플래그만 저장하기 | 어떤 작업을 다시 허용했는지, 새 작업이 또 취소됐을 때 무엇을 막을지 모호해 미채택 |

목표 내용은 유지하되 버전을 올려 새 허용 의도를 기록합니다. 오래된 무진척 계획을 계속 재개하는 대신 현재 기준으로 계획할 수 있고, 진행 중인 이전 버전 결과는 적용하지 않습니다. 이 조작으로 다른 작업도 범위를 재검사하는 비용을 감수합니다. 별도 권한 세대 번호를 도입하는 대안은 상태 기준이 늘어 현재는 선택하지 않았습니다.

취소 이력의 당시 정책과 소비량은 새 작업으로 이어집니다. 정책이 없던 과거 기록만 서버의 현재 기본 정책과 저장된 실행 이력으로 초기화합니다. Task별 Run 번호는 1부터 시작하되 전체 제한 판단에는 연결 이전의 실행도 포함합니다. 현재 기능은 취소한 계획 생성 작업에 한정하며, 실패·보류는 기존 복구 절차를 따릅니다. 모델이 스스로 사용자 취소를 해제하는 기능은 제공하지 않습니다.

## 계획 제안의 보존과 작업 생성 — 2026-11-03

**선택:** Goal별 계획 예약을 SQLite에 저장하고, AI 제안을 Run에 먼저 보존한 뒤 종료·현재 목표·입력을 대조해 후속 Task와 함께 적용합니다. 계획은 기존 Run·Step·계정 차단·기간 예산 경로를 사용합니다. Codex에는 서버가 정한 응답 형식을 전달하며 읽기 전용 권한을 유지합니다.

| 대안 | 판단 |
| --- | --- |
| AI 응답에서 바로 작업 등록 API 호출 | 결과 일부만 저장되거나 재전송으로 중복 작업이 생길 수 있어 미채택 |
| 메모리에 제안을 두고 종료 뒤 한 번에 저장 | 완료 저장 직전 서버가 중단되면 받은 제안을 잃고 다시 호출해야 하므로 미채택 |
| 제안 보존 후 DB 트랜잭션으로 검증·적용 | 중단 뒤 같은 제안을 대조하고 중복 없이 반영할 수 있어 채택. 제안 저장과 적용 사이의 복구 절차가 필요 |
| 별도의 계획 전용 실행 서버 | 기존 종료 확인·취소·예산 규칙이 갈라지므로 현재 단위에서 추가하지 않음 |

경로 집합에서 문제 식별자를 만들고 같은 목표 버전·기준 커밋의 중복 작업을 억제합니다. 제목 해시만 사용하는 대안은 이름을 바꿔 취소와 제한을 우회할 수 있어 제외했습니다. 처음에는 미해결 작업이 있는 목표 전체를 보류했습니다. 이후 종료된 취소·실패 작업의 대상 경로가 겹치는 제안만 제외하도록 나누었습니다. 경로가 다른 문제는 계속 계획할 수 있지만, 같은 파일의 별개 문제까지 억제할 수 있다는 제약이 있습니다. 취소한 작업의 명시적 재허용은 연결된 새 작업과 이전 실행 제한을 함께 보존합니다.

한 계획의 작업 수는 최대 3개, 제안은 32KiB, 과거 작업은 최대 20개 발췌로 제한합니다. 같은 코드를 대상으로 중복 작업만 제안하는 판단이 세 번 이어지면 보류합니다. 이 수치는 초기 제한이며 실제 입력 크기·호출 시간과 유용한 작업 생성 비율을 보고 조정합니다. 다음 단계 개발 실행기가 연결되기 전에는 생성한 작업을 `development_pending`으로 보존합니다.

실제 Codex 연동에서 JSON Schema의 `uniqueItems`가 HTTP 400으로 거부되는 것을 확인했습니다. [공식 구조화 출력 문서](https://developers.openai.com/api/docs/guides/structured-outputs)의 지원 범위를 참고해 해당 키워드를 보내지 않고, 경로 중복·겹침은 서버가 직접 검사합니다. 수정한 응답 형식으로 실제 계획 생성·제안 저장·후속 작업 등록·원본 불변·전체 종료를 확인했습니다. 계획이 만든 작업의 실제 개발·테스트 수행을 검증한 것은 아닙니다.

## 계획의 서비스 관측 근거와 입력 크기 — 2026-11-03

**선택:** 관측 화면의 판정 함수를 계획에서도 사용하고, 프로젝트·현재 설정·설정 식별값으로 자료를 한정합니다. 서버의 실제 관측 활성 상태를 함께 확인하므로 재시작 뒤 오래된 성공을 정상으로 오해하지 않습니다. 계획은 저장된 관측을 읽으며 외부 수집은 기존 관측 루프가 담당합니다.

| 대안 | 판단 |
| --- | --- |
| 마지막 수집 성공만 전달 | 이후 실패·유효 기간 경과를 숨길 수 있어 미채택 |
| 모델이 상태 주소에 직접 접속 | 주소·인증 전달과 별도 접근 권한이 필요하므로 미채택 |
| 관측할 때마다 진행 중 계획 폐기 | 짧은 수집 주기에서 계획이 끝나지 못할 수 있어, 당시 근거를 보존하고 실제 변경 검증에서 효과를 확인하는 방식 선택 |
| Run에는 관측 ID만 보관 | 관측 보존 기간이 지나면 내용과 당시 판정을 복원하기 어려워, 실제 전달한 제한된 자료 자체를 함께 저장 |
| 고정 개수만 자르기 | 긴 한글·파일 경로·JSON 이스케이프 때문에 호출 크기를 넘길 수 있어, 전체 직렬화 크기 안에서 각 자료 종류에 번갈아 공간을 배분 |

목표와 권한 경로는 일부만 전달하지 않습니다. 필수 입력만으로 60,000바이트를 넘으면 보류하므로 큰 목표는 나누어야 한다는 제약이 있습니다. 생략한 선택 자료는 개수로 표시하고 서버의 전체 이력 검사와 구분합니다. Run마다 최대 수십 KiB의 입력 자료가 추가로 쌓이는 비용을 감수하며 장기 보관 정책은 운영 단계에서 다룹니다.

실제 로컬 HTTP 예제에서 계산 결과 102·153과 기대값 200·450의 차이를 관측한 뒤, Codex가 관측 ID를 인용하고 계산 수정·Node 테스트 작업을 생성하는 것을 확인했습니다. 원본 불변과 전체 종료도 확인했습니다. 생성된 코드의 실제 수정·검증이나 매매 전략 개선을 입증하는 실험은 아닙니다.

## 간접 의존성의 알려진 취약점 보완 — 2026-11-03

`pnpm audit --prod`에서 `@fastify/static → glob → minimatch` 경로의 보통 등급 취약점 2개를 확인했습니다. [minimatch 패턴 증폭 문제](https://github.com/advisories/GHSA-g3hv-75wg-m249)는 11.0.1, [glob 취소 뒤 탐색 지속 문제](https://github.com/advisories/GHSA-3g3m-2fjr-6pw4)는 14.0.2부터 수정됐습니다.

현재 화면 경로는 `@fastify/static`의 기본 wildcard 라우팅을 사용하므로 설치 코드의 glob 사전 탐색 분기는 사용하지 않습니다. 따라서 이번 점검이 실제 공격 경로를 재현한 것은 아닙니다. 다만 알려진 취약 버전을 남기지 않도록 해당 의존 경로에 한정해 glob 14.0.2와 minimatch 11.0.1을 고정했습니다. 직접 의존성 전체를 일괄 갱신하거나 정적 파일 서버를 새로 구현하지 않았습니다.

개발 의존성에는 Drizzle Kit의 설정 로더가 사용하는 esbuild 0.18.20의 [개발 서버 CORS 문제](https://github.com/evanw/esbuild/security/advisories/GHSA-67mh-4wv8-2f99)도 있었습니다. 이 프로젝트의 DB 변경 파일 생성은 해당 개발 서버를 열지 않습니다. `@esbuild-kit/core-utils` 경로에만 esbuild 0.25.12를 적용하고, 실제 `pnpm db:generate`가 기존 스키마를 읽어 불필요한 마이그레이션 없이 끝나는지 확인했습니다.

고정한 버전은 Node.js 24를 지원하며 `pnpm-workspace.yaml`의 제한적인 override와 잠금 파일에 기록했습니다. 상위 패키지가 수정된 버전을 공식 의존성으로 채택하면 override 제거를 검토합니다. 선언된 의존 범위를 바꾼 조치이므로 잠금 파일을 변경하지 않는 설치·타입 검사·테스트 317개(실제 Docker 14개)·화면 테스트 7개를 다시 검증했습니다. 수정 후 개발 도구를 포함한 `pnpm audit`의 보고된 취약점은 0개입니다. 알려지지 않은 취약점까지 없다는 뜻은 아닙니다.

## 공개 저장소의 자동 검사 — 2026-11-03

**선택:** GitHub가 제공하는 Ubuntu 22.04·24.04 실행 서버에서 기존 검증 명령을 실행합니다. 로컬 검사에만 의존하면 다른 환경의 실패와 PR의 회귀를 놓칠 수 있어 타입·빌드·SQLite·컨테이너·화면 검사를 연결했습니다. 별도의 테스트 프레임워크나 개인 서버는 추가하지 않습니다.

Node.js는 `.nvmrc`, pnpm은 `packageManager` 값을 읽고 `--frozen-lockfile`로 설치합니다. [checkout](https://github.com/actions/checkout)·[setup-node](https://github.com/actions/setup-node) 등 외부 Action은 전체 커밋 ID로 고정하며 저장소 권한은 읽기만 허용합니다. [Playwright의 CI 안내](https://playwright.dev/docs/ci-intro)에 따라 Chromium과 OS 의존성을 설치하고, 이미 빌드한 앱에 가짜 AI 실행기를 연결합니다. Docker 이미지를 먼저 빌드해 첫 다운로드 시간을 개별 테스트의 제한 시간과 분리합니다.

개인 인증을 가진 자체 실행 서버와 `pull_request_target`은 사용하지 않습니다. 컨테이너 테스트는 실제 CLI의 파일 권한 경계까지 검사하지만 모델을 호출하지 않습니다. 실제 계정·모델 품질·AWS 운영 검증은 계속 별도로 수행합니다. CI 구성 추가 자체를 원격 실행 성공으로 간주하지 않으며, 해당 커밋의 Actions 결과로 확인합니다.


### Linux 호스트의 샌드박스 제약 확인

첫 Ubuntu 24.04와 22.04 CI에서 실제 Codex CLI의 샌드박스 검사만 `bwrap: No permissions to create a new namespace`로 실패했습니다. 당시 Mac Docker 엔진은 seccomp 기본 정책이 `unconfined`였으므로 로컬 통과만으로 일반 Linux 호환성을 판단할 수 없었습니다. Moby 기본 정책을 로컬에 명시하니 동일하게 격리 공간 생성이 거부됐습니다. 실제 시스템 호출을 추적해 고정 CLI가 필요한 clone 플래그·unshare·파일 트리 생성 호출을 확인했습니다.

**선택:** [Docker의 seccomp 정책 지정 방식](https://docs.docker.com/engine/security/seccomp/)을 사용해 검토한 고정 정책을 매 실행에 적용합니다. 원본의 기본 거부 규칙에 정확한 clone 플래그와 사용자 공간 생성, 중첩 파일 트리 구성에 필요한 호출을 추가합니다. AppArmor를 사용하는 호스트에는 Moby 기본 프로필을 바탕으로 한 전용 프로필도 설치합니다. 원본 버전·라이선스·변경 범위는 [보안 정책 폴더](../apps/server/security/README.md)에 기록했습니다.

| 대안 | 판단 |
| --- | --- |
| 호스트 정책에 그대로 의존 | 개발 PC의 설정에 따라 검증 결과가 달라지고 일반 Linux에서는 실행하지 못해 미채택 |
| seccomp·AppArmor 전체 해제 또는 특권 컨테이너 | 격리 조건을 크게 바꾸므로 미채택 |
| 별도 VM·다른 컨테이너 런타임 | 대안이지만 새로운 운영 구성과 자원 측정이 필요해 현재 단위에서 도입하지 않음 |
| 검토한 seccomp·AppArmor 정책 명시 | 호출 범위와 적용 버전을 재현할 수 있어 선택. 중첩 네임스페이스·마운트 관련 커널 기능을 허용하는 부담을 감수하고 업데이트마다 재검증 |

일반 사용자·capability 전체 제거·권한 상승 금지·읽기 전용 루트·작업 폴더를 유지합니다. 정책의 capability 허용 문법 자체가 커널 권한을 부여하는 것은 아닙니다. 실제 테스트는 외부 seccomp 활성화와 capability 0, 독립 마운트·네트워크 공간 변경 거부, 준비한 파일 읽기, 작업 파일 쓰기·인증·외부 파일·통신 차단을 확인합니다. AppArmor 호스트에서는 적용 프로필도 커널 상태에서 대조합니다. 로컬 전체 테스트 319개(실제 Docker 14개)·타입 검사를 통과했습니다. [18d371f의 CI](https://github.com/lmj00/agent-hub/actions/runs/41542978575)에서도 Ubuntu 22.04·24.04 각각 설치·타입 검사·빌드·테스트 319개·Chromium 7개가 모두 통과했습니다. AWS 운영 검증은 별도입니다.

실행 어댑터는 네임스페이스·loopback 초기화 실패를 `unsupported_settings`로 분류합니다. 모델이 그 뒤 보고서를 반환하더라도 성공으로 처리하지 않으며, 기존 설정 차단·종료 확인 절차를 따릅니다.

추가로 명시적 seccomp 정책을 적용한 로컬 Docker에서 실제 Codex medium 분석을 수행했습니다. 약 13.5초 만에 예제 파일을 읽고 현재 계산값 190·기대값 180을 확인했으며, 파일 불변·전체 종료·임시 인증 정리까지 확인했습니다. 원격 CI는 실제 모델 호출 없이, 이 별도 실험은 실제 ChatGPT 인증으로 검증한 결과입니다.

## 분리된 개발 기준과 변경 내용 검사 — 2026-11-04

**선택:** 서버 전용 Git 저장소에 원본의 시작 커밋과 현재 파일 상태만 가져오고 개발 브랜치를 축적합니다. AI에게는 Goal 범위의 파일 복사본만 제공합니다. 원본의 과거 커밋·로컬 설정·원격 주소는 가져오지 않으며, 서버의 전체 Git 객체는 AI 작업 폴더에 노출하지 않습니다. Git과 기존 Node 파일 API를 사용하며 패키지는 추가하지 않았습니다.

| 대안 | 판단 |
| --- | --- |
| 원본의 worktree·브랜치에서 직접 개발 | 구성이 간단하지만 원본 저장소와 실행 경계가 섞여 미채택 |
| 전체 clone을 AI에 제공 | 현재 범위 밖 파일과 과거 이력을 함께 읽을 수 있어 미채택 |
| 범위별 파일만 가진 Git 저장소에 변경 축적 | 범위가 바뀔 때 누락 파일·범위 밖 파일 보존을 별도로 처리해야 함 |
| 서버 전용 저장소 + 범위별 복사 + 변경 바이트 검사 | 원본과 검증 기준을 분리하고 범위 밖 파일을 그대로 보존할 수 있어 채택 |

전체 기준은 초기 상한을 트리 항목 10,000개·파일 합계 64MiB로 정했습니다. AI 입력과 변경 결과는 기존 500개·파일당 1MiB·합계 8MiB를 유지하며, 개발 경로는 UTF-8 1KiB·32단계까지 허용합니다. 초과하면 일부를 생략하지 않고 보류합니다. 이력 없이 명시한 객체만 Git pack으로 가져오며 원본과 객체 파일을 공유하지 않습니다. SHA-1·SHA-256 저장소를 실제 Git 테스트로 확인했습니다. 이 상한의 대형 프로젝트 적합성·2GiB 장기 운영은 별도 측정이 필요합니다.

서버는 입력 기준과 각 파일의 내용·실행 권한을 검사하고 새 Git 트리(검증할 파일 상태)를 구성합니다. 범위 밖 쓰기, 링크·서브모듈 생성, 비밀 설정 경로, 대소문자·유니코드 충돌, 선언하지 않은 파일을 없애는 파일/폴더 충돌을 거부합니다. 모델이 수정한 Git 설정·훅·작업 폴더를 호스트 Git 명령으로 읽지 않습니다. 기존 Git 읽기·범위 검사 코드는 계획 입력 준비와 함께 사용합니다.

후보 트리 생성은 브랜치 반영이나 작업 성공을 뜻하지 않습니다. 컨테이너의 변경 수집과 DB 영속 기록은 아래 단위에서 구현했으며, 자동 테스트·별도 검토와 ChangeApplication 복구는 다음 연결 단위에 남아 있습니다. 원본 상태나 기록된 개발 기준이 달라지면 자동 덮어쓰지 않습니다. 저장소 생성 중 중단된 비공개 디렉터리는 확인 없이 다시 사용하지 않습니다.

### 컨테이너의 수정 공간과 변경 수집

**선택:** 읽기 전용 입력을 컨테이너의 32MiB tmpfs(크기가 제한된 임시 파일 공간)에 복사합니다. 파일·디렉터리 항목도 4,096개로 제한합니다. 원본 폴더의 쓰기 가능한 연결은 호스트 디스크 사용량까지 제한하기 어려워 채택하지 않았습니다. 종료되지 않은 임시 변경을 영속 저장으로 취급하지 않으며, 종료 확인 뒤 서버가 만든 후보를 아래 개발 기록에 저장합니다.

수집은 Linux 컨테이너에서만 수행합니다. 각 상위 디렉터리를 열린 파일 식별자(FD)로 고정하고, 다음 경로를 열 때 링크를 거부합니다. 마지막 파일에만 `O_NOFOLLOW`를 지정하면 상위 경로 교체를 막지 못하므로 각 단계에 적용합니다. 정규 파일·같은 파일 시스템·단일 링크인지 확인하고 실제 읽은 바이트에 상한을 적용하며 FIFO는 기다리지 않고 거부합니다. [Linux open의 FD·링크 처리](https://man7.org/linux/man-pages/man2/open.2.html)와 [Node 24 파일 API](https://nodejs.org/docs/latest-v24.x/api/fs.html)를 참고했고, 실제 컨테이너에서 링크 교체 중 합성 인증 파일이 수집되지 않는지 검사했습니다.

원본 바이트 합계는 8MiB이며 전송용 base64와 경로 정보를 포함한 변경 결과는 12MiB로 제한합니다. 일반 분석의 기존 출력 제한은 유지합니다. 부모는 입력 기준·해시·범위·파일 종류·크기를 다시 검사하며, 자식이 보낸 종료 증명이나 다른 서버 상태는 채택하지 않습니다. 범위를 벗어난 수정은 `invalid_change`로 보류합니다. 내부 실행기의 개발 모드는 일반 직접 SDK 실행에서 거부하며, 컨테이너 runner에서만 명시적으로 허용합니다.

실제 Codex 검증에서 CLI 0.166.0의 파일 단위 쓰기 경로가 `파일/.git`을 만들려다 샌드박스 초기화에 실패하는 것을 재현했습니다. 따라서 CLI에는 필요한 기존 상위 디렉터리를 쓰기 경로로 전달하고, 수집과 서버의 후보 검사에서 원래 파일 단위 Task 범위를 강제합니다. 범위를 넓힌 주변 파일 변경은 반영하지 않습니다. 초기화 실패 문구도 설정 오류로 분류해 정상 결과로 오인하지 않도록 했습니다.

실제 모델이 예제 `total` 함수를 덧셈에서 곱셈으로 수정했으며, 인증 마운트·네트워크가 없는 별도 컨테이너에서 고정된 두 검산을 통과했습니다. 원본 불변·전체 종료·후보 트리 구성을 확인했습니다. 이 검산은 내부 모듈의 실제 연결 확인이며, 자동 테스트 실행기의 영속 기록·독립 검토·변경 반영·자율 대기열 연결이 끝났다는 의미는 아닙니다.

### 개발 준비·후보의 영속 기록

**선택:** 프로젝트별 개발 저장소와 Run별 입력·수정 후보를 SQLite에 기록합니다. 마이그레이션 `0024_development_journal`은 기존 실행 이력을 바꾸지 않고 두 테이블을 추가합니다. 경로만 메모리에 보관하는 방식은 재시작 뒤 준비 여부와 기준을 잃고, Git 브랜치만 보고 완료 여부를 판단하는 방식은 검증 전 후보와 승인된 변경을 구분하기 어려워 채택하지 않았습니다.

파일 생성 전 의도를 저장하고, 모든 준비가 끝났을 때만 준비 완료 파일을 임시 파일에서 이름 변경으로 게시합니다. 게시 뒤 DB 저장에 실패하면 같은 식별자·파일 내용을 검사해 기존 결과를 연결합니다. 준비 완료 파일이 없으면 폴더가 있어도 완성된 입력으로 취급하지 않습니다. 이는 프로세스 중단 복구이며, 디스크 자체의 손실까지 복구하는 백업 기능은 아닙니다.

재작업 입력에는 이전 후보와 승인된 기준을 함께 기록합니다. 수정 결과는 항상 승인된 기준과 비교해 누적 차이를 검사하므로 앞선 수정이 빠지거나 Task 범위 밖 변경이 숨어 들어가지 않습니다. 다른 Task의 미승인 후보는 가져오지 않습니다. 컨테이너 종료 근거를 먼저 저장해야 후보를 확정할 수 있고, 후보 저장이 실패하면 다음 실행도 막힙니다. 후보 저장만으로 Task가 성공하는 경로는 차단합니다.

한 Run의 개발 라운드는 최대 3개로 제한합니다. 검토 실패를 받은 재작업 선택과 실제 테스트·검토 호출은 다음 구현 단위에서 이 기록을 사용합니다. 현재 추가한 DB·Git·컨테이너 검사는 저장 순서와 복구 경계를 확인하며, 실제 모델의 검토 품질이나 자동 변경 반영을 검증한 것은 아닙니다.

### 인증 없는 실제 테스트 실행

**선택:** 기존 컨테이너 실행기의 식별자 저장·종료 관측·정리를 재사용하고 테스트 실행 경로를 추가합니다. AI 인증 폴더를 제외하고 `--network none`을 적용합니다. 운영자 설정의 이미지·명령 배열·제한 시간을 사용하며 모델이 명령을 선택하지 않습니다. 검사한 이미지 ID로 실행하고 그 ID를 결과에 기록하므로 태그 변경과 실행 당시 이미지를 구분할 수 있습니다. 이미지의 `VOLUME` 선언은 크기 제한 밖 저장 공간이 생기지 않도록 거부하고, 자동 상태 점검 명령은 비활성화합니다.

| 대안 | 판단 |
| --- | --- |
| 개발 AI에게 테스트를 실행하고 통과 여부를 보고하게 함 | 인증 환경과 테스트 실행이 섞이고 모델 문장을 완료 근거로 삼게 되어 미채택 |
| 호스트에서 프로젝트 테스트 실행 | 생성된 코드가 서버 파일·환경에 접근할 수 있어 미채택 |
| 별도 테스트 서버·실행 기록 체계 | 같은 종료 규칙을 중복 구현하고 새 운영 구성이 필요해 현재 단계에서는 미채택 |
| 같은 서버의 인증 없는 테스트 컨테이너 | 기존 실행 식별자·종료 확인을 유지하면서 입력·권한·결과를 분리할 수 있어 채택 |

테스트 출력은 서버 이벤트나 성공 JSON으로 해석하지 않습니다. 부모가 Docker에서 읽은 실제 종료 코드와 메모리 종료 여부를 사용하고, 시간·출력 제한으로 중단됐으면 종료 코드가 우연히 0이어도 통과시키지 않습니다. 정상 반환 전 종료 근거를 DB에 저장하며, 취소와 제한 시간 처리는 같은 종료 관측을 공유합니다. 컨테이너가 사라져 실제 상태를 대조하지 못하면 통과로 추정하지 않습니다.

테스트 이미지는 현재 Node.js 24를 포함해야 합니다. 서버의 고정 시작 프로그램이 입력 바이트를 확인하고 임시 공간에 복사한 뒤 설정된 프로그램을 실행합니다. 이 시작 프로그램은 Node 기본 모듈만 사용하는 `.mjs` 파일로 두어 테스트 이미지에 앱의 SDK·패키지까지 설치하지 않아도 됩니다. Python·Java 등 다른 테스트 도구도 이미지에 미리 넣어 사용할 수 있으나 이번 실측은 Node에 한정합니다. 패키지 설치와 외부 서비스가 필요한 통합 테스트는 실행 전에 준비하거나 별도 정책이 필요하며, 현재 격리 조건을 자동 완화하지 않습니다. 입력은 8MiB, 임시 작업 공간은 32MiB, 컨테이너 메모리는 768MiB입니다. 일반 프로젝트에 충분한지는 별도 측정이 필요합니다.

실제 Docker에서 계산 검산, 인증·소켓·통신 부재, 읽기 전용 입력과 시작 프로그램, 출력 위조·입력 변조 거부, 비정상 종료·시간 초과·출력 초과·메모리 종료를 검사합니다. 이는 테스트 실행 경계의 검증이며, 모델이 만든 테스트의 품질이나 독립 검토·자동 변경 반영의 완료를 뜻하지 않습니다.
