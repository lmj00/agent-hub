# 구현 순서와 완료 기준

> 이 문서는 **무엇부터 만들고, 무엇을 확인해야 다음 단계로 넘어가는지**를 정합니다. 현재는 4단계의 자동 복구·다단계 분석과 5단계의 목표 관리·기간 예산·자료 준비·내부 계획 예약과 작업 생성을 구현했습니다. 다음은 목표 변경·취소 제어의 남은 연결과 실제 개발 실행입니다. 아래 단계별 항목은 계획이며, 실제 완료 범위는 진행 상태에 따로 기록합니다.

## 현재 진행 상태

실행 환경, SQLite 저장 기반과 프로젝트·작업 등록·조회 API를 구현했습니다. CLI에서 작업 한 건을 분석하는 기능에 이어, 실행 설정을 지정한 서버가 대기 작업을 자동으로 하나씩 처리하도록 연결했습니다. 선택한 로컬 컨테이너 실행의 전체 종료 확인, 제공자 차단·확인 실행 조건도 추가했습니다. 종료·차단 조건을 사용하는 수동 복구 API까지 검증했습니다. 3단계의 로그인·세션 보호, 관리 화면·공통 계약 패키지와 서비스 관측을 거쳐 4단계의 일시 오류·서버 중단 자동 복구와 사용 한도 자동 확인을 추가했습니다. 최초 effort 자동 선택과 결과를 이어받는 제한된 다음 Step 선택까지 추가했습니다.

### 단위별 검증 기록 — 해당 단위를 완료한 당시 상태

계획의 관측 근거는 SQLite·HTTP·실행 연결 검증 17개를 추가했습니다. 현재 실패와 과거 수집 성공, 비활성·오래된 관측·설정 변경·다른 프로젝트 제외, 호출 전 자료 저장·저장 실패 시 호출 거부·재시작 후 보존·다국어 입력 크기를 확인했습니다. 기존 실제 Docker 계획 시나리오에서 관측 전달과 자식의 가짜 자료 거부도 검증했습니다. Chromium에서는 당시 자료·실패와 과거 기록의 구분·문자열 출력·모바일 폭·새로고침을 확인했습니다. 실제 Codex 호출 1회에서도 로컬 HTTP의 예제 검산 근거를 인용하고 후속 작업 하나를 생성했으며, 원본 불변·전체 종료를 확인했습니다. 생성된 작업의 실제 개발 수행은 후속 단위입니다.

취소 작업 재허용은 실제 SQLite·HTTP 검증 32개를 추가했습니다. 원본 기록 보존·연결된 새 작업·목표 버전 이력, 독립 DB 연결의 중복 요청, 저장 실패의 전체 되돌림, 범위·상태·종료 근거·복구·누적 한도 검사를 확인했습니다. 여러 번 취소·재허용한 뒤에도 최초 실행과 재시도를 구분하고 오류·누적 시간을 이어받습니다. Chromium에서는 응답을 의도적으로 잃은 뒤 같은 요청을 다시 보내도 작업이 하나만 생기는 것과 기록 간 이동·새로고침을 확인했습니다. 재허용한 작업의 실제 개발 수행은 후속 개발 실행기 단위입니다.

읽기 전용 관측 적용은 **서버·화면 자동 테스트 229개(실제 Docker 8개 포함)**, 타입 검사와 빌드를 통과했습니다. 실제 로컬 HTTP 상태 서버·SQLite로 수집 실패·오래된 응답·정상 대기·업무 지연·시간 초과·응답 크기 제한·주소/토큰 비노출·설정 변경·저장 실패·재시작·기록 보관 상한을 검증했습니다. 분석이 응답하지 않거나 취소돼도 관측을 계속하며, 대기 중인 관측도 서버 종료 시 중단됩니다. **Chromium 시나리오 4개**에는 정상 대기 → 관측 실패 → 오래된 정보 → 회복, 프로젝트 전환 중 화면 중복 방지, 데스크톱·모바일 표시가 포함됩니다. 기존 DB의 작업·세션을 보존하는 관측 테이블 마이그레이션도 확인했습니다. 이 검증은 임시 상태 서비스와 AI 대역을 사용했고, 실제 트레이딩 서비스·AWS 배포·24시간 연속 운영은 변경하거나 확인하지 않았습니다.

4단계 첫 단위는 **서버·화면 테스트 253개(실제 Docker 10개 포함)**, 타입 검사와 빌드를 통과했습니다. SQLite·HTTP에서 대기 시각·횟수 소비·정책 보존·연속 오류·누적 시간·수동 요청 경합·취소·계정 차단·저장 실패를 확인했습니다. 실제 Docker에서 일시 오류 뒤 두 번째 실행, 서버 SIGKILL 뒤 남은 컨테이너 종료 → 자동 재시도 → 완료를 검증했습니다. Chromium 시나리오 5개에서 재시도 예약과 새 실행 이력을 확인했으며 로그인 요청 제한도 유지했습니다. 오류와 AI 응답은 대역으로 주입했고 실제 계정 한도를 소진하지 않았습니다. 한도 자동 확인·effort 변경·자율 작업 생성·원격 배포는 이 단위의 완료 범위가 아닙니다.

계정 사용 한도 자동 확인은 **서버·화면 테스트 269개(실제 Docker 10개 포함)**, 타입 검사와 빌드를 통과했습니다. SQLite·HTTP에서 제공 시각·미제공·계정 횟수·재시작·단일 예약·Task 상한·취소·새 차단·저장 실패와 지연된 종료 확인을 검증했습니다. Chromium 시나리오 5개는 계정 확인 예정 시각 표시 → 확인 실행 성공 → 대기 작업 재개까지 검증합니다. 실제 계정 사용량을 소진하지 않고 SDK 오류·AI 응답을 대역으로 주입했습니다. 실제 제공자의 한도 시각 제공 여부·24시간 운영은 미확인입니다.

최초 effort 선택은 **서버·화면 테스트 279개(실제 Docker 12개 포함)**, 타입 검사·빌드와 Chromium 시나리오 5개를 통과했습니다. SQLite·HTTP·컨테이너 전달·SDK 설정·화면의 선택 근거를 검증했습니다. 실제 ChatGPT 인증과 `gpt-6.1-sol`로 같은 계산 예제를 medium/high/xhigh에서 각각 분석해 오류 원인·현재 190·기대 180을 모두 확인했습니다. CLI 세션의 실제 effort, DB 기록, 대상 파일 불변과 컨테이너 종료도 대조했습니다. 도구 실행 경로 문제를 이 과정에서 수정했고 실제 이미지의 권한 경계 테스트를 추가했습니다. 단일 소규모 예제이며 추론 강도별 일반적인 품질 차이나 다단계 전환을 검증한 결과는 아닙니다.

다단계 분석은 **서버·화면 테스트 295개(실제 Docker 14개 포함)**, 타입 검사·빌드와 Chromium 시나리오 6개를 통과했습니다. 같은 Run의 호출 순서·세션 분리·맥락 전달·effort 상향/하향·변경 상한·잘못된 제안·누적 맥락 상한·타이머 유지·부분 결과 보존을 확인했습니다. 실제 컨테이너에서는 DB 저장 확인 전 후속 호출 금지와 저장 실패 후 중단을 검증했습니다. 별도 실제 Codex로 high → xhigh → medium 분석 완료와 두 번째 세션 시작 시 취소 → 첫 보고서 보존·전체 컨테이너 종료를 확인했습니다. 목표에서 새 일을 생성하거나 코드를 수정하는 기능은 아직 없습니다.

목표 관리 단위는 **서버·화면 테스트 317개(실제 Docker 14개 포함)**, 타입 검사·빌드와 Chromium 시나리오 7개로 검증했습니다. 목표·버전 이력의 재시작 보존, 두 연결의 중복 등록·동시 수정, 재전송의 원래 응답 보존, 오래된 버전·경로 이탈·잘못된 예산 거부, 이력 저장 실패 시 전체 되돌리기와 기존 작업 보존 마이그레이션을 확인했습니다. 브라우저에서는 등록 응답 유실 뒤 중복 없는 재시도, 수정·일시정지·재개·이력·모바일 표시를 확인했습니다. 목표 예산 집행과 목표 기반 작업 생성은 아직 연결하지 않았습니다.

## 0단계 설계 기반

**목표:** 프로그램이 할 일과 하지 않을 일, 중단·복구 기준을 정합니다.

### 구현할 내용

- 제품 범위, 구조, 상태 전이, 복구 정책을 문서화합니다.
- 공개 소스와 비공개 설정·실행 데이터를 분리합니다.
- 이후 설계 변경은 이유와 함께 해당 문서를 수정합니다.

### 완료 기준

- 문서 사이의 범위와 상태 이름이 일치하고, 실제 비밀번호·인증 키 없이 저장소를 공개할 수 있습니다.

## 1단계 개발 환경과 작업 API

**목표:** 작업을 등록하고 서버를 다시 켜도 같은 기록을 조회할 수 있게 합니다.

### 구현할 내용

- 한 저장소에서 화면·서버 코드를 함께 관리하는 TypeScript 워크스페이스를 만들고, web/server 패키지로 나눕니다. 실행 모듈은 server 내부에 둡니다.
- 서버 코드를 상태 확인(`health`), 프로젝트 관리(`projects`), 작업 관리(`tasks`)로 나누고 등록·조회부터 만듭니다. `app.ts`는 DB와 기능을 연결하고, `main.ts`는 서버를 시작하고 종료합니다. 취소·재시도·AI 실행 코드는 해당 개발 단계에서 추가합니다.
- [기술 선택안](03-technology-decisions.md)에 따라 Node.js 24 LTS, pnpm, better-sqlite3와 Drizzle ORM·Kit의 호환성을 확인하고 정확한 버전을 고정합니다. 대안으로 변경하면 이유를 기록합니다.
- Fastify 상태 확인 API와 DB 구조 변경을 순서대로 적용하는 SQLite 마이그레이션을 추가합니다. 생성 SQL을 검토하고 빈 DB 생성과 기존 DB 업그레이드를 검증합니다.
- 프로젝트 등록, 작업 등록·목록·상세 조회를 구현합니다.
- 이 단계의 Task는 Goal 없는 단발 작업으로 저장합니다. Goal과 자율 작업 생성은 5단계에 추가하며, 기존 작업 기록을 유지하는 마이그레이션을 적용합니다.
- 작업 등록 조건을 판단하는 코드와 요청을 받거나 DB에 저장하는 코드를 나눕니다. 같은 요청을 반복해도 작업이 하나만 만들어지는지 실제 SQLite로 확인합니다. 다른 기능의 내부 파일을 직접 가져와 사용하지 않는지도 확인합니다.
- 화면과 서버가 함께 사용할 요청·응답 형식(스키마)을 정하고, 실제 주고받는 값이 형식에 맞는지 실행 중 검사합니다(런타임 검증).
- 상태 확인 API에서 앱 응답과 DB 준비 상태를 구분하고 관측 시각을 제공합니다.

### 완료 기준

- 로컬 API로 작업을 등록·조회할 수 있고, 재시작 후 기록이 남습니다.
- 잘못된 입력과 중복 등록 요청을 검증합니다.
- 이 단계에는 실제 AI 호출이 없습니다.

## 2단계 내부 실행 모듈과 Codex 연결

**목표:** 등록한 작업을 실제 Codex가 읽기 전용으로 분석하게 합니다.

### 현재 구현한 단위와 남은 범위

첫 단위는 **CLI로 지정한 대기 작업 한 건 → 실제 분석 → 실행 기록 저장 → API 조회**였습니다. 다음 단위에서 이를 **HTTP로 작업 등록 → 서버 내부 대기열이 순차 분석 → 결과 조회**로 연결했습니다. CLI와 API는 같은 서버 패키지의 모듈과 로컬 DB를 사용하며 원격 실행 서버를 추가하지 않았습니다.

현재는 한 Run에 Step 하나를 만들고 effort는 medium으로 고정합니다. 최종 분석문과 제공된 사용량을 저장하며, 이벤트에는 종류·시각만 남깁니다. 파일 수정이나 코드 개선은 수행하지 않습니다.

종료 미확인 중단은 `interrupted`로 보존합니다. 컨테이너 종료가 확인되면 사용자 취소는 `cancelled`, 시간 초과는 `failed`, 서버 종료는 `waiting_retry`로 확정합니다. 직접 SDK 실행과 구버전 실행은 종료 미확인으로 남습니다. 인증·설정 오류는 `blocked`, 확인된 한도 오류는 `waiting_capacity`입니다. 종료 미확인 실행과 제공자 차단은 각각 새 배정을 막습니다. 제공된 재시도 시각을 저장하고 확인 실행 하나의 예약·완료 규칙을 구현했습니다. 재개·상태 확인·취소 API로 조건을 검증하고, 실제 종료가 확인된 작업만 다시 배정할 수 있습니다. 자동 재시도는 4단계입니다.

### 구현할 내용

- DB의 대기 작업을 하나씩 처리하는 내부 실행 루프를 구현합니다.
- 작업 선택·상태 변경·Run 생성을 함께 저장하는 배정 처리(원자적 배정), 실행 이력, 이벤트 순번을 추가합니다. 같은 백엔드가 중복으로 켜지는 것도 막습니다.
- Codex SDK 어댑터를 연결하고 이벤트·오류·결과를 공통 형식으로 저장합니다.
- 작업 관리 코드가 Codex SDK를 직접 호출하지 않고 공통 실행 기능을 요청하도록 만듭니다. Codex 연결 코드가 그 요청을 실제 호출로 바꾸고, 취소·대화 세션·오류 처리가 약속한 방식으로 동작하는지 확인합니다. 제공자마다 지원하는 기능과 설정의 차이를 기록합니다.
- 모델·SDK가 지원하는 effort 설정을 확인하고 우선 고정 기본값 `medium`으로 연동합니다. Run 아래 호출 단위 Step과 실제 적용 설정·세션·결과를 기록합니다.
- 비공개 환경에서 구독 로그인 인증을 설정하고, 비밀 정보가 없는 예제 프로젝트를 읽기 전용으로 분석합니다.
- 기본 취소와 제한 시간을 적용하고, 실행 상태를 확인할 수 없으면 중단 상태로 보존합니다.
- `waiting_capacity`·`waiting_retry`·`blocked`를 포함한 상태와 오류 분류를 적용합니다. 사용 한도는 `waiting_capacity`, 종료가 확인된 일시적 오류는 `waiting_retry`, 인증 복구가 필요한 경우는 `blocked`로 구분합니다. 제공자·계정별 차단 사유와 확인 가능한 재시도 시각을 저장하고 대기 중 자동 배정하지 않습니다.
- 이 단계에서는 수동 재개 API로 검증합니다. 실행 중이었다면 기존 종료·결과를 확인하고 다음 배정에서 같은 Task에 새 Run을 생성합니다. 최초 실행 전 보류는 재개 후 첫 Run을 만듭니다. 수동 재개도 재시도 가능 시각·계정 차단·취소·제한 조건을 확인합니다.
- 현재 단계, 최근 이벤트·진척 시각, 대기 사유와 다음 행동을 기록합니다. 프로세스 생존을 작업 진척과 구분합니다.
- 초기 연동은 같은 컴퓨터에서만 접속할 수 있는 주소(루프백 주소)에 서버를 연결한 로컬 환경에서 검증합니다. 원격 접근은 다음 단계의 인증 구현 후 허용합니다.

### 완료 기준

- API로 등록한 작업을 실제 Codex가 분석하고 결과가 DB에 남습니다.
- 대상 파일은 변경되지 않으며, 중단된 작업은 자동 재배정하지 않습니다.
- 배정 중복 방지와 기본 종료 처리를 검증합니다.
- 인증 오류·일시적 오류·사용 한도·지원하지 않는 설정을 구분하고, 원인이 해소되지 않은 작업이 수동 요청만으로 실행되지 않는지 확인합니다.

## 3단계 최소 관리 화면과 인증

**목표:** 사용자가 브라우저에서 지시하고, 진행·결과·문제를 확인하게 합니다.

### 현재 구현한 단위와 남은 범위

로그인·세션 저장·폐기·만료와 요청 위조 방지, 실제 API에 연결한 관리 화면, 읽기 전용 서비스 관측을 구현했습니다. `AUTH_CONFIG`로 로그인 설정, `SERVICE_CONFIG`로 관측 대상·대기 허용·업무 지연 기준을 전달합니다. 인증 없는 로컬 API 개발은 `LOCAL_API_ONLY=1`로 명시하며, 인증 설정 없이 기본 서버를 켜는 동작은 거부합니다. 기존 트레이딩 서비스 연결과 AWS 운영은 아직 검증하지 않았습니다.

현재 화면은 저장된 Task 지시와 실제 분석 Step들을 기준으로 표시합니다. effort 선택 이유·다단계 결과와 Goal 정의·버전 이력을 표시합니다. 목표에 따른 다음 작업 선택과 코드 검증 진척은 아직 연결 전이며, 해당 기능을 구현할 때 실제 기록과 함께 추가합니다.


### 구현할 내용

- 프로젝트 선택, 지시 입력, 작업 목록, 상세 결과 화면을 만듭니다.
- 상태 조회와 이벤트 표시, 취소 요청을 연결합니다.
- 종료가 확인된 중단 작업의 수동 재시도를 연결합니다. 실행 종료 여부가 불명확하면 재시도를 거부하고 확인이 필요한 이유를 표시합니다.
- 한도 도달로 보류된 작업에 보류 사유와 확인 가능한 재시도 시각을 표시하고, 사용자 재개 요청을 연결합니다. 회복 시각이 없으면 미확인으로 표시합니다.
- 목표·현재 단계·경과 시간·최근 진척·다음 행동을 표시하고, 상태 조회가 끊기면 마지막 확인 시각과 연결 끊김을 보여줍니다.
- 현재 Step의 모델·적용 effort와 선택 이유를 표시합니다. 초기에는 고정 기본값이며, 4단계에서 자동 선택과 연결합니다.
- 설정한 장기 실행 서비스 하나의 읽기 전용 상태 관측을 연결합니다. 최근 업무 처리 시각, 정상 대기, 관측 실패를 구분해 표시합니다.
- 단일 사용자 로그인과 세션 보호를 구현합니다. 내부 실행 모듈에 별도 로그인 API는 만들지 않습니다.
- 인증 정보는 초기 설정 또는 비공개 환경 설정으로 전달하고 기본 비밀번호를 제공하지 않습니다.

### 완료 기준

- 브라우저에서 실제 Codex 분석 작업을 등록하고 결과와 취소 상태를 확인할 수 있습니다.
- 앱과 작업의 생존·진척을 구분하고, 별도 서비스의 상태는 근거와 관측 시각을 함께 표시합니다.
- 인증 없는 접근과 다른 사이트에서 위조한 작업 변경 요청이 거부됩니다.

## 4단계 무인 운영을 위한 자동 복구와 실행 검증

**목표:** 사용자가 없어도 복구 가능한 문제를 처리하고 다음 단계의 추론 강도를 선택하게 합니다.

### 현재 구현한 단위와 남은 범위

`automaticRecovery`를 켠 서버에서 일시 오류·서버 중단의 자동 복구를 구현했습니다. 기존 종료 확인과 복구 접수를 재사용하고, Task에 정책·횟수·다음 시각·누적 실행 시간을 저장합니다. 예약·보류는 이벤트와 관리 화면에서 확인합니다. 인증·계정 차단·취소·수동 재개도 제한을 우회하지 않으며 재시작으로 정책을 초기화하지 않습니다.

사용 한도의 제한된 자동 확인도 구현했습니다. 계정별 정책·횟수·내부 확인 시각을 별도로 보존하고 제공자 시각과 Task 상한을 함께 검사합니다. 최초 effort 선택과 결과를 이어받는 다단계 호출·effort 전환까지 구현했습니다. 다음 단계는 목표 관리와 자율 개발·검증입니다. 외부 채널 알림은 6단계의 운영 설정에서 연결합니다. 현재 새 Task를 찾거나 코드를 바꾸는 기능은 5단계 범위로 남아 있습니다.

### 단계별 effort 선택

- 작업 시작과 Step 전환 시 다음 호출의 effort를 자동 선택합니다. 규칙과 이전 단계의 구조화된 제안을 검증해 난이도에 따라 상향·하향하며, 실패 후 조정으로 한정하지 않습니다.
- 같은 세션의 호출별 설정 변경 가능 여부와 실제 적용을 검증합니다. 새 세션이 필요하면 이전 단계의 결과·근거·제약을 전달합니다. 정상 단계 전환은 같은 Run에 기록합니다.
- Step 수·effort 변경 횟수·허용 범위를 설정하고, 단계 전환에도 Run 제한 시간과 Task 누적 예산이 유지되게 합니다. 지원되지 않는 설정, 잘못된 제안, 예산 소진을 처리합니다.
- 초기 effort 허용 범위를 `medium`·`high`·`xhigh`, 최소·기본값을 `medium`으로 설정합니다. 어려운 작업의 최초 high·xhigh 선택과 이후 medium까지의 하향, 허용 범위 밖 제안의 차단을 검증합니다.

### 중단 실행과 취소 확인

- 2단계에서 검증한 중단 표시·자식 실행 종료 확인·결과 대조를 자동 복구에 연결하고, 재전송·장기 운영 조건을 보강합니다.
- 종료 보고와 이벤트의 재전송, 늦게 도착한 결과, 취소와 완료의 경합을 검증합니다.
- 실제 제한 시간과 취소 시 자식 실행이 남지 않는지 확인합니다.

### 한도·오류 처리와 알림

- 사용량 제한, 인증 실패, 네트워크 실패를 구분해 표시합니다.
- 2단계에서 도입한 상태에 자동 재개 정책을 연결하고, 다음 시도 시각이 된 작업 중 배정 가능한 작업을 자동 선택합니다. 일시적 오류와 재시도 가능한 중단 작업은 기존 실행 종료를 확인한 뒤 자동 재시도합니다.
- 한도 도달 시 알려진 재시도 가능 시각까지 기다리고, 시각을 모르면 간격을 늘려 제한적으로 재시도합니다. 저장된 계정별 차단을 기준으로 확인 실행 하나만 자동 허용하는 규칙을 구현합니다.
- 오류 종류별 최초·최대 간격, 무작위 지연, 최대 재시도 횟수, 동일 오류 연속 횟수와 Task 누적 실행 시간 상한을 설정하고 기본값을 문서화합니다. 정책과 횟수·다음 시도 시각·누적 시간·계정 차단을 DB에 보존합니다.
- 사용자 취소는 자동 재시도하지 않습니다. 인증 만료나 복구 한도 초과는 사용자 조치가 필요한 상태로 보류합니다. 실행 제한 시간 초과·재시도 불가능한 오류는 실패로 남깁니다.
- 화면에 자동 재시도 예정 시각·횟수·보류 사유·필요한 조치를 표시하고, 부재중 알림 이벤트를 기록합니다. 수동 재개도 계정 차단과 종료 확인을 우회하지 못하게 합니다.

### 오류를 재현해 검증

- 사용량을 실제로 소진하지 않고도 오류 처리를 확인할 수 있도록 테스트에서 SDK 오류가 발생하도록 설정합니다.
- 자동 복구 정책과 시각 조건이 충족될 때만 재개하는지, 다시 한도에 도달하면 보류하는지 검증합니다. 재시작으로 횟수·대기 시간·누적 실행 시간 제한이 초기화되지 않는지 확인합니다.
- 무출력 장기 작업, 반복 로그만 있는 작업, 정상 대기 서비스, 상태 수집 실패를 구분하는지 검증합니다.
- 실패 없이도 복잡한 단계에서 effort를 올리고 단순한 단계에서 낮추는 흐름을 검증합니다. 네트워크·한도 오류만으로 상향하지 않는지, 단계별 결과가 이어지는지, 설정값과 실제 호출 값이 일치하는지 확인합니다.

### 완료 기준

- 서버나 Codex 실행이 중단돼도 작업이 중복 실행되지 않고, 같은 결과를 반복 처리해도 중복 저장되지 않습니다.
- 실제 실행의 취소·재시작과 테스트에서 주입한 오류를 각각 검증합니다.
- 복구 가능한 장애와 사용 한도는 정책 안에서 사용자 입력 없이 재시도하며, 복구 불가능한 상황은 반복 호출 없이 필요한 조치를 남깁니다.
- 단계별 effort 자동 선택·상향·하향과 설정 적용을 검증하고, 고정 기본값으로 실행한 대표 분석 작업과 결과 품질·시간·제공된 사용량을 비교해 기록합니다.

## 5단계 목표 기반 자율 개발과 에이전트 협업

**목표:** 프로젝트 목표를 한 번 설정하면 총괄이 할 일을 만들고, 개발·검증·재작업과 다음 작업 선택까지 사용자 입력 없이 이어가게 합니다.

### 현재 구현한 단위와 남은 범위

Goal 정의·상태·버전·허용 경로·예산 정책과 등록·수정·일시정지·재개 화면을 구현했습니다. 모든 변경의 이전 내용을 별도 이력으로 남기고, 같은 요청의 재전송·오래된 버전 수정·저장 실패 시 원자성을 검사합니다. Task의 종류·목표 연결과 실행 전 상태·버전 검사도 구현했습니다. 실행·개발 설정이 준비된 목표는 대기열이 자동으로 계획을 예약하고 기존 예산·계정 검사를 거쳐 호출합니다.

Goal·프로젝트의 기간 예산 소비·예약, 허용 경로의 자료 준비에 이어 단일 계획 예약·구조화된 결과 검증·후속 작업 저장을 구현했습니다. 제안을 먼저 보존하고 종료·원본·목표를 확인한 뒤 적용합니다. 계획 취소는 Goal도 일시정지합니다. 진행 중이거나 근거가 부족한 작업은 새 계획을 보류하고, 종료된 취소·실패 작업은 경로별 재생성을 막으면서 다른 작업을 계획할 수 있습니다. 취소한 계획 생성 작업의 명시적 재허용과 이전 제한 상속을 연결했습니다. 서비스 관측과 입력 자료 저장, 자동 계획 시작을 연결했습니다. 목표 변경 후 계획 작업의 범위 재검사·재연결은 구현했습니다. 목표 변경으로 실행할 수 없어진 사용 한도 확인 작업의 교체와 허용 범위 축소 시 진행 중 실행의 중단은 연결했습니다. 분리된 개발 작업 공간·코드 변경·검증·변경 반영 기록도 연결했습니다.

### 다음 구현을 나눌 단위

아래 순서 중 5b·5c·5e와 5d의 계획 예약·작업 생성·자동 시작을 구현했습니다. 5f에서 유한 목표의 완료 판정·조회·복구를 연결했고 실제 두 작업의 누적 반영과 목표 완료를 확인했습니다. 개발 작업은 읽기 전용 실행에 배정하지 않습니다.

| 순서 | 변경할 내용 | 넘어가기 전에 확인할 결과 |
| --- | --- | --- |
| 5b. 목표와 실행 연결 — 구현 | Task에 목표·판단 당시 버전·계획/실제 작업 구분 추가. 기존 수동 Task는 Goal 없이 유지. 배정·수동 재개·자동 복구가 같은 목표 상태 검사를 사용 | 일시정지한 목표에서 새 Run을 만들지 않음. 오래된 계획이 배정되지 않음. 다른 목표와 기존 수동 작업은 계속 처리 |
| 5c. 기간 예산 집행 — 구현 | Goal·프로젝트 양쪽 정책과 소비·예약 기록 저장. 첫 호출과 다음 Step 시작 전에 원자적으로 검사. 예산 대기 사유·기간 종료 시각을 화면에 표시 | 재시작·새 Task·정책 수정으로 소비량이 초기화되지 않음. 저장 실패 때 호출하지 않음. 다음 기간에도 계정 차단·Task 상한 유지 |
| 5d. 계획 예약·작업 생성 | Goal마다 미완료 계획 하나만 예약. 허용 경로로 준비한 읽기 전용 자료·현재 코드 버전·이력을 총괄에게 제공. 계획 검증과 후속 Task 저장을 함께 처리 | 중복 결과가 작업을 두 번 만들지 않음. 목표 변경 중 도착한 결과·범위 밖 제안 거부. 취소한 문제의 재생성 억제. 할 일이 없으면 다음 점검까지 대기 |
| 5e. 개발·검증·변경 반영 | 분리된 Git 작업 공간, 개발과 별도 검토 호출, 실제 테스트, ChangeApplication 기록과 개발 브랜치 반영 | 검증 전 성공 표시 금지. Git 성공 후 DB 저장 전 종료도 대조해 복구. 검증된 변경이 다음 작업의 기준으로 이어짐 |
| 5f. 무인 흐름 검증 | 예제 프로젝트와 화면에서 목표 → 계획 → 서로 다른 작업 두 건 → 검증·반영 → 다음 판단 연결 | 추가 사용자 지시 없이 진행. 취소·목표 수정·예산 대기·재시작을 끼워 넣어도 중복 실행·무한 계획 반복이 없음 |

5f의 첫 연결로 다음 계획이 반영된 개발 코드를 읽고, 후속 Task에 그 기준 버전을 남기도록 했습니다. 저장된 기준·실제 Git·원본의 불일치와 재시작 복구를 검사합니다. 자동 계획 시작은 실행 서버에 연결했고, 새 작업이 없는 판단은 점검 간격을 두어 다시 확인합니다. 유한 목표의 독립 검증과 원자적 완료·조회·복구를 연결했습니다. 서로 다른 두 Task의 실제 모델 누적 반영·전체 목표 완료·별도 검산·완료 후 재시작을 확인했습니다. 아래 F3 기록은 예제 흐름 검증이며 원격 장기 운영 증명은 아닙니다.

5b는 기존 `createDrizzleRunStore`의 배정, `recover-task`의 재개, 자동 복구 경로에 검사를 연결했습니다. 계획에서 생성한 이전 버전 작업은 5d에서 범위를 재검사한 뒤 버전·근거를 갱신합니다. 경로 근거가 없는 기존 작업, 종료나 복구가 미확정인 작업은 보류합니다. 사용 한도 확인의 원인 작업이 목표 변경으로 실행 불가능하면 계정 보류를 유지하며, 다른 적격 작업으로 시작 전 확인 예약을 넘기는 처리는 5d에서 연결했습니다. 5c의 호출 수는 Task 수가 아닌 실제 시작을 허용한 AI Step 단위로 계산하며, 예약 이후 실행 여부가 불명확하면 임의로 환불하지 않습니다. 계획·재작업·제공자 확인 호출도 해당 작업의 예산에서 빠져나가지 못하게 합니다.

5d의 경로 범위는 지시문으로만 전달하지 않습니다. 자료 준비와 실행 권한에서 함께 제한하고, 심볼릭 링크·저장소 밖 경로·비밀 설정이 제외되는지 검사합니다. 결과에 적힌 파일명이나 “테스트 통과” 문장만 믿고 목표를 완료하지 않으며, 서버가 확인한 코드 버전과 검증 기록을 대조합니다. `nextCheckAt`은 실제 계획의 대기 판단을 저장할 때 채우며, 목표 등록 직후 null인 상태도 자동 점검 대상입니다. 재시작은 저장된 점검 시각을 초기화하지 않습니다.

### 구현할 내용

- Goal에 목표, 완료 기준, 목표 버전, 유한/지속 관리 구분, 우선순위, 허용 범위, 상태, 다음 점검 시각과 기간 예산을 저장합니다. 목표 등록·수정·일시정지·재개 화면을 추가합니다. 계획 반영과 작업 배정 시 현재 목표 버전·상태를 확인합니다.
- 현재 코드·테스트·이전 결과에서 작업을 찾는 총괄 역할을 연결합니다. 계획 호출도 Task·Run·Step으로 기록하고 같은 실행 제한·계정 차단·복구 정책을 적용합니다.
- 지속 관리 목표에는 실제 서비스의 입력 데이터·실행 결과를 판단 근거로 연결합니다. 정한 기준의 이상 발견 → 원인 분석 → 개선 작업 → 비교 실험 → 허용된 테스트 환경 반영 → 재관측을 검증합니다. 모의매매 같은 별도 실험 환경부터 적용하며, 기존 운영 서비스를 직접 변경하지 않습니다.
- 계획 결과와 후속 Task를 원자적으로 저장합니다. 생성 키·문제 식별자·관련 Task를 기록하고, 동일 이벤트 재처리와 의미가 같은 작업의 재생성을 제어합니다.
- 실제 작업 완료·검증 피드백·목표 변경·주기 점검을 다음 판단의 계기로 사용합니다. Task의 `planning`·`work` 종류를 구분하고, 계획 Task 완료만으로 다음 계획을 만들지 않습니다. Goal별 미완료 계획을 하나로 제한합니다. 대기열이 비어도 활성 목표를 다시 점검하고, 변경이 없으면 점검 간격을 두어 반복 분석을 줄입니다. 프로젝트 간 우선순위와 대기 시간을 함께 반영합니다.
- 지정된 개발 브랜치·작업 공간에서 코드 수정과 테스트를 실행합니다. 기준 커밋과 변경 내용을 기록하고 검증을 통과한 변경을 개발 브랜치에 로컬 커밋해 다음 작업으로 이어갑니다. 외부 푸시·기본 브랜치 병합·운영 배포는 별도 정책입니다.
- Git과 DB의 반영을 나누어 기록합니다. 반영 예정 기록 → Git 변경 → 결과 대조·DB 성공 확정 순서로 처리하고, 각 구간에서 재시작해도 이미 수행한 변경을 중복 반영하지 않게 합니다. Git·테스트 실행 중 DB 트랜잭션을 열어두지 않습니다.
- 개발과 검증 역할을 별도 호출·대화 맥락으로 연결합니다. 검증 결과는 실제 코드 버전·테스트 근거와 함께 저장하고, 필요한 수정은 같은 Task의 제한된 Step으로 요청합니다. 별도 개선은 관련된 새 Task로 생성합니다.
- Goal·프로젝트의 기간 예산, 계획 호출·재작업 횟수, 진척 없는 반복 한도를 적용하고 재시작 후 보존합니다. 새 Task 생성으로 취소·실패·인증 차단·상한을 우회하지 못하게 합니다.
- 기간 예산 대기는 `waiting_capacity`와 해당 범위·다음 기간 시각으로 기록합니다. Run 생성 전의 대기는 재시도로 세지 않으며, 기간 갱신 시에도 Task 누적 제한과 계정 차단을 확인합니다. 기간 예산은 실제 구독 잔여량으로 표시하지 않습니다.
- 화면에서 다음 작업을 선택한 이유, 역할별 진행·검토 의견, 검증된 변경, 목표 상태, 대기 사유와 다음 점검 시각을 확인하게 합니다. 목표 일시정지와 실행 중인 작업 취소를 구분합니다.

### 완료 기준

- 예제 프로젝트의 목표 설정 후 추가 입력 없이 두 개 이상의 서로 다른 작업을 발견·생성하고 개발·검증해 다음 작업까지 이어갑니다. 검증된 변경이 다음 작업의 기준 코드에 포함됩니다.
- 검증에서 지적된 실제 결함을 개발 역할이 수정하고 다시 검증하는 흐름을 확인합니다. 테스트 실패를 숨기거나 완료 기준을 낮추지 않습니다.
- 대기열이 빈 상태에서도 활성 목표의 다음 점검이 수행됩니다. 유한한 목표 달성과 지속 관리 목표의 대기를 구분하고, 의미 없는 작업을 계속 만들지 않습니다.
- 계획 완료 이벤트가 반복돼도 계획만 연속 생성하지 않습니다. 완료 조건·검증 근거와 미완료 실제 작업을 확인한 경우에만 유한한 목표를 완료하고, 해당 계획 Task의 성공도 함께 저장합니다.
- 목표 변경·일시정지 중 도착한 이전 계획은 작업 생성과 목표 완료에 적용하지 않습니다. 일시정지는 실제 대기 작업을 취소하지 않으며, 재개 시 현재 범위에 맞는 작업은 버전·재확인 근거를 갱신합니다. 오래된 계획은 종료를 확인해 정리하고 새 계획을 막지 않게 합니다.
- 중복 완료 이벤트·서버 재시작·미완료 변경이 있어도 후속 작업이나 로컬 커밋을 무조건 반복하지 않습니다. 기존 실행 종료와 실제 작업 공간을 확인한 뒤 복구합니다.
- Git 커밋 직후 DB 저장 전에 중단해도 결과를 대조해 복구하며, 검증하지 않은 코드나 반영 여부가 불명확한 변경을 다음 작업의 기준으로 사용하지 않습니다.
- 사용자가 취소한 작업의 재생성, 실패한 작업의 이름 변경 재시도, 새 Task로 예산 초기화가 차단됩니다. 목표 일시정지 후 새 계획·배정이 중지되고 다른 활성 목표는 계속 진행합니다.
- 계획 Task 취소 시 Goal도 일시정지하고, 명시적 재개 후에만 다시 계획합니다. 실제 작업의 취소 억제를 사용자가 해제하면 원본 취소 기록을 유지한 채 연결된 새 Task로 처리합니다. 허용 범위 축소에 따른 중단은 사용자 취소와 사유를 구분합니다.
- 개발 호출이 정상 종료해도 검증·개발 브랜치 반영이 끝나지 않으면 Task 성공으로 표시하지 않습니다. 재작업 횟수 소진은 `blocked`, Run 시간 초과는 `failed`로 구분합니다.
- 기간 예산 소진 후 사용자 입력 없이 다음 기간에 재개하되, 인증 차단·실패·Task 누적 제한은 그대로 적용합니다. 목표 일시정지와 자동 예산 대기를 화면에서 구분합니다.
- 총괄·개발·검증 역할이 동시 실행 하나의 제한 안에서 협업하며, 매 작업마다 사용자 승인을 요구하지 않습니다.

## 6단계 클라우드 MVP

**목표:** 사용자 PC와 추가 지시 없이 목표에 따른 작업을 계속 발견·수행하고, 결과와 복구를 확인할 수 있게 합니다.

### 구현할 내용

- 서버 한 대에 agent-hub 백엔드와 빌드한 관리 화면을 배포합니다.
- HTTPS, 컨테이너를 다시 만들어도 데이터가 남는 저장 공간(영속 볼륨), 로그 보존 한도, DB 백업과 복원 절차를 적용합니다.
- 백엔드와 Codex 실행 재시작 후 상태 복구를 확인합니다.
- 대표 계획·개발·테스트·검증 작업에서 CPU·메모리·디스크 사용량을 측정합니다.
- 프로세스 종료 감지·재시작과 별도 위치의 외부 상태 점검을 구성합니다. 부재중 장애 알림은 사용자가 지정한 채널에 연결합니다.
- 사용자 조치가 필요한 보류·복구 실패 알림도 지정 채널에 연결하고, 알림 전송 실패가 작업 배정과 상태 관측을 막지 않는지 확인합니다.
- 24시간 동안 추가 사용자 지시 없이 작업 발견·개발·검증·다음 작업 선택·필요한 대기와 자동 복구를 관측합니다. 오류는 통제된 방식으로 주입하고 실제 사용 한도를 소진하지 않습니다. 시나리오별 결과와 운영 기록을 남깁니다.

### 완료 기준

- 사용자 PC 없이 원격 서버에서 목표 설정부터 자율 작업 생성·개발·검증·다음 작업까지 동작하며, 4·5단계 검증과 24시간 연속 관측 기록이 있습니다. 단순 생존 시간이나 등록 작업의 재시도만으로 완료 처리하지 않습니다.
- 서버 재시작 후 미완료 실행을 확인하고 정책에 따라 처리를 재개합니다.
- 사용자 취소는 재실행하지 않고, 인증 만료·복구 한도 초과는 알림으로 확인할 수 있습니다.
- 기존 장기 실행 서비스의 디렉터리와 데이터는 수정하지 않습니다.

## 중요한 검증 시나리오

- 동일 등록 요청을 두 번 보내도 Task가 하나만 생성됩니다.
- 두 처리가 동시에 작업 배정을 시도해도 동일 작업에 활성 실행이 둘 생기지 않습니다.
- 이전 Run의 늦은 결과가 새 실행의 최종 상태를 덮어쓰지 않습니다.
- 서버·Codex 실행이 재시작하거나 외부 서비스 연결이 끊겨도 작업 이력이 보존됩니다.
- 완료 처리와 취소 요청이 거의 동시에 발생할 때 상태 전이 규칙에 따라 일관된 최종 결과를 남깁니다.
- 한도 도달·인증 실패로 즉시 무한 재시도하거나 인증 방식을 자동 전환하지 않습니다.
- 같은 계정의 한도에 걸린 뒤 다른 프로젝트를 통해 호출을 반복하지 않으며, 다음 시도 시각에는 확인 실행 하나만 시작합니다.
- 보류 작업이 실행 가능한 작업의 배정을 막지 않습니다. 기존 실행의 종료 여부가 불명확하면 동시 실행 한도를 지키기 위해 새 AI 실행을 보류하되 서비스 관측은 계속합니다.
- 재시도 정책·횟수·다음 시도 시각·누적 실행 시간·계정 차단·취소 요청이 재시작 후에도 유지됩니다.
- 입력 경로의 범위 이탈, 심볼릭 링크 우회, 셸 인자 주입을 차단합니다.
- 브라우저 흐름에서 작업 등록, 진행 확인, 결과 조회, 취소가 실제로 연결됩니다.
- 프로세스 생존·로그 출력만으로 실제 진척을 표시하지 않고, 출력 없음만으로 종료를 확정하지 않습니다.
- 관측 실패나 오래된 상태를 현재 정상으로 표시하지 않습니다.
- 분석 작업 취소와 제한 시간이 별도로 관측 중인 장기 실행 서비스를 종료하지 않습니다.
- agent-hub 전체 종료 시 브라우저와 외부 점검에서 접근 불가를 확인할 수 있습니다.

각 시나리오는 해당 기능을 구현하는 단계에 추가합니다. 문서만 존재하는 단계에서 동작 테스트가 통과했다고 표시하지 않습니다.

### 1. 구조 검토

A1 [CRITICAL, confidence: 9/10] **실행을 더 기다리지 않는 것과 실행 종료를 확인하는 것이 구분되지 않는 인터페이스입니다.** `analysis.ts:7`은 `Promise<AnalysisResult>`만 반환하고, `run-task.ts:86`은 종료 보장을 하지 못한다고 명시합니다. 현재는 안전하게 보류하지만 이 상태로 재개 기능을 붙일 수는 없습니다.

채택한 안은 SDK를 같은 패키지의 관리 대상 자식 프로세스에서 실행하고, 실행 식별자·중단 요청·종료 관측을 공통 실행 계약으로 전달하는 것입니다. SDK 코드를 직접 수정하지 않습니다. 실제 종료 확인은 지원 OS와 설치한 SDK에서 증명한 범위에 한정합니다. 프로세스 그룹에 신호를 보냈다는 사실만으로 그룹을 벗어난 자식까지 종료됐다고 처리하지 않습니다. 관리 프로세스 자체가 강제 종료돼 확인할 수 없거나, 구버전 기록에 실행 식별 정보가 없으면 보류를 유지합니다.

**T2 구현 중 조정:** 실제 SDK·모의 CLI 실험에서 정상 응답과 취소 후 모두 분리된 손자가 남았습니다. Node 자식으로 감싸는 것만으로는 전제 조건이 충족되지 않아 로컬 Run 전용 컨테이너를 선택했습니다. 기존 직접 실행은 유지하고 설정으로 선택합니다. 전체 ID·실행 토큰·Docker 엔진을 대조한 관측만 복구 근거로 삼습니다. [이유·대안·검증](03-technology-decisions.md#실행-전체의-종료-확인--2026-11-03)을 기록했습니다.

구조가 다른 대안도 비교했습니다.

| 안 | 호출 경계 | 장점 | 비용·판단 |
| --- | --- | --- | --- |
| A. SDK를 관리 대상 로컬 자식에서 실행 | 업무 코드 → 공통 실행 계약 → 로컬 자식 → 기존 SDK 어댑터 | 기존 설정·이벤트 변환을 재사용하고 프로세스 수명을 실행 어댑터 안에 둠 | 자식 통신·종료 확인 필요. 우선 선택하고 실제 종료 근거 확보를 선행 검증 |

두 안 모두 새 서버를 배포하지 않습니다. `start → cancel → observe`의 내부 구현은 어댑터가 소유하고, DB 쓰기와 복구 정책은 부모의 실행 모듈이 소유합니다. 기본 라이브러리와 기존 SDK를 사용하는 [Layer 1] 선택입니다. 실제 관측으로 안 A의 조건을 충족하지 못하면 무리하게 재개를 허용하지 않고, 구현 근거를 기록한 뒤 종료 관측 부분을 재설계합니다.

### 적용 방식과 대안

내부 에이전트에는 **gstack에서 가져와 실행 환경에 맞게 수정한 역할별 지침**을 제공합니다. 첫 연동의 모드는 `adapted_instructions`입니다. 원본 버전·원본 파일·수정한 내용·지침 해시를 공개 파일에 남깁니다. 실제 gstack CLI 실행이나 전체 스킬 절차를 끝냈다는 의미로 사용하지 않습니다. 테스트 실행·취소·예산·변경 반영은 기존 서버가 담당합니다.

| 역할 | 참고하는 gstack 지침 | 적용할 행동 |
| --- | --- | --- |
| 총괄·계획 | `plan-eng-review`의 구조·품질·테스트·성능 검토 | 기존 코드와 근거를 읽고 실행 가능한 다음 작업·완료 기준 제안 |
| 개발 | `verify`의 검증 원칙, `investigate`의 원인 분석 | 작은 수정, 실패 원인과 근거 확인, 서버가 수행하지 않은 테스트를 통과했다고 주장하지 않기 |
| 독립 검토 | `review/checklist.md` | 신뢰 경계·데이터·동시성·검증 약화·빠진 요구를 확인하고 구체적인 보완 의견 반환 |
| 수동 분석 | 같은 리뷰 체크리스트의 읽기 전용 적용 | 요청 범위의 근거를 확인하고 파일을 바꾸지 않기 |

두 구조를 비교했습니다. **A 선택 [Layer 1]:** 서버와 이미지에 고정한 지침 묶음을 포함하고, 기존 요청·이벤트·Step 저장 경계로 연결합니다. **B:** 전체 gstack 설치와 Bun·Git·상태 폴더·추가 모델·브라우저를 각 실행 환경에 제공하고 무인 실행 계약을 구현합니다. B는 원본 도구 활용 범위가 넓지만 현재 입력에는 Git 이력·도구 상태 저장 공간이 없고 검토자는 읽기 전용입니다. A는 현재 역할의 판단 기준을 적용하면서 기존 실행 제약을 유지합니다. 전체 CLI·브라우저·배포 스킬 지원은 별도 능력으로 구분하며, 이 지침 연동의 완료 결과로 주장하지 않습니다. 필요 기능이 원본 도구 실행을 요구하면 해당 실행기와 검증을 추가한 뒤 지원한다고 표시합니다.

지침 파일의 명령을 그대로 실행하거나 프로젝트의 `SKILL.md`를 자동으로 읽지 않습니다. 사용자 질문·자동 업그레이드·텔레메트리·외부 모델·원격 배포 지시는 제품용 지침에 포함하지 않습니다. 수정·검증·승인의 권한은 서버 규칙에 남습니다. 이 차이는 묶음의 NOTICE와 적용 모드에 명시합니다.

### Architecture review

**A1 — 서버 실행 방식.** 두 구조를 비교했습니다. A는 백엔드·HTTPS 프록시 모두 컨테이너로 운영하며 호스트 Docker를 제어합니다. 배포 묶음은 간결하지만 실행기에 전달하는 절대 경로와 컨테이너 안팎 경로를 함께 관리해야 합니다. B는 Linux 호스트의 systemd가 Node 서버를 관리하고 Caddy가 HTTPS를 종료하며, 기존 Docker 실행기를 그대로 사용합니다. 첫 버전은 B를 선택합니다. 기존 경로·종료·소유권 규칙을 재사용할 수 있기 때문입니다. Docker 소켓 접근 권한을 가진 서버는 신뢰하는 관리 프로그램이며, 작업 컨테이너의 제한과 서버 자체의 권한을 혼동하지 않습니다.

**A2 — 저장·백업 경계.** 앱 배포 파일과 비공개 상태·설정·인증을 나눕니다. DB·개발 Git·준비한 입력을 같은 백업 시점으로 묶습니다. 처음에는 서버를 멈춘 상태의 백업을 지원합니다. 실행 소유권과 미확정 실행·반영을 검사하고, 복원 미리보기에서 저장 경로·해시·스키마·Git 일치를 확인합니다. 첫 복원 계약은 같은 절대 경로·호환 앱 버전입니다. 운영 데이터를 덮어쓰기 전에 빈 복원 위치에서 검증하며, 임의 경로 이동·온라인 Git 변경 중 백업은 지원했다고 표시하지 않습니다. DB만 복사하는 대안은 WAL 및 Git 반영 기록을 함께 보존하지 못하므로 채택하지 않습니다.

**A3 — 장애 감지와 알림.** systemd는 부모 프로세스의 종료를 감지합니다. 별도 위치의 외부 점검은 HTTPS 접근과 `/health/ready`를 확인합니다. 앱 내부는 인증 실패·복구 한도 초과 등 사용자 조치가 필요한 상태를 알립니다. 정상 대기·예산 대기와 장애를 구분하고, 긴 실행 동안 대기열의 마지막 점검 시각이 오래됐다는 이유만으로 죽었다고 판정하지 않습니다. 알림은 제한 시간·재시도 상한·중복 억제를 갖고, 전송 실패가 작업 배정이나 상태 저장을 막지 않게 합니다. 실제 수신처 적용 전에는 소유한 로컬 수신기만 사용합니다.

**A4 — 배포와 검증 경계.** 설치를 자동 실행하는 스크립트 대신 검토 가능한 서비스·프록시·로그 설정과 실행 절차부터 제공합니다. Node·pnpm·앱 의존성은 저장소의 고정 버전을 사용하고, Linux 도구의 실제 검사 버전도 기록합니다. 앱 교체는 서버 중지 → 백업 → 검증한 빌드 교체 → 시작 → 상태 확인 순서입니다. DB 마이그레이션 이후 예전 실행 파일만 되돌리는 것을 복구로 안내하지 않습니다.

```text
브라우저 → Caddy HTTPS → 127.0.0.1의 인증된 Node 서버
                            ├─ SQLite + 비공개 개발 Git + 준비한 입력
                            └─ 기존 Docker 개발 / 테스트 / 독립 검토
systemd → 부모 종료 감지·제한된 재시작 → 기존 실행 대조·복구
외부 점검 → HTTPS / DB 준비 상태 → 지정한 알림 수신처
서버 중지·실행 대조 → 일관된 백업 → 미리보기·무결성 검사 → 복원
```

새 공개 모듈의 책임은 운영 보존·전달에 둡니다. 업무 실행 상태의 소유자는 기존 서버입니다. 얕은 전달 계층, 단계별로 흩어진 백업 모듈, 별도 상태 사본, 두 큐, 임의 내부 import, 수동으로 맞추는 스키마 목록을 추가하지 않습니다. 배포 설정의 고정 경로는 한 운영 문서에서 관리하고 실제 설정 검사로 불일치를 찾습니다. Dispositions: A1~A4 accepted(사용자의 자율 진행 지시, R1~R4).

**P1 — 측정 전 사양 확정 금지.** F3의 337.0MiB는 부모 Node의 표본 최대 RSS입니다. Docker·OS·동시 서비스가 빠져 있어 서버 최소 사양으로 쓰지 않습니다. 대표 작업의 CPU·전체 메모리·디스크 증가량과 종료 후 반환을 따로 측정합니다. 측정 때문에 실행 중 SQLite를 외부 도구로 반복 열 필요는 없습니다.
