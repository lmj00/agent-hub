# agent-hub

여러 프로젝트의 목표를 맡기면, AI 에이전트들이 스스로 할 일을 찾고 개발·검증·개선을 이어가는 개인용 프로젝트 관리 시스템입니다.

사용자는 프로젝트별 목표·우선순위·허용 범위를 설정합니다. 총괄은 현재 코드와 작업 이력을 바탕으로 다음 작업을 만들고, 개발·검증 역할의 에이전트가 결과와 피드백을 주고받습니다. 작업이 끝나면 다음 작업을 선택하므로 매번 사용자의 새 지시가 필요하지 않습니다. 사용자는 진행 상황을 확인하고 목표를 바꾸거나 실행을 멈출 수 있습니다.

현재는 **실제 AI 연결·관리 화면·서비스 관측·자동 복구를 거쳐 목표 기반 계획 기능을 구현 중**입니다. 프로젝트·작업 등록·조회, Codex 읽기 전용 분석, 자동 대기열과 종료 확인 후 재개·취소가 동작합니다. 자동 복구를 켜면 일시적 연결 오류와 서버 재시작 뒤 종료가 확인된 작업을 정해진 횟수 안에서 다시 시도합니다. 사용 한도에 도달하면 계정 전체를 보류하고 제한된 확인 실행으로 회복을 검사합니다. 추론 강도 자동 선택과 제한된 다단계 분석도 지원합니다. 프로젝트 목표·완료 기준·허용 범위·예산의 등록과 버전별 이력, 프로젝트·목표별 기간 예산을 지원합니다. 내부 계획 모듈은 허용한 코드·작업 이력·서비스 관측을 참고해 다음 작업을 검증하고 저장합니다. 목표 등록 후 자동 계획을 시작하는 연결과 실제 코드 변경·배포는 아직 완료하지 않았습니다.

## 첫 번째 목표

> 예제 앱에 “기본 학습 흐름을 완성하고 테스트로 검증해줘”라는 목표를 설정한다. 이후 사용자 입력 없이 미완성 기능을 찾아 작업으로 만들고, 개발·검증·필요한 재작업을 수행한 뒤 다음 작업으로 넘어간다. 관리 화면에서 선택 이유와 변경 결과를 확인할 수 있고, 서버를 재시작해도 이어서 처리한다.

MVP는 핵심 목적을 실제로 수행할 수 있는 첫 운영 버전입니다. 이 프로젝트에서는 02 문서의 6단계까지 완성한 자율 운영 버전을 뜻합니다. 1단계의 등록·조회와 2단계의 읽기 전용 분석은 연결을 검증하는 중간 단계입니다. 5단계에서 자율 작업 생성·개발·검증을 연결하고, 6단계에서 클라우드 무인 운영을 검증합니다.

| 범위 | 첫 버전의 기준 |
| --- | --- |
| 운영 규모 | 사용자 한 명, 서버 한 대, 백엔드 한 개, 동시 실행 Run 한 개. 그 안의 AI 호출은 순차 실행 |
| 프로젝트 작업 | 목표에 따른 작업 자동 생성, 분리된 개발 작업 공간에서 코드 수정·테스트 |
| 에이전트 협업 | 총괄·개발·검증 역할이 기록을 주고받으며 순차 실행. 병렬 실행은 후속 확장 |
| 다음 작업 | 완료·검증 결과와 프로젝트 상태를 반영해 자동 선택. 주기적으로 새 변화도 확인 |
| 변경 결과 | 검증된 변경을 개발용 브랜치에 축적. 외부 푸시·기본 브랜치 병합·운영 배포는 별도 정책 |
| 진행 확인 | 현재 단계, 최근 활동·진척, 대기 사유와 다음 행동 표시 |
| 기존 서비스 관측 | 상태를 읽기만 하고 정상 동작·정상 대기·관측 실패를 구분 |
| 무인 복구 | 사용 한도 대기 후 자동 재개, 일시적 오류의 제한된 재시도 |
| 사용자 조치 | 사용자 취소는 자동 재시도하지 않으며, 인증 만료·복구 한도 초과는 보류·알림 |
| 추론 강도 | 다음 호출마다 `medium`·`high`·`xhigh` 중 선택. 최소·기본값은 `medium` |

24시간 운영의 핵심은 사용자 부재중에도 목표에 맞는 일을 발견하고 수행하는 반복 흐름입니다. 대기열이 비면 목표와 현재 상태를 다시 평가합니다. 할 일이 없거나 실행 예산이 부족하면 이유와 다음 점검 시각을 기록하고, 조건이 충족되면 자동으로 이어갑니다. 유한한 목표는 완료로 닫고, 지속 관리 목표는 정해진 주기로 점검합니다. effort는 단계 난이도에 따라 높이거나 낮추며 실제 지원 범위와 실행 예산은 백엔드가 확인합니다.

작업 관리와 실행은 같은 프로그램 안에서 나눕니다. 코드는 기능별로 모으고, 업무 규칙은 HTTP·DB·AI SDK 사용 코드에서 분리합니다. 단순한 기능에 불필요한 계층을 추가하지 않습니다. 작업 취소와 제한 시간은 해당 AI 실행에만 적용하며, 관측 중인 다른 서비스를 종료하지 않습니다.

## 기술 스택

| 영역 | 선택 | 역할 |
| --- | --- | --- |
| 언어 | TypeScript | 화면·서버·실행 프로그램의 데이터 형식 공유 |
| 관리 화면 | React + Vite | 프로젝트, 작업 목록, 진행 상황, 결과 표시 |
| 총괄 서버 | Node.js + Fastify | 인증, 작업 등록·배정, 상태·결과 저장 |
| 내부 실행 모듈 | Node.js + Codex SDK | 프로젝트 준비, 에이전트 실행, 결과 기록 |
| 데이터 저장 | SQLite | 프로젝트 설정, 작업, 실행 이력, 이벤트 저장 |
| 테스트 | Vitest + Playwright | 상태 전이와 주요 사용자 흐름 검증 |
| 배포 | Docker Compose | 서비스 실행 환경과 재시작해도 데이터가 남는 저장 공간 구성 |

개발 환경은 Node.js 24 LTS와 pnpm을 사용합니다. SQLite는 better-sqlite3와 Drizzle ORM·Kit으로 연결합니다. 의존성은 `package.json`과 `pnpm-lock.yaml`에 고정했습니다. 초기 SQLite 기반은 macOS arm64·Linux arm64에서, 현재 Codex 연동은 macOS arm64에서 검증했습니다. [대안 비교와 선택 이유](docs/03-technology-decisions.md)를 기록합니다.

## 로컬 실행

저장소 루트에서 실행합니다. Node.js는 [`.nvmrc`](.nvmrc)의 24.22.1, pnpm은 [`package.json`](package.json)의 12.16.1을 준비합니다. [nvm](https://github.com/nvm-sh/nvm)을 사용한다면 다음과 같이 맞출 수 있습니다.

```sh
nvm install
nvm use
npm install --global pnpm@12.16.1
```

의존성을 설치하고 개발 서버를 실행합니다. `pnpm dev`는 소스가 바뀌면 서버를 다시 시작합니다.

```sh
pnpm install --frozen-lockfile
LOCAL_API_ONLY=1 pnpm dev
```

다른 터미널에서 응답을 확인합니다.

```sh
curl http://127.0.0.1:3000/health/live
curl http://127.0.0.1:3000/health/ready
```

위 명령은 인증 없는 로컬 API 개발 모드를 명시적으로 켭니다. 이 README의 curl 예제는 이 모드를 기준으로 합니다. 로그인 기능을 사용할 때는 아래 `AUTH_CONFIG` 방식으로 실행하며, `/health/live` 외 데이터 API에는 로그인 세션이 필요합니다. 둘 중 하나를 정하지 않은 서버는 시작하지 않습니다.

서버 응답 확인(`/health/live`) 예시:

```json
{"status":"ok","checkedAt":"2026-10-29T00:00:00.000Z"}
```

DB 준비 상태(`/health/ready`) 예시:

```json
{"status":"ok","database":"ok","checkedAt":"2026-10-29T00:00:00.000Z"}
```

| API | 확인하는 범위 |
| --- | --- |
| `/health/live` | 서버가 HTTP 요청에 응답하는지 확인 |
| `/health/ready` | 프로젝트·작업·실행·실행별 컨테이너·호출 단계·이벤트·실행 소유권·제공자 차단·복구 요청·로그인 세션·서비스 대상·관측 결과·목표·목표 이력·예산 정책·기간·실행 예약·계획 예약 테이블을 조회하는지 확인. 성공하면 200, 실패하면 503 |

두 응답 모두 `checkedAt`에 UTC 관측 시각을 담고 `Cache-Control: no-store`를 지정합니다. 실행 중 DB 조회가 실패해도 서버 응답 여부는 별도로 확인할 수 있습니다. DB 준비 상태는 조회 기준이며, AI 실행 준비 상태는 해당 단계에서 추가합니다.

현재 서버는 같은 컴퓨터에서 접속하는 `127.0.0.1`에 바인딩합니다. 포트의 기본값은 3000이며, `LOCAL_API_ONLY=1 PORT=4000 pnpm dev`처럼 셸 환경 변수로 바꿀 수 있습니다. `PORT`는 1~65535의 정수여야 합니다. 종료할 때는 `Ctrl+C`를 누릅니다.

| 명령 | 하는 일 |
| --- | --- |
| `pnpm dev` | TypeScript 소스로 개발 서버 실행·변경 감지. AUTH_CONFIG 또는 LOCAL_API_ONLY 지정 필요 |
| `pnpm dev:web` | 화면 변경을 감지해 다시 빌드. 별도 터미널에서 개발 서버 실행 필요 |
| `pnpm typecheck` | 공통 계약·서버·화면 코드와 테스트의 타입 검사 |
| `pnpm test` | 자동 테스트 한 번 실행 |
| `pnpm test:browser` | 빌드 후 Chromium에서 임시 DB·가짜 AI로 주요 화면 흐름 검증 |
| `pnpm build` | 공통 계약·서버·화면을 각 패키지의 `dist`에 빌드 |
| `pnpm start` | 빌드한 서버 실행. 먼저 `pnpm build` 및 접근 모드 설정 필요 |
| `pnpm auth:setup --config .local/auth.json --origin http://127.0.0.1:3000` | 비공개 로그인 설정과 무작위 비밀번호 생성 |
| `pnpm db:generate --name=변경이름` | 스키마와 이전 기록을 비교해 SQL 마이그레이션 생성 |
| `pnpm task:run --task 작업ID --config 설정파일절대경로` | 등록된 대기 작업 한 건을 실제 Codex로 분석하고 결과 저장 |

서버는 `apps/server`, 화면은 `apps/web`, 공통 요청·응답 형식은 `packages/contracts`에 있습니다. 서버의 `main.ts`는 시작·종료, `app.ts`는 DB와 기능 연결, `config.ts`는 환경 변수 확인을 담당합니다. DB 코드는 `db/`, 기능별 코드는 `modules/`에 둡니다. `run-task-cli.ts`는 분석 실행의 CLI 진입점입니다. 루트 실행 명령은 필요한 공통 패키지를 먼저 빌드합니다.

### GitHub 자동 검사

[`CI`](.github/workflows/ci.yml)는 `main` 푸시와 PR마다 Ubuntu 22.04·24.04에서 잠금 파일을 유지한 설치·타입 검사·빌드·테스트를 실행합니다. Node.js와 pnpm 버전은 저장소 설정을 읽습니다. Docker 종료·권한 제한 테스트와 Chromium 화면 테스트도 포함합니다. 실패한 화면의 추적 자료는 7일간 보관합니다.

GitHub가 제공하는 임시 실행 서버에서 합성 인증과 가짜 AI 실행기를 사용하며, 개인 Codex 인증·실제 모델 호출·배포는 연결하지 않습니다. 로컬 전체 검증은 `RUN_CONTAINER_TESTS=1 pnpm test`와 `pnpm test:browser`로 실행할 수 있습니다. 자동 검사의 성공 여부는 저장소의 Actions에서 해당 커밋 결과를 확인합니다.

기본 Docker 정책에서는 Codex의 중첩 샌드박스 생성이 거부될 수 있어 전용 seccomp·AppArmor 정책을 적용합니다. 정책의 근거와 설치 방법은 아래 컨테이너 실행 안내에 있습니다. 초기화 실패는 설정 문제로 보류하며, 샌드박스를 끄거나 실패한 분석을 성공으로 표시하지 않습니다.

## 단일 사용자 로그인 설정

기본 비밀번호는 없습니다. 다음 명령은 로그인 설정 파일을 소유자만 읽을 수 있는 권한으로 만들고, 생성한 비밀번호를 한 번 출력합니다. 비밀번호는 따로 저장하고 설정 파일은 Git에 넣지 않습니다. 저장 파일에는 비밀번호 해시·세션 서명 키·접속 주소만 남습니다.

```sh
pnpm auth:setup --config .local/auth.json --origin http://127.0.0.1:3000
pnpm build
AUTH_CONFIG=.local/auth.json pnpm start
```

`origin`은 브라우저에서 접속할 정확한 주소이며 경로·끝의 슬래시는 넣지 않습니다. HTTP는 `127.0.0.1`·`localhost`·`[::1]`만 허용합니다. 원격 주소는 HTTPS를 지정하며 실제 원격 배포·프록시 구성은 6단계입니다. 서버 자체는 계속 루프백 주소에 연결합니다.

직접 정한 비밀번호를 쓰려면 `--password-stdin`을 추가하고 표준 입력으로 전달합니다. 비밀번호는 12자 이상·1024바이트 이하여야 하며 명령 인자로 받지 않습니다. 기존 설정 파일은 덮어쓰지 않습니다. 비밀번호를 바꿀 때는 새 파일을 만들고 `AUTH_CONFIG`를 변경해 서버를 다시 시작합니다. 새 서명 키를 사용하므로 이전 로그인 쿠키도 무효가 됩니다.

| API | 사용 방법 |
| --- | --- |
| `GET /auth/session` | 로그인 여부·변경 요청용 `csrfToken`·로그인 만료 시각 조회. 처음에는 임시 쿠키 발급 |
| `POST /auth/login` | 임시 쿠키와 `X-CSRF-Token` 헤더, JSON `{ "password": "입력한 비밀번호" }` 전송. 성공 시 새 쿠키·새 토큰 발급 |
| `POST /auth/logout` | 로그인 쿠키와 현재 토큰으로 세션 삭제. 204 응답 |

로그인한 뒤 데이터 API에는 쿠키를 보내고 등록·취소·재개 같은 변경 요청에는 `X-CSRF-Token`도 보냅니다. 잘못된 비밀번호는 401, 요청 위조·접속 주소 불일치는 403, 반복 로그인 제한은 429입니다. 로그인 세션은 8시간 뒤 만료되며 상태를 계속 조회해도 늘어나지 않습니다. 로그인 전 임시 세션은 10분입니다. 세션은 SQLite에 저장하므로 서버 재시작 후에도 유효 기간 안에서 유지되고, 로그아웃한 쿠키를 복사해 다시 보내도 인증되지 않습니다.

`AUTH_CONFIG`와 `LOCAL_API_ONLY=1`은 함께 사용할 수 없습니다. 로컬 API 모드도 외부 Origin·잘못된 Host의 요청은 거부합니다. 로그인 설정과 DB를 분석 작업 폴더 안에 두면 AI 배정을 거부합니다. 자동 분석까지 켤 때는 `AUTH_CONFIG=.local/auth.json EXECUTION_CONFIG=.local/execution.json pnpm start`로 실행합니다.

## 관리 화면 사용

위 로그인 모드로 서버를 실행한 뒤 설정한 주소를 브라우저에서 엽니다. 빌드한 화면은 Fastify가 API와 같은 주소에서 제공합니다. 화면 파일이 없거나 로컬 API 전용 모드이면 관리 화면을 제공하지 않습니다.

1. 초기 설정에서 만든 비밀번호로 로그인합니다.
2. 프로젝트 이름과 실행 설정에 등록한 `workspaceKey`를 입력합니다. 프로젝트 등록이 작업 폴더를 자동으로 만들지는 않습니다.
3. 분석 지시를 입력합니다. `EXECUTION_CONFIG`를 지정하지 않았다면 작업은 대기 상태로 남고 화면에도 자동 실행이 꺼졌다고 표시합니다.
4. 작업을 선택해 실행 시도, 모델·추론 강도, 최근 활동과 결과를 확인합니다. 읽기 전용 분석이며, 기본 `medium` 또는 자동 선택한 추론 강도와 이유를 표시합니다.
5. 필요한 경우 취소·종료 확인·재개를 요청합니다. 요청 접수와 처리 완료는 구분해서 표시하며, 재개 판단은 서버가 수행합니다. 종료 확인을 지원하는 컨테이너 실행 설정이 필요합니다.

화면은 3초 간격으로 상태를 조회하며, 복구 접수는 1초 간격으로 확인합니다. 통신이 끊기면 마지막 기록과 확인 시각을 표시하고 로그인 만료 시 로그인 화면으로 돌아갑니다. 분석 결과는 HTML을 실행하지 않는 텍스트로 보여줍니다. 프로젝트 선택·입력 중인 지시·화면에서 확인 중인 접수 ID는 새로고침하면 초기화되지만 서버에 접수한 작업과 기록은 DB에 남습니다.

화면을 수정할 때는 한 터미널에서 `pnpm dev:web`, 다른 터미널에서 `AUTH_CONFIG=.local/auth.json pnpm dev`를 실행합니다. 첫 화면 빌드가 끝난 뒤 서버를 시작하고, 화면 변경은 브라우저 새로고침으로 확인합니다. 별도 Vite 웹 서버나 CORS 설정 없이 동일한 로그인 주소를 유지합니다.

브라우저 테스트 최초 실행에는 Chromium을 준비합니다. 테스트는 별도 임시 DB와 테스트 전용 로그인·AI 대역·상태 API를 사용하며 실제 계정이나 작업 폴더를 읽지 않습니다. 로컬 4320·4321 포트를 사용하며 기존 서버를 재사용하지 않습니다.

```sh
pnpm --filter @agent-hub/web exec playwright install chromium
pnpm test:browser
```

실제 Codex 연결은 별도로 검증했습니다. 화면에서 분석 등록·결과 조회·실행 중 취소·컨테이너 종료와 대상 파일 불변을 확인했으며, 이 실제 호출은 자동 브라우저 테스트에 포함하지 않습니다.

## 프로젝트 목표 관리

프로젝트를 선택한 뒤 **프로젝트 목표 → 목표 등록 +**에서 목표와 완료·평가 기준을 저장합니다. 유한한 목표와 지속 관리 목표를 구분하고, 우선순위·허용/제외 경로·점검 간격·기간 예산을 설정할 수 있습니다. 기본값은 15분 점검, 1시간당 최대 20호출·30분 실행입니다.

목표 관리와 실행 전 상태·버전 검사, 기간 예산 집행을 구현했습니다. 목표에 연결된 작업은 목표가 일시정지·완료됐거나 판단 당시 버전이 달라지면 새 실행을 시작하지 않습니다. 등록만으로 AI가 새 작업을 만들거나 코드를 수정하지는 않습니다. 작업 생성·점검 예약은 후속 단위에서 연결합니다. 현재 등록 API로 만드는 수동 분석 작업은 Goal에 연결되지 않으며 프로젝트 예산을 적용합니다.

작업 조회에는 종류(`kind`: 계획 `planning` 또는 실제 작업 `work`), 목표 ID(`goalId`), 판단 당시 버전(`goalVersion`)을 포함합니다. 기존 수동 작업은 `work`와 두 개의 `null` 값으로 유지합니다. 실행 이력에는 시작할 때의 목표 버전을 남기므로 이후 목표를 수정해도 과거 실행의 기준은 바뀌지 않습니다. 계획에서 만든 작업은 목표 재개·변경 때 대상 경로를 재검사합니다. 현재 범위에 맞으면 같은 Task의 버전과 최근 검사 근거(`goalReview`)를 갱신하고, 벗어나면 범위 제외로 취소합니다. 기존 실패·대기·재시도 제한과 과거 Run 버전은 유지합니다. 경로 근거가 없는 이전 작업이나 종료 미확인 작업은 자동으로 재연결하지 않습니다.

목표 수정·일시정지·재개마다 버전을 올리고 이전 내용을 **변경 이력**에 남깁니다. 목표 일시정지는 기존 수동 작업의 취소가 아니며, 실행 중 분석은 작업의 취소 버튼으로 중단합니다. 화면에서 확인한 버전이 이미 바뀌면 저장을 거부하므로 입력을 닫고 최신 목표를 다시 열어 수정합니다. 사용자가 임의로 목표를 완료 처리하는 API는 제공하지 않습니다.

| API | 동작 |
| --- | --- |
| `POST /projects/:projectId/goals` | `{ requestKey, definition }`으로 목표 등록. 처음 201, 같은 요청 재전송은 기존 응답 200 |
| `GET /projects/:projectId/goals` | 프로젝트의 목표 목록 |
| `GET /goals/:id` | 현재 목표 |
| `GET /goals/:id/revisions` | 이전 내용을 최신 버전부터 조회 |
| `PATCH /goals/:id` | `{ requestKey, expectedVersion, definition }`으로 전체 정의 수정 |
| `POST /goals/:id/control` | `{ requestKey, expectedVersion, action: "pause" 또는 "resume" }` |

`definition`의 예시는 아래와 같습니다. 경로는 등록된 작업 폴더 기준이며 절대 경로·상위 폴더 이동·글롭 패턴을 받지 않습니다. 점(`.`)은 작업 폴더 전체, 제외 경로는 하위 폴더까지 뜻합니다. 목표에 연결된 작업은 아래 자료 준비 단계에서 이 범위를 적용합니다. 현재 공개 작업 등록 API는 목표 없는 수동 분석만 만듭니다. 내부 계획 모듈의 작업 생성은 구현했지만 목표 등록만으로 자동 호출하지는 않습니다.

```json
{
  "description": "단어 복습 흐름을 완성한다",
  "completionCriteria": "복습 결과와 날짜가 저장되고 테스트를 통과한다",
  "kind": "finite",
  "priority": 50,
  "allowedPaths": ["src", "tests"],
  "excludedPaths": ["src/private"],
  "checkIntervalMs": 900000,
  "budget": { "windowMs": 3600000, "maxCalls": 20, "maxRunMs": 1800000 }
}
```

우선순위는 0~100이며 큰 값이 우선입니다. 점검 간격은 1분~24시간, 예산 기간은 10분~24시간, 호출 상한은 1~1,000회, 실행 시간 상한은 1초~예산 기간입니다. 이는 프로그램의 실행 한도이며 실제 구독 잔여량이 아닙니다. 요청 키는 응답 유실 뒤에도 같은 내용을 다시 보내는 데 사용합니다. 같은 키로 내용을 바꾸면 409, 오래된 버전으로 수정하면 `GOAL_VERSION_CHANGED` 409입니다.

### 목표에 허용한 파일 준비

목표에 연결된 작업을 실행할 때는 원본 작업 폴더를 그대로 제공하지 않습니다. 최초 커밋이 있고 커밋하지 않은 변경이 없는 Git 저장소의 최상위 폴더에서, 허용 경로에 해당하는 커밋 파일만 별도 폴더에 준비합니다. 제외 경로와 알려진 인증·환경 설정·DB 파일은 포함하지 않으며, 선택 범위에 심볼릭 링크나 서브모듈이 있으면 보류합니다. Git 필터가 설정된 저장소도 자동 명령 실행을 막기 위해 보류합니다.

현재 상한은 파일 500개, 개별 파일 1MiB, 전체 8MiB입니다. 초과하면 일부만 읽은 결과를 전체 결과로 표시하지 않고 `input_unavailable`로 보류합니다. 준비 중 목표가 바뀌면 호출을 시작하지 않고, 실행 중 원본 코드나 목표가 바뀌면 결과를 성공으로 반영하지 않습니다. 허용 범위를 줄이면 중단 요청도 저장하며, 실행기는 출력이 없는 동안에도 이 요청을 확인합니다. 파일 내용에 포함된 모든 비밀을 자동 탐지하는 기능은 아니므로 인증 정보가 없는 예제 저장소부터 사용합니다.

준비한 파일은 DB 옆의 비공개 폴더에 두고, 종료 확인을 DB에 저장한 뒤 정리합니다. 서버 재시작 시에도 확인된 실행의 미완료 정리를 다시 수행합니다. 종료를 증명하지 못하면 파일과 기록을 보존합니다. 이 자료 준비 기능은 서버와 CLI에 함께 적용되며, 코드 수정 권한을 추가하지 않습니다.

### 내부 계획 모듈의 현재 범위

목표마다 진행 중인 계획 하나를 예약하고, 허용한 파일·코드 버전·최근 작업 결과를 총괄 호출에 전달합니다. 결과는 작업 제안·대기·완료 제안으로 구분합니다. 서버가 목표 버전·자료 해시·경로·중복 여부를 검사하고, 실행 종료를 확인한 뒤 계획 반영과 후속 작업 저장을 함께 확정합니다. 대기 판단에는 다음 점검 시각을 남깁니다. 완료 제안만으로 목표를 완료 처리하지 않습니다.

종료된 취소·실패 작업의 대상 경로와 겹치는 새 제안은 제외하고, 관련 없는 경로의 작업은 생성할 수 있습니다. 제목·목표 버전·기준 커밋이 달라져도 이 검사는 유지합니다. 아직 실행·복구 중이거나 경로 근거가 없는 작업은 해당 목표의 계획을 보류합니다. 같은 파일 안의 서로 다른 문제까지 구분하는 의미 분석은 아니며, 같은 파일의 별도 작업도 보류할 수 있습니다.

계획 호출에는 같은 프로젝트에 설정한 서비스의 관측도 전달합니다. 현재 수집 실패·오래된 정보·관측 꺼짐과 과거 수집 성공을 구분하며, 모델 호출 전에 선정한 자료를 저장합니다. 실행 상세의 **계획에 사용한 관측**에서 당시 시각·관측 ID·상태·발췌 개수를 확인할 수 있습니다. 자료가 길면 과거 기록과 파일 목록을 일부 생략하고 개수를 표시하며, 목표와 허용 범위는 자르지 않습니다. 현재 관측은 프로세스·업무 상태이며 트레이딩 전략의 수익률·위험 지표를 평가하는 기능은 아직 없습니다.

이 모듈은 내부 검증 경로에 연결돼 있습니다. 목표 변경 후 기존 계획 작업의 범위 재검사는 연결했습니다. 취소한 계획 생성 작업의 명시적 재허용도 연결했습니다. 자동 계획 시작과 실제 개발 실행은 남아 있습니다. 계획에서 만든 개발 작업은 현재 `queued`로 보존하고 `development_pending`으로 배정을 보류합니다. 읽기 전용 분석의 성공을 코드 구현 완료로 처리하지 않습니다.

계획에서 만든 작업을 취소한 뒤에는 상세 화면의 **취소한 작업 다시 허용**으로 새 작업을 이어갈 수 있습니다. 현재 활성 목표의 범위에 맞고 모든 이전 실행의 종료가 확인돼야 합니다. 원본 취소 기록은 유지하며, 이전 작업으로 이동할 수 있는 연결을 남깁니다. 재시도 횟수·같은 오류 반복·누적 실행 시간과 계정 차단·기간 예산은 초기화하지 않습니다. 한도가 소진됐거나 목표가 일시정지·완료됐으면 거부합니다.

API는 `POST /tasks/:id/release`에 `{ requestKey, expectedGoalVersion }`을 받습니다. 새 요청은 `201`, 같은 요청을 재전송하면 원래 접수 결과를 `200`으로 반환하고 `Location`에 새 작업 주소를 보냅니다. 이 조작은 새 작업 생성·연결·목표 버전 증가를 함께 저장합니다. 기존 목표 내용은 유지하며, 새 작업의 실행 시점에 허용 범위와 제한을 다시 확인합니다. 일반 수동 분석 작업이나 실패·보류 작업의 복구는 기존 재개 절차를 사용합니다.


## 실행 예산

프로젝트의 **실행 예산**에서 현재 기간의 호출 수·정산 시간·예약 시간을 확인하고 프로젝트 전체의 상한을 수정합니다. 기본 프로젝트 예산은 1시간당 60호출·45분 실행입니다. 목표에 연결된 작업은 목표 예산도 함께 적용합니다. 이는 프로그램이 정한 한도이며 ChatGPT 구독의 남은 사용량은 아닙니다.

기간은 첫 배정 검사 때 시작합니다. 기간 안에서 설정을 바꿔도 이미 쓴 양과 적용 중인 상한을 유지하고, 새 설정은 다음 기간부터 적용합니다. 서버 재시작·새 Task·목표 버전 변경으로 소비 기록을 지우지 않습니다. 사용하지 않은 과거 기간을 밀린 실행으로 처리하지 않습니다.

첫 호출은 Run 생성과 함께, 다음 호출은 Step 생성과 함께 횟수를 예약합니다. 준비 중 실패하거나 실행 여부가 불확실해도 예약한 횟수는 돌려주지 않습니다. 실행 시간은 준비부터 종료 확인까지 계산하며, 종료 확인 전에는 예약 시간을 유지합니다. 종료가 확인되면 실제 시간으로 정산하고 중단 처리 중 초과한 시간도 포함합니다. 종료 증명을 제공하지 않는 직접 SDK 모드는 예약한 시간을 보수적으로 유지합니다.

예산이 부족하면 Task를 `waiting_capacity`로 두고 `budgetWait`에 목표/프로젝트 구분·사유·다음 확인 시각을 저장합니다. 배정 전 대기에는 Run과 추가 재시도를 만들지 않습니다. 기간이 바뀌면 자동 대기열이 다시 검사하며, 종료 미확인·사용자 취소·목표 일시정지·계정 차단·Task 누적 제한은 그대로 적용합니다. 실행 중 기다리게 된 분석은 이전 Step 결과를 보존하고, 재개할 때 최근 분석의 제한된 발췌를 참고 자료로 전달해 현재 파일과 다시 대조하게 합니다.

| API | 동작 |
| --- | --- |
| `GET /projects/:projectId/budget` | 프로젝트 설정 버전·정책과 프로젝트/목표의 최근 기간 사용량 조회. 조회만으로 기간을 시작하지 않음 |
| `PUT /projects/:projectId/budget` | `{ expectedVersion, policy: { windowMs, maxCalls, maxRunMs } }`으로 프로젝트 정책 수정. 현재 기간은 보존, 오래된 설정 버전은 409 |

목표 예산은 기존 목표 수정에서 관리합니다. 프로젝트 설정의 저장 응답이 유실되거나 버전이 달라지면 최신 설정을 다시 열어 확인합니다. DB 준비 상태는 예산 정책·기간·실행 예약 테이블도 함께 조회합니다.

## 기존 서비스의 상태 관측

서비스가 제공하는 **읽기 전용 상태 API**를 주기적으로 읽습니다. 서비스의 시작·중지·재시작이나 설정 변경은 하지 않습니다. AI 작업이 취소되거나 실행 대기열이 보류돼도 관측은 별도로 계속합니다.

먼저 화면에서 프로젝트를 등록하고 왼쪽 **프로젝트 연결 정보**에서 전체 프로젝트 ID를 확인합니다. [설정 예시](examples/service-observation.json)를 비공개 파일로 복사한 뒤 실제 프로젝트 ID·서비스 이름·상태 조회 주소로 바꿉니다. 설정의 상대 파일 경로는 저장소 루트 기준입니다.

```sh
cp examples/service-observation.json .local/services.json
chmod 600 .local/services.json
# .local/services.json의 projectId와 url 등을 실제 값으로 수정
AUTH_CONFIG=.local/auth.json SERVICE_CONFIG=.local/services.json pnpm start
```

AI 분석도 함께 실행하려면 위 명령에 `EXECUTION_CONFIG=.local/execution.json`을 추가합니다. 설정 변경은 서버 재시작 시 적용합니다. 관측 서버도 같은 DB의 실행 소유권을 확보하므로 중복 관측 서버·별도 실행 CLI는 동시에 켜지 않습니다.

| 설정 | 기본값·의미 |
| --- | --- |
| `key`·`projectId`·`name`·`url` | 필수. 대상 식별 키·기존 프로젝트 ID·표시 이름·GET 조회 주소 |
| `intervalMs` | 15,000ms. 이전 조회가 끝난 뒤 다음 조회까지의 최소 간격 |
| `timeoutMs` | 3,000ms. 한 요청의 제한 시간, 100~5,000ms |
| `staleAfterMs` | 최소 60,000ms이며 기본값은 조회 간격의 2배 이상. 수집·보고 시각의 유효 기간 |
| `allowWaiting` | `true`. 서비스가 명시적으로 보고한 입력 대기를 정상으로 인정 |
| `activityTimeoutMs` | 미지정. 업무 처리 중인 서비스의 최근 성공 시각이 너무 오래됐는지 판단하는 선택 기준 |
| `bearerToken` | 필요할 때만 비공개 설정에 지정. GET 요청의 Authorization 헤더로 전송 |

활성 대상은 최대 10개이며 한 번에 한 대상을 조회합니다. 다른 대상의 응답이 늦으면 예정 시각보다 수집이 늦을 수 있습니다. 화면의 다음 시각은 예정이며 마지막 수집·보고 시각을 함께 확인합니다.

상태 API는 `Content-Type: application/json`과 아래 형식을 반환해야 합니다. 시각은 시간대를 포함한 ISO 문자열이며 `observedAt`은 응답을 만들 때의 실제 관측 시각이어야 합니다. 아래 고정 시각을 그대로 응답하면 오래된 정보로 처리됩니다.

```json
{
  "observedAt": "2026-11-03T00:00:00.000Z",
  "processState": "running",
  "activityState": "waiting",
  "lastSuccessAt": "2026-11-02T23:50:00.000Z",
  "nextExpectedAt": null,
  "errorCount": 0,
  "summary": "처리할 새 입력을 기다립니다."
}
```

`processState`는 `running`·`stopped`·`unknown`, `activityState`는 `working`·`waiting`·`degraded`·`unknown`입니다. 성공·예정 시각을 모르면 `null`로 보냅니다. `summary`는 500자, 전체 응답은 16KiB까지입니다. `errorCount`는 서비스가 정한 집계 범위의 오류 수이며 이 값만으로 장애를 판단하지 않습니다.

정상 대기는 최근 성공이 오래됐어도 허용할 수 있습니다. 다만 명시한 다음 업무 예정 시각에서 유효 기간까지 지나면 확인 필요로 표시합니다. 수집·보고 시각이 오래됐거나 응답이 실패하면 이전 기록을 현재 정상으로 보여주지 않습니다. ‘종료 보고’는 상태 API가 전달한 값이며 agent-hub가 대상 서버의 OS 프로세스를 직접 검사했다는 뜻은 아닙니다.

원격 주소는 HTTPS, HTTP는 루프백만 허용합니다. URL의 사용자 정보·쿼리·fragment와 리다이렉트는 허용하지 않습니다. 주소·토큰은 설정에만 두고 DB·조회 API에 연결 설정을 저장하지 않습니다. 관측 결과는 대상별 최근 1,000건과 마지막 수집 성공을 보존하며 조회 API는 최신·마지막 성공 기록을 반환합니다. 대상 주소·판단 기준을 바꾸면 이전 설정의 성공을 현재 근거로 사용하지 않습니다.

`GET /projects/:projectId/services`는 저장된 관측과 현재 판단을 조회하며 호출 자체로 외부 상태 API를 실행하지 않습니다. 설정 없이 재시작하면 과거 기록을 보여주되 관측 꺼짐·상태 미확인으로 표시합니다. 실제 트레이딩 서비스를 연결하거나 변경한 검증은 수행하지 않았습니다.

## 프로젝트 등록·조회

서버를 실행한 뒤 프로젝트 이름과 작업 공간 식별자를 JSON으로 전송합니다. 식별자는 실제 폴더 경로 대신 사용할 이름이며, 아래 실행 설정에서 분석할 폴더에 연결합니다.

```sh
curl -i -X POST http://127.0.0.1:3000/projects \
  -H 'Content-Type: application/json' \
  -d '{"name":"예제 프로젝트","workspaceKey":"example-project"}'

curl http://127.0.0.1:3000/projects
```

등록 성공 시 `201`과 함께 `id`, `name`, `workspaceKey`, `createdAt`을 반환합니다. `Location` 헤더의 `/projects/{id}` 주소로 상세 정보를 조회할 수 있습니다. 목록 응답은 `{ "projects": [...] }`이며, 아직 등록하지 않았다면 빈 배열입니다. 서버를 다시 실행해도 같은 DB를 사용하면 등록한 프로젝트가 유지됩니다.

이름은 공백만으로 작성할 수 없으며 앞뒤 공백을 제거해 저장합니다. 작업 공간 식별자는 영문·숫자로 시작하고 영문·숫자·점·밑줄·하이픈을 사용할 수 있습니다. 두 입력 모두 최대 100자이며, 정의하지 않은 필드와 잘못된 타입은 `400`으로 거부합니다. 잘못된 ID 형식은 `400`, 없는 프로젝트는 `404`, JSON 이외의 등록 요청은 `415`입니다. [응답·입력·반복 등록 기준](docs/01-architecture.md#1단계-프로젝트-api)을 참고합니다.

프로젝트 등록 요청을 반복하면 각각 새 프로젝트가 생깁니다. 아래 작업(Task) 등록의 요청 키를 통한 중복 방지와 구분합니다.

## 작업 등록·조회

프로젝트 등록 응답의 ID를 사용해 작업을 등록합니다. `requestKey`는 요청을 보내는 쪽에서 정하는 중복 방지 키입니다. 응답을 받지 못해 같은 요청을 다시 보낼 때는 같은 키를 사용하고, 별개의 작업을 만들 때는 새 키를 사용합니다.

```sh
PROJECT_ID="프로젝트 등록 응답의 id"
curl -i -X POST "http://127.0.0.1:3000/projects/$PROJECT_ID/tasks" \
  -H 'Content-Type: application/json' \
  -d '{"instruction":"프로젝트 구조를 분석해줘","requestKey":"inspect-project-001"}'

curl "http://127.0.0.1:3000/projects/$PROJECT_ID/tasks"
```

처음 등록하면 `201`과 작업 정보를 반환합니다. `Location` 헤더의 `/tasks/{id}`로 상세 조회할 수 있으며, 목록 응답은 `{ "tasks": [...] }`입니다. 작업 정보에는 `id`, `projectId`, `instruction`, `requestKey`, `status`, `createdAt`이 포함됩니다.

- 같은 프로젝트에서 같은 키·같은 지시를 다시 보내면 `200`과 기존 작업을 반환합니다. 서버 재시작 후에도 유지됩니다.
- 같은 키에 다른 지시를 보내면 `409`로 거부하고 기존 작업을 유지합니다. 서로 다른 프로젝트에서는 같은 키를 사용할 수 있습니다.
- 지시는 1~10,000자이며 공백만으로 작성할 수 없습니다. 앞뒤 공백을 제거한 뒤 비교·저장하고 내부 줄바꿈은 보존합니다.
- 요청 키는 1~100자이며 영문·숫자로 시작하고 영문·숫자·점·밑줄·하이픈을 허용합니다. UUID도 사용할 수 있습니다.
- 없는 프로젝트·작업은 `404`, 잘못된 입력은 `400`, JSON 이외의 등록 요청은 `415`입니다.

작업은 `queued`(대기) 상태로 등록됩니다. 기본 서버는 등록·조회만 수행하며 아래 CLI에서 한 건을 실행할 수 있습니다. 자동 실행 설정을 지정한 서버는 등록 후 대기열에서 작업을 선택합니다. [작업 API의 상세 기준](docs/01-architecture.md#1단계-작업-api)을 참고합니다.

## Codex로 작업 한 건 분석하기

먼저 비밀 정보가 없는 프로젝트 사본을 준비합니다. 첫 확인에는 저장소의 [예제 프로젝트](examples/analysis-project/README.md)를 사용할 수 있습니다. 지정한 폴더만 읽도록 권한을 설정하며, 코드 수정·웹 검색·외부 도구 연결은 허용하지 않습니다. 런타임 동작에 필요한 시스템 파일은 읽을 수 있습니다. 원본 프로젝트를 자동 복사하거나 비밀 파일을 찾아 제거하는 기능은 아직 없습니다.

agent-hub 전용 인증 폴더에서 ChatGPT 계정으로 로그인합니다. 아래 로그인 명령에는 별도로 설치된 Codex CLI가 필요하며, 분석 실행에는 SDK에 포함된 CLI를 사용합니다. 인증 파일은 Git에서 제외된 `.local/`에 두고 공개하지 않습니다.

```sh
mkdir -p .local/codex
chmod 700 .local/codex
CODEX_HOME="$PWD/.local/codex" codex -c 'cli_auth_credentials_store="file"' login
cp examples/execution.json .local/execution.json
```

[설정 예시](examples/execution.json)는 `.local/execution.json`에 복사해 사용하는 기준입니다. `codexHome`과 작업 폴더의 상대 경로는 이 설정 파일을 기준으로 해석합니다.

```json
{
  "model": "gpt-6.1-sol",
  "codexHome": "./codex",
  "timeoutMs": 300000,
  "workspaces": {
    "example-project": "../examples/analysis-project"
  }
}
```

`model`은 사용하는 계정에서 지원하는 모델을 명시합니다. 위 모델은 실제 예제 분석에 사용한 값이며 모든 계정의 사용 가능 여부를 보장하지 않습니다. effort는 기본 `medium`이며 아래 선택 설정으로 자동 판단을 켤 수 있습니다. `timeoutMs`는 실행 제한 시간으로 기본 5분, 허용 범위는 1초~30분입니다. 전용 인증 폴더의 개인 설정·사용자 스킬과 작업 폴더가 상속하는 `.codex/config.toml`은 실행 전에 거부합니다. Codex가 생성하는 기본 스킬 폴더(`skills/.system`)와 정해진 플러그인 캐시 폴더는 허용하되, 호스트 스킬 탐색·플러그인 실행·원격 플러그인 탐색은 끕니다. API 키 인증으로 자동 전환하지 않습니다.

최초 호출의 추론 강도를 자동으로 고르려면 실행 설정에 다음 항목을 추가합니다. `effortPolicy`를 생략하면 기존처럼 `medium`을 사용합니다.

```json
"effortPolicy": { "mode": "adaptive", "maxEffort": "xhigh" }
```

`medium`·`high`·`xhigh`만 허용합니다. 일반 분석은 medium, 동시성·보안·설계 검토는 high, 여러 시스템의 복잡한 원인 분석은 xhigh를 초기 후보로 고르고 `maxEffort`로 제한합니다. 지시문의 단서를 사용하는 초기 규칙이며 AI 분류 호출을 추가하지 않습니다. 선택 이유·정책 버전·실제 전달 값은 Step에 저장합니다. 기본은 Run당 호출 한 번입니다. 같은 실행 안에서 결과를 이어받는 분석이 필요하면 아래 항목도 추가합니다.

```json
"analysisWorkflow": { "maxSteps": 3, "maxEffortChanges": 2 }
```

호출 수는 1~6, 추론 강도 변경 횟수는 0~`maxSteps - 1` 범위입니다. 생략하면 단일 호출, `{}`로 켜면 최대 3회·변경 2회입니다. 각 호출은 보고서·근거·남은 질문·다음 단계 제안을 반환합니다. 서버가 결과와 다음 호출을 DB에 저장한 뒤에만 다음 SDK 세션을 시작합니다. 이전 보고서와 원래 지시를 전달하며 같은 Run의 Step으로 남깁니다. 진행 중인 호출의 설정을 바꾸지는 않습니다.

제안한 effort는 서버의 고정 정책·상한·변경 횟수로 다시 제한합니다. 알 수 없는 effort는 medium을 후보로 사용합니다. 형식이 잘못되면 `invalid_plan`, 필요한 입력이 없으면 `analysis_incomplete`, 호출 수 또는 전달 맥락 상한이면 `workflow_limit`으로 보류합니다. 부분 분석은 단계 기록에서 확인할 수 있으며 전체 성공으로 표시하지 않습니다. Run 제한 시간과 Task 누적 시간은 단계가 바뀌어도 새로 시작하지 않습니다. 다단계 분석은 추가 호출을 소비하므로 한 번에 충분한 작업에는 켤 필요가 없습니다.

앞서 `workspaceKey`를 `example-project`로 등록했다면, 해당 프로젝트의 작업 ID로 실행합니다. CLI와 서버는 같은 DB를 사용해야 합니다. `DATABASE_PATH`를 바꿨다면 양쪽에 같은 값을 지정합니다.

```sh
TASK_ID="작업 등록 응답의 id"
pnpm task:run --task "$TASK_ID" --config "$PWD/.local/execution.json"
curl "http://127.0.0.1:3000/tasks/$TASK_ID/runs"
```

CLI는 `runId`와 상태를 출력합니다. 실행 상세에는 분석 결과, 오류 분류, 호출 단계(Step), 제공된 토큰 사용량, 이벤트 종류·시각이 포함됩니다.

```sh
RUN_ID="CLI가 출력한 runId"
curl "http://127.0.0.1:3000/runs/$RUN_ID"
```

현재는 같은 DB에서 한 번에 실행 하나만 허용합니다. 인증·설정 오류는 `blocked`, 확인된 사용 한도 오류는 `waiting_capacity`로 보존하고 공통 차단 기록으로 다른 작업의 실행도 보류합니다. 중단 후 종료 미확인은 `interrupted`로 남깁니다. 컨테이너 종료가 확인되면 사용자 취소·범위 축소는 서로 다른 사유를 가진 `cancelled`, 시간 초과는 `failed`, 서버 종료는 `waiting_retry`로 확정합니다. 자동 복구를 켜면 재시도 가능한 오류와 서버 중단을 처리하며, 꺼져 있으면 수동 재개를 기다립니다. 프로세스가 강제 종료되면 DB에 `running`이 남을 수 있으므로 이전 실행을 대조하기 전에는 후속 실행을 막습니다.

중단 요청에 SDK가 응답하지 않아도 결과 대기를 끝내고, 종료 근거가 없으면 `interrupted`를 저장합니다. 뒤늦은 결과·오류·이벤트는 이 기록을 덮어쓰거나 닫힌 DB에 접근하지 않습니다. DB 저장이 실패하면 기존 `running` 기록이 남아 다음 실행을 막습니다. 수동 CLI도 결과 처리 후 SDK 때문에 종료되지 않으면 10초 뒤 부모 CLI를 종료하며, DB 저장 실패로 종료 절차에 들어온 경우에도 같은 제한을 적용합니다.

컨테이너 실행은 아래 [수동 복구 API](#중단된-작업-재개취소하기)로 종료를 확인하고 재개할 수 있습니다. 직접 SDK 실행과 구버전처럼 종료 근거가 없는 기록은 요청만으로 해제하지 않습니다. DB의 `running` 표시는 현재 프로세스가 살아 있다는 확인 결과가 아닙니다. 이 버전은 준비된 예제의 실행 연결을 확인하는 단계이며 24시간 자율 운영 버전은 아닙니다.

`GET /runs/{id}`에는 `stopReason`, `stopRequestedAt`, `terminationConfirmedAt`도 포함됩니다. 중단 이유는 사용자 취소(`user_cancel`), 허용 범위 축소(`scope_changed`), 서버 종료(`server_shutdown`), 시간 초과(`timeout`), 기간 예산 소진(`budget_limit`), 구분할 수 없는 중단(`unknown`)입니다. 중단 요청을 저장한 뒤 실행에 신호를 보냅니다. 저장 실패 시에도 중단은 요청하지만 Run을 해제하거나 정상 처리하지 않습니다.

Run의 `attempt`는 같은 작업에서 몇 번째 실행인지 나타냅니다. 첫 실행은 1이며 새 배정마다 증가합니다. 실행 목록은 시도 번호가 큰 순서로 반환하므로 시계가 달라지거나 시작 시각이 같아도 가장 최근 실행을 구분할 수 있습니다. 취소 의도가 기록된 작업은 대기 상태로 잘못 바뀌어도 다시 배정하지 않습니다.

수동 CLI의 `Ctrl+C`는 사용자 취소, `SIGTERM`과 자동 서버의 종료는 서버 종료로 기록합니다. `terminationConfirmedAt`은 분석 결과의 `finishedAt`과 별개이며 성공한 응답만으로 채우지 않습니다. 직접 SDK를 실행하는 기본 모드와 구버전 기록은 `null`입니다. 구버전 중단 기록은 실제 요청 시각을 알 수 없어 `stopRequestedAt`도 `null`일 수 있습니다.

### 컨테이너로 실행 종료 확인하기

Docker를 사용할 수 있는 일반 사용자 계정에서 실행합니다. root 실행은 지원하지 않습니다. 준비한 작업 폴더와 전용 인증 폴더는 이 사용자가 읽고 쓸 수 있어야 합니다. 모델이 읽는 작업 폴더는 컨테이너 안에서 읽기 전용으로 연결됩니다.

```sh
docker build -f docker/analysis-runner.Dockerfile -t agent-hub-analysis:local .
```

실행마다 저장소의 seccomp 정책을 명시해 Docker 엔진의 기본 설정에 의존하지 않습니다. 서버의 `dist/`만 따로 배포한다면 `apps/server/security/`도 같은 패키지에 보관해야 합니다. AppArmor를 사용하는 Linux Docker 엔진에서는 agent-hub를 시작하기 전에 전용 프로필을 한 번 설치합니다. 정책을 갱신할 때는 기존 agent-hub 실행을 종료한 상태에서 적용합니다.

```sh
# docker info의 SecurityOptions에 name=apparmor가 있는 Linux 호스트에서 실행
sudo apparmor_parser -r apps/server/security/agent-hub-codex.apparmor
```

앱이 관리자 권한으로 호스트 정책을 자동 변경하지는 않습니다. AppArmor가 있는 엔진은 지정한 프로필을 사용하며, 프로필이 없으면 실행이 거부됩니다. Docker Desktop처럼 AppArmor가 없는 엔진에도 seccomp·권한 제거·읽기 전용 파일 시스템은 적용합니다. [정책의 원본·추가 허용 범위와 검증](apps/server/security/README.md)을 확인할 수 있습니다.

비공개 실행 설정에 `"containerImage": "agent-hub-analysis:local"`을 추가하면 같은 서버·CLI가 Run마다 로컬 컨테이너 하나에서 SDK를 실행합니다. 설정을 생략하면 기존 직접 실행입니다. 실행 시 이미지를 내려받거나 Docker를 자동 설치하지 않습니다. runner 코드를 변경한 뒤에는 이미지를 다시 빌드합니다.

컨테이너 전체 ID·임의 실행 토큰·Docker 엔진 ID를 실행 전에 저장합니다. 중단 때 이 식별자를 대조하고 해당 컨테이너만 종료하며, PID namespace 전체의 종료를 확인해야 `terminationConfirmedAt`을 기록합니다. 아직 시작하지 않은 컨테이너는 삭제가 성공해야 뒤늦은 시작도 불가능한 것으로 처리합니다. 종료를 확인할 수 없으면 결과가 있어도 `interrupted`로 보류합니다. DB 저장을 마친 컨테이너는 정리하고 실행 기록은 남깁니다.

Docker 연결 실패·다른 엔진·잘못된 식별자·이미 사라진 컨테이너는 종료의 근거가 아닙니다. 사용자 PC의 Docker에 실행 수명을 맡기며, Docker 소켓·호스트 PID 공간·관리자 권한은 컨테이너에 전달하지 않습니다. 인증은 모델 명령의 파일 접근 규칙으로 차단하고 원래의 전용 폴더에서 갱신할 수 있게 합니다.

실제 컨테이너 수명 검증은 아래 명령으로 실행합니다. 일반 `pnpm test`는 Docker가 필요한 테스트를 건너뜁니다. 실행 수명 검증은 모의 runner를 사용하고, 별도로 실제 분석 이미지·고정 Codex CLI의 파일 읽기·권한 제한을 검사합니다. AI를 호출하거나 실제 인증을 읽지는 않습니다.

```sh
RUN_CONTAINER_TESTS=1 pnpm test
```

### 자동 복구 켜기

종료 확인을 지원하는 컨테이너 설정에 `automaticRecovery`를 추가하고 서버를 다시 시작합니다. 빈 객체 `{}`는 아래 기본값을 사용합니다. 설정을 생략하면 수동 복구 모드이며, CLI는 정책을 적용한 작업 한 건만 실행합니다. 서버의 자동 대기열이 재시도 예약을 처리합니다.

```json
{
  "containerImage": "agent-hub-analysis:local",
  "automaticRecovery": {
    "initialDelayMs": 10000,
    "maxDelayMs": 300000,
    "jitterRatio": 0.2,
    "maxRetries": 3,
    "maxConsecutiveErrors": 3,
    "maxTotalRunMs": 1800000
  }
}
```

위 항목을 기존 실행 설정에 추가합니다. 일시적인 네트워크·서비스 오류(`transient`), 정상 서버 종료, 강제 종료 뒤 소유자를 잃은 실행이 자동 복구 대상입니다. 이전 컨테이너의 종료를 먼저 확인하고, 재시도 시각이 되면 같은 Task에 새 Run을 만듭니다. 실패 원문이나 정체를 알 수 없는 오류를 모두 재시도 대상으로 취급하지 않습니다.

| 설정 | 기본값과 의미 | 허용 범위 |
| --- | --- | --- |
| `initialDelayMs` | 최초 대기 10초. 이후 재시도 횟수에 따라 2배 증가 | 1초~1시간 |
| `maxDelayMs` | 추가 지연까지 포함한 최대 대기 5분 | 최초 간격 이상, 최대 24시간 |
| `jitterRatio` | 같은 시각에 반복 호출하지 않도록 0~20% 추가 지연 | 0~0.5 |
| `maxRetries` | 첫 실행 이후 최대 3번의 새 실행 | 0~20 |
| `maxConsecutiveErrors` | 같은 오류가 3번 연속 발생하면 보류 | 1~20 |
| `maxTotalRunMs` | 한 Task의 누적 실행 30분 | 1초~24시간 |

정책은 첫 배정 또는 기존 미완료 작업의 첫 자동 복구 검사에서 Task에 저장합니다. 서버 재시작·설정 수정·수동 재개로 횟수와 누적 시간을 초기화하지 않습니다. 새 설정은 아직 정책이 없는 작업에 적용하며, 기존 작업의 상한을 늘리는 API는 아직 없습니다. 새 Run 배정에서만 재시도 횟수를 늘리고 대기 시간은 실행 시간에 합산하지 않습니다. 강제 종료된 실행은 시작부터 종료 확인 시각까지 보수적으로 계산합니다. 다음 Run에는 전체 제한 시간과 남은 누적 시간 중 더 짧은 제한을 적용합니다.

종료 근거가 없으면 자동 대조 한 번 후 보류하고, 화면에서 다시 종료 확인을 요청할 수 있습니다. 사용자 취소·시간 초과·재시도 불가능한 오류는 자동으로 다시 실행하지 않습니다. 사용량·인증·설정 차단도 우회하지 않습니다. 사용량 제한은 아래 계정별 확인 정책으로 처리하며 인증·설정 차단은 사용자 조치를 기다립니다.

작업 조회의 `retryState`와 관리 화면에서 정책·횟수·누적 시간·다음 시각·보류 이유를 확인합니다. `/execution`의 `automaticRecoveryEnabled`는 현재 서버에서 자동 복구가 켜져 있는지 알려줍니다. 실행 이벤트에는 예약·보류 이유를 남기며 외부 알림 채널 전송은 아직 연결하지 않았습니다.

### 한도·인증·설정 차단 확인하기

`GET /execution/provider-gate`로 현재 차단 여부(`blocked`), 사유(`capacity`·`authentication`·`configuration`), 변경 버전(`version`), 원인 실행(`sourceRunId`)과 제공된 재시도 가능 시각(`retryAt`)을 조회합니다. 현재는 한 계정을 전제로 Codex 로그인 전체를 같은 범위로 묶어 인증 폴더·모델·프로젝트 변경으로 차단이 사라지지 않게 합니다. 계정 ID·인증 경로는 응답에 넣지 않습니다.

```sh
curl http://127.0.0.1:3000/execution/provider-gate
```

`retryAt: null`은 시각 미제공입니다. SDK 오류에 `try again at 2030-01-01T09:00:00+09:00`처럼 시간대가 포함된 절대 시각이 있을 때만 저장합니다. `오전 9시`와 같은 표현으로 회복 시각을 추정하지 않습니다. 시각이 지나도 차단은 유지되며, 명시적으로 예약한 확인 실행 하나가 성공하고 종료까지 확인돼야 해제됩니다. 실패·중단·저장 오류는 차단을 유지합니다. 확인 실행의 작업·실행 ID는 `probeTaskId`·`probeRunId`입니다. 아래 수동 재개 요청에 현재 차단 버전을 보내 확인 실행을 예약합니다.

`automaticRecovery`를 켜면 한도 자동 확인도 기본으로 켜집니다. 다음 설정은 선택 사항이며 `automaticRecovery` 안에 추가합니다.

```json
"capacity": {
  "initialDelayMs": 900000,
  "maxDelayMs": 21600000,
  "jitterRatio": 0.2,
  "maxChecks": 3
}
```

최초 15분, 최대 6시간, 0~20% 추가 지연, 계정 확인 최대 3회가 기본입니다. 간격은 1초~24시간 안에서 최초 ≤ 최대, 추가 지연은 0~0.5, 횟수는 1~20으로 설정할 수 있습니다. 제공자의 `retryAt`과 내부 대기 간격 중 더 늦은 시각을 `capacityState.nextCheckAt`으로 저장합니다. `retryAt`이 미제공이면 그대로 null이며, 내부 예약을 제공자의 회복 약속처럼 표시하지 않습니다.

계정 정책·확인 횟수·다음 시각은 ProviderGate의 `capacityState`에 보존합니다. 실제 확인 Run을 배정할 때만 횟수를 늘립니다. 실패하면 완료 저장과 함께 다음 대기 시각을 갱신하므로 수동 요청도 그 사이에 재호출하지 못합니다. 프로젝트·Task 변경이나 서버 재시작으로 계정 횟수가 초기화되지 않습니다. 성공 결과와 실제 종료를 확인하면 차단을 풀고 해당 차단 기간의 계정 정책을 마칩니다.

자동 확인은 원인 작업을 다시 사용하며 Task의 재시도·연속 오류·누적 시간 상한도 적용합니다. 계정 상한과 Task 상한 중 먼저 도달한 조건으로 보류합니다. 원인 작업이 취소됐거나 실행할 수 없으면 자동으로 다른 Task를 고르지 않고 필요한 조치를 표시합니다. 수동으로 다른 대기 작업을 선택할 수 있지만 계정 상한과 대기 시각은 그대로 적용됩니다. 현재 기존 정책 상한을 늘리는 API는 없습니다.

`"capacity": false`로 새 자동 확인 예약만 끌 수 있습니다. 이미 접수된 예약과 저장된 계정 제한은 유지합니다. `/execution`의 `capacityRecoveryEnabled`와 화면에서 현재 자동 확인 활성 여부를 확인합니다. 종료 미확인 확인 실행은 예약·버전을 보존하고 기존 실행을 대조한 뒤에만 결과를 확정합니다.

확인할 작업의 목표를 멈추거나 수정해 실행할 수 없어지면, 자동 확인은 다른 적격 대기 작업을 선택합니다. 이미 시작한 실행은 바꾸지 않으며, 기존 계정 대기 시간·확인 횟수와 후보 작업의 예산·취소·재시도 제한을 유지합니다. 적격 작업이 없으면 계정 차단을 보존합니다.

Run의 과거 보류 상태를 삭제하지 않고 현재 차단 조건을 별도로 관리합니다. 종료가 확인된 과거 `interrupted`는 실행 자리를 계속 점유하지 않습니다. 종료 미확인 실행과 제공자 차단은 각각 새 배정을 막습니다. 설정 오류도 공통 차단하므로 잘못된 모델·실행 환경으로 대기 작업을 연속 실패시키지 않습니다.

## 중단된 작업 재개·취소하기

`EXECUTION_CONFIG`로 실행을 켠 서버가 복구 요청을 처리합니다. 재개에는 `containerImage`를 설정한 실행 환경이 필요합니다. 조회 전용 서버는 복구 요청을 `503 / EXECUTION_DISABLED`로 거부합니다.

먼저 `/tasks/{id}/runs`에서 가장 최근 Run ID를 확인합니다. 실행 이력이 없으면 `runId`에 `null`을 보냅니다. 한도·인증 차단이 있으면 `/execution/provider-gate`의 현재 `version`도 함께 보냅니다.

```sh
curl -i -X POST "http://127.0.0.1:3000/tasks/$TASK_ID/recovery-requests" \
  -H 'Content-Type: application/json' \
  -d '{"requestKey":"resume-001","runId":"최근 실행의 UUID","action":"resume"}'
```

| `action` | 하는 일 |
| --- | --- |
| `resume` | 이전 실행의 종료·저장 결과와 현재 차단 조건을 확인한 뒤 같은 작업을 대기열에 넣음. 다음 배정에서 새 Run 생성 |
| `reconcile` | 이전 실행을 종료·확인하고 저장된 상태만 확정. 새 실행은 예약하지 않음 |
| `cancel` | 취소 의도를 먼저 저장하고 해당 실행만 중단. 실제 종료가 확인돼야 취소 완료 |

새 요청은 `202`와 요청 ID, 조회 주소인 `Location: /recovery-requests/{id}`를 반환합니다. 이 응답은 접수이며 작업 재개 성공을 뜻하지 않습니다. 조회 응답의 `status`는 `pending`(확인 중), `completed`(처리 완료), `rejected`(조건 미충족)입니다. `resultStatus`는 요청을 처리한 시점의 작업 상태이므로 현재 상태는 `/tasks/{id}`로 확인합니다.

같은 작업에 같은 `requestKey`·내용을 다시 보내면 `200`과 같은 접수 기록을 반환합니다. 내용이 다르면 `409 / REQUEST_KEY_CONFLICT`입니다. 실패 원인을 해결해 새로 시도할 때는 새 키를 사용합니다. 이전 Run을 대상으로 보낸 새 요청은 `409 / STALE_RUN`이며 가장 최근 기록을 다시 조회해야 합니다.

차단 확인 요청은 본문에 `"providerGateVersion": 1`처럼 조회한 버전을 추가합니다. `retryAt` 이전 요청은 `RETRY_TOO_EARLY`, 달라진 버전은 `GATE_CHANGED`, 이미 예약한 확인 실행은 `PROVIDER_CHECK_RESERVED`로 거부합니다. 시각 미제공 때는 수동 확인 하나를 허용하며 자동 반복하지 않습니다. 아직 한 번도 실행하지 않은 대기 작업도 `runId: null`과 차단 버전으로 확인 실행을 요청할 수 있습니다.

종료 근거가 없는 요청은 `rejected / TERMINATION_UNCONFIRMED`로 남습니다. 실제로 실행이 끝났는지 확인할 수 있을 때 새 요청을 보냅니다. 클라이언트가 종료 시각이나 컨테이너 ID를 제출해 이 조건을 우회할 수 없습니다. 구버전의 모호한 중단은 `UNKNOWN_STOP_REASON`으로 재개를 거부합니다. 현재 서버가 처리 중인 실행의 재개는 `RUN_ACTIVE`로 거부하며, 사용자 취소가 기록된 작업은 재개하지 않습니다.

취소는 확인 중인 재개보다 우선합니다. 한도 때문에 보류된 작업을 취소해도 제공자 차단은 유지합니다. 복구 요청은 DB에 저장돼 서버 재시작 후 이어지고, 종료 관측은 DB 처리 밖에서 최대 8초 기다립니다. 확인 중에도 상태 조회는 응답합니다.

## 서버가 대기 작업을 자동으로 실행하게 하기

앞 절의 인증 폴더·분석 대상·설정 파일을 준비한 뒤 저장소 루트에서 실행합니다. 소스 변경으로 서버가 자동 재시작되는 개발 모드보다 빌드한 서버로 실행 흐름을 확인하는 것을 권장합니다.

```sh
pnpm build
LOCAL_API_ONLY=1 EXECUTION_CONFIG=.local/execution.json pnpm start
```

`EXECUTION_CONFIG`를 지정해야 자동 실행을 켭니다. 상대 경로는 저장소 루트 기준이며, 설정 값 변경은 서버를 재시작하면 적용됩니다. 기본 `pnpm dev`·`pnpm start`는 이 변수가 없으면 AI를 호출하지 않습니다.

서버는 설정에 연결된 프로젝트의 `queued` 작업 중 먼저 등록한 작업을 선택합니다. 등록 시각이 같으면 ID 순서로 처리하며, 설정에 없는 `workspaceKey`의 작업은 대기로 남기고 건너뜁니다. 작업 선택·실행 상태 변경·Run 생성은 함께 저장합니다. 분석이 끝나면 다음 작업으로 넘어가고, 처리할 작업이 없거나 보류 상태이면 1초마다 DB와 실행 환경을 다시 확인합니다. 이 대기 확인에는 AI를 호출하지 않습니다.

현재 서버의 자동 실행 상태는 다음 API로 조회합니다.

```sh
curl http://127.0.0.1:3000/execution
```

| `state` | 의미 |
| --- | --- |
| `disabled` | 이 서버에서 자동 실행을 켜지 않음 |
| `idle` | 설정에 연결된 실행 가능한 대기 작업이 없음 |
| `running` | 이 서버가 분석 호출을 처리 중. `runId`·`taskId`로 상세 조회 |
| `recovering` | 접수한 재개·상태 확인·취소 요청 처리 중. `reason`은 요청 action |
| `held` | 기존 실행·인증·사용 한도 문제로 다음 호출 보류. `runId`·`reason` 확인 |
| `error` | 실행 전 환경 검사 또는 DB 저장 문제. `reason`은 `configuration_invalid` 또는 `storage_error` |
| `stopping` / `stopped` | 새 배정을 중지하고 종료 중 / 실행 루프 종료 |

`lastCheckedAt`은 대기열을 마지막으로 확인한 시각입니다. 실행 중인 AI의 생존·진척 시각은 아니며, 최근 활동과 결과는 `/runs/{id}`에서 확인합니다. `disabled`는 수동 CLI나 다른 서버의 실행 여부까지 뜻하지 않습니다. API에는 인증 파일·개인 폴더·내부 잠금 정보가 포함되지 않습니다. 서버 종료 중에는 상태 응답 대신 503 또는 연결 종료가 보일 수 있습니다.

대기열 검사 오류는 서버 로그의 `execution_queue.error`에서 확인합니다. 실패한 단계(`recovery`·`validation`·`claim`·`execution`), 확인된 오류 코드, 고정된 설명, 관련 Run·Task ID와 발생 횟수를 남깁니다. 오류 원문·스택·파일 경로·SQL은 기록하지 않으며 미분류 오류는 `UNKNOWN_ERROR`입니다. 같은 단계·실행·오류 코드는 처음과 이후 1분 간격으로 기록합니다. 해당 단계가 정상적으로 확인되면 `execution_queue.recovered`를 한 번 남깁니다. 이 로그는 보류된 Run의 복구 완료를 뜻하지 않습니다.

같은 DB로 자동 실행 서버를 두 개 켜거나, 자동 실행 서버가 켜진 상태에서 `pnpm task:run`을 실행하면 거부합니다. 수동 실행은 자동 실행 서버를 종료한 뒤 사용합니다. 설정에 연결된 폴더와 인증 상태는 매 호출 전에 다시 확인하며, 환경 검사 실패 시 새 Run을 만들지 않습니다. 파일 상태를 바로잡으면 검사를 다시 통과할 수 있지만, 이미 Run에 기록된 인증·한도·중단 보류는 자동 해제하지 않습니다.

`Ctrl+C`·`SIGTERM`을 받으면 새 배정을 멈추고 현재 분석에 중단을 요청한 뒤 기록을 저장합니다. HTTP·DB를 닫았어도 SDK 때문에 프로세스가 남아 있으면 종료 요청 10초 뒤 부모 서버를 종료합니다. 정상 종료가 빨리 끝나면 10초를 기다리지 않습니다. 재시작 시 이전 부모 프로세스가 사라졌더라도 미완료 Run은 그대로 다음 호출을 막습니다. 정상 완료한 작업은 재시작해도 다시 실행하지 않습니다.

## 로컬 DB와 테이블 변경

기본 DB 파일은 저장소 루트의 `data/agent-hub.sqlite`입니다. 서버 시작 시 디렉터리와 DB를 만들고, `apps/server/migrations/`의 SQL 중 아직 적용하지 않은 변경을 순서대로 적용합니다. 성공해야 HTTP 요청을 받으며, DB 열기나 마이그레이션에 실패하면 시작을 중단하고 오류를 기록합니다. 정상 종료 시 DB 연결도 닫습니다.

다른 DB 파일을 사용하려면 셸 환경 변수로 경로를 전달합니다. 상대 경로는 개발 실행·빌드 실행 모두 저장소 루트를 기준으로 해석하고, 절대 경로도 사용할 수 있습니다.

```sh
DATABASE_PATH=data/dev.sqlite pnpm dev
```

기본 `data/` 디렉터리, `*.sqlite`·`*.db` 파일과 그에 붙는 SQLite 임시·로그 파일은 Git에서 제외합니다. 테스트는 별도의 임시 디렉터리에 DB를 만들어 사용합니다.

DB에는 비공개 작업 지시·분석 결과·로그인 세션이 저장됩니다. 새 DB 폴더는 소유자만 접근하는 `0700`, DB 파일은 소유자만 읽고 쓰는 `0600`으로 만듭니다. 기존 DB와 WAL·SHM·journal 보조 파일도 소유자를 확인한 뒤 `0600`으로 제한하며 데이터는 유지합니다. 다른 계정이 파일을 바꿔치기할 수 있는 쓰기 가능한 폴더, 다른 소유자의 파일, 심볼릭 링크·하드 링크는 거부합니다. 기존 상위 폴더의 권한은 자동으로 바꾸지 않습니다. 이 보호는 같은 운영 계정으로 실행되는 프로그램이나 관리자까지 차단하는 기능은 아닙니다.

테이블을 바꿀 때는 다음 순서를 따릅니다.

1. `apps/server/src/db/schema.ts`에서 테이블 정의를 수정합니다.
2. `pnpm db:generate --name=변경이름`으로 SQL과 변경 기록을 생성합니다.
3. 생성된 SQL을 검토하고, 빈 DB 적용·기존 데이터 보존·실패 시 되돌리기를 테스트합니다.
4. 스키마와 `migrations/`를 함께 커밋합니다. 검토한 변경은 다음 서버 시작 때 적용됩니다.

이미 적용한 마이그레이션은 수정하지 않고 새 변경을 추가합니다. 빌드한 서버를 실행할 때도 `apps/server/migrations/`가 함께 있어야 합니다. `0000_projects.sql`은 프로젝트, `0001_tasks.sql`은 작업과 등록 중복 방지 조건을 생성합니다. `0002_execution.sql`은 기존 작업을 보존하며 상태를 확장하고 실행·호출 단계·이벤트 테이블을 추가합니다. `0003_execution_queue.sql`은 실행 소유권 테이블과 대기 작업 선택용 인덱스를 추가합니다.

`0004_execution_stop_evidence.sql`은 중단 요청 사유·시각과 종료 확인 시각을 추가합니다. 기존 실행 이력을 유지하며, 예전 `cancel_requested`는 사유가 불명확한 `unknown`으로 옮기고 실제 요청·종료 시각은 추정하지 않습니다.

`0005_execution_identity.sql`은 비공개 실행 식별 정보를 추가합니다. 기존 실행에는 식별자를 만들어 넣지 않으며 API에도 컨테이너 ID·실행 토큰을 노출하지 않습니다.

`0006_provider_gate.sql`은 제공자 차단·확인 실행 예약과 재시도 시각을 추가합니다. 기존 한도·인증·설정 보류도 차단 기록으로 옮기며, 과거 이력은 보존합니다. 실행 자리의 유일성 조건은 현재 실행과 종료 미확인 보류에 적용합니다.

`0007_completion_states.sql`은 취소 상태와 실행 시도 번호를 추가합니다. 기존 작업을 참조하는 Run·Step·이벤트·차단 기록을 보존하며, 마지막 외래 키 검사에 실패하면 테이블 변경과 마이그레이션 기록을 함께 취소합니다.

`0020_task_goal_review.sql`은 기존 Task·Run·복구 기록을 유지하며 작업의 최근 목표 범위 검사 근거를 추가합니다. 이전 작업의 값은 `null`이며 검사하지 않은 작업을 확인 완료로 표시하지 않습니다.

## 구성

```mermaid
flowchart TD
    User[사용자 브라우저] --> API
    subgraph Hub[agent-hub 백엔드]
        API[관리 API] --> Tasks[작업 관리]
        API --> Goals[프로젝트 목표]
        Goals --> Planner[총괄: 상태 점검·다음 작업 선택]
        Planner --> Tasks
        Tasks --> Worker[실행 모듈]
        Tasks -->|완료·검증 결과| Planner
    end
    Tasks <--> DB[(SQLite)]
    Worker -->|이벤트·결과| Tasks
    Goals <--> DB
    Worker --> Agent[총괄·개발·검증 역할의 Codex 실행]
    Agent --> Workspace[프로젝트별 작업 공간]
    Worker --> Artifacts[결과 파일]
```

첫 배포에서는 빌드한 관리 화면과 API를 같은 백엔드에서 제공합니다. 내부 모듈끼리는 함수 호출로 연결하며 별도 HTTP 통신을 만들지 않습니다. AI 모델 연산은 외부 서비스에서 수행하고, 코드 읽기·명령 실행 등은 서버의 Codex 실행 환경에서 수행합니다. 여러 서버가 필요해지면 실행 모듈을 별도 프로그램으로 분리합니다.

위 그림은 목표 구조입니다. 현재는 백엔드 내부의 자동 실행 루프 또는 같은 서버 패키지의 CLI에서 실행 모듈을 호출합니다. 목표를 읽고 새로운 일을 만드는 총괄·개발·검증의 자율 협업은 후속 구현입니다.

## 문서와 구현 상태

현재 구현된 범위는 위 로컬 실행 안내와 [구현 계획의 진행 상태](docs/02-implementation-plan.md#현재-진행-상태)에서 확인할 수 있습니다. 설계 문서의 “수행한다”, “검증한다”는 구현할 동작을 뜻하며, 완료 기록이 없는 항목까지 이미 동작한다는 뜻은 아닙니다. 초기 수치와 세부 정책은 설계 기본안입니다. 구현과 측정 결과에 따라 변경하고, 변경 이유를 해당 문서에 기록합니다.

## 공개 저장소와 실제 운영 데이터

이 저장소에는 프로그램 코드, 설계 문서, 가상 설정 예시를 보관합니다. 실제 프로젝트 소스, 서버 접속 정보, 인증 정보, 작업 DB, 실행 로그, 에이전트 대화와 결과 파일은 별도 비공개 저장소에 둡니다.

공개 저장소라는 사실이 관리 화면이나 실행 API의 공개 접근을 의미하지 않습니다. 원격 운영 전 사용자 인증과 HTTPS를 적용합니다. 실행 프로그램을 서버 밖으로 분리하는 단계에서는 프로그램 간 인증도 추가합니다. 공개 저장소의 코드 변경 제안(PR)을 자동 검사하는 절차(CI)에서 개인 계정으로 인증한 에이전트를 호출하지 않습니다.

소스 저장소 공개와 프로그램의 운영 배포는 별도 단계입니다. 공개 재사용을 허용할 라이선스는 별도로 선택합니다.
